## 5. 已确认问题分级

### 5.1 立即进入主线

#### R-001：初始化事务清理过早删除所有权标记

`store.py` 当前安全树把事务根加入目录集合，清理逻辑又先删除包括 `transaction.yaml` 在内的文件，再删除目录。若中途失败，可能留下失去可验证所有权标记的事务残片。

影响：不会直接覆盖已提交 Item，但会破坏恢复清理不变量，使本应可回收的自有残片永久变成未知树。

结论：真实缺陷，优先修复；不是简单移动一行，而是需要把内容文件、内容目录、marker 和事务根分开表达。

#### R-002：配置临时文件没有绑定精确目标身份

不同配置目标在同一父目录下使用不同锁，但配置临时文件采用共享模式扫描；当两个请求产生相同配置字节时，一个请求可能清理另一个请求的在途临时文件。

影响：并发初始化可能异常失败；现有“内容相同”不足以证明文件属于当前请求。

结论：真实缺陷，优先修复；身份应绑定精确配置路径、完整请求摘要和预期内容，不能只依赖截断 tag。

## 6. 总体执行原则

所有后续批次遵守：

1. 一批只解决一个可复核目标；测试、实现和必要文档同批闭合。
2. 每批都需要明确授权，上一批完成不自动授权下一批。
3. 除非用户另行明确要求，所有测试只使用测试持有的临时 Store。
4. 不创建或探测性写入生产配置、`E:\KnowledgeFlowData\capture-store` 或其他真实知识库。
5. 不调用网络、模型、GBrain、账号或 API key，除非对应实验另获授权。
6. 不提交故意失败的测试；未来场景先登记到测试矩阵，在所属功能批次与实现一起转绿。
7. 不为代码行数、覆盖率或类型检查提前重构稳定的 C2/C3 实现。
8. 不删除未知 staging、旧评估目录、fixtures 或用户文件。
9. 每批结束报告改动文件、测试数量、命令结果、未证明项和下一停点。
10. Git commit、push、建分支继续视为独立授权；代码完成不自动提交或推送。

## 7. 详细实施阶段

## 7.1 R0.1：初始化事务清理所有权修复

### 目标

保证所有权 marker 在所有自有内容被安全移除前始终存在；清理失败后，同一请求仍可在下一次初始化中验证并恢复自有事务树。

### 实现范围

- 调整 `src/knowledgeflow_capture/store.py` 中安全树的内部表示。
- 将事务树拆分为：
  - `content_files`
  - `content_directories`
  - `marker_path`
  - `transaction_root`
- 固定删除顺序：

```text
unlink(content_files)
  -> rmdir(content_directories，按深度逆序)
  -> unlink(marker_path)
  -> rmdir(transaction_root)
```

- 清理任一步失败时保持 fail-closed，不扩大到未知树。

### 测试范围

- 在内容文件删除失败时，marker 仍存在。
- 在内容目录删除失败时，marker 仍存在。
- 下一次相同初始化请求可以识别并清理残片。
- marker 不匹配、树结构未知或路径身份变化时完全不删除。
- marker 删除完成后只允许留下空事务根；不得留下带内容但无 marker 的树。

故障注入属于 `_InitFaultPoint`/初始化测试支持，不使用 `_CaptureFaultPoint`。

### 非目标

- 不修改 `capture_text` staging。
- 不实现 C6 的业务事务启动恢复。
- 不顺带重构所有路径或错误类型。

### 完成门禁

- 新增的针对性测试通过。
- C3V 的 144 项基线及新增测试在普通模式、严格 `ResourceWarning` 模式均通过。
- `compileall`、依赖检查和 `git diff --check` 通过。
- 未创建生产制品。

完成记录（2026-09-11）：提交 `92a37b3` 调整初始化事务安全树和删除顺序，新增 INIT-17 与 FI-07；普通与严格模式全量均增至 146 项。内容删除失败时 marker 保留，清理在 marker 删除前被强制终止后，新进程仍能验证归属并恢复；未知残片与生产路径未被触碰。

## 7.2 R0.2：配置临时文件精确所有权

### 目标

确保配置父目录中并行的不同初始化请求不能相互删除临时文件。

### 推荐设计

- 以规范化后的精确目标配置路径参与 request identity。
- 使用完整 `request_sha256`，不采用 16 hex 截断作为唯一身份。
- 清理候选时同时核对：
  - 文件名中的请求身份；
  - 目标配置身份；
  - 预期规范配置字节；
  - 必要的普通文件/非 reparse 身份。
- 对旧版无身份或无法完整证明所有权的临时文件保守保留。

### 测试范围

- 同一父目录、不同配置路径、相同 Capture root、相同配置内容并发初始化。
- 当前请求只能删除自己的候选。
- 外来同名、错误字节、错误身份、reparse 候选均不删除。
- 同一目标仍受现有配置锁串行化且保持幂等。

### 完成门禁

与 R0.1 相同，并要求测试采用确定性屏障，不以概率竞态作为唯一证据。

完成记录（2026-09-11）：提交 `79515ed` 以完整 `request_sha256 + transaction_id` 命名配置临时文件，清理同时核对请求身份、普通非 reparse 文件和规范配置字节；新增 INIT-18/INIT-19，以确定性屏障证明不同配置目标不互删在途文件，并证明身份匹配但字节不符的候选会保留。普通与严格模式全量均增至 148 项，生产路径与外部系统未被触碰。

## 7.3 R0.3：初始化错误语义分诊

## 7.5 C4-0：读取契约收口

C4-0 是文档/契约批次，不实现公开操作。用户已于 2026-09-13 授权，以下项目已经逐项形成明确结论。

### A. 正文传输和内存边界

裁定：`get_capture` 返回结构化元数据和 `body_length_bytes`，正文不嵌入结果，而是写入调用方提供的二进制 sink。实现先用 Store 外、测试或运行时拥有的磁盘 spool 完成“验证后再公开”。

必须满足：

- Store→spool 和 spool→sink 的单次块大小均不超过 1 MiB。
- 64 MiB 正文不整体常驻内存。
- 哈希、字节数或 Envelope 校验失败时，不向调用方暴露部分正文。
- Store 读取/完整性失败时 sink 为零字节；sink 写失败使用 `output_write_failed` 和固定消息，调用方丢弃可能存在的部分输出后以新/空 sink 重试。

### B. 已提交版本的判定

必须明确“目录存在”和“版本已逻辑提交”不是天然同义。

裁定规则：

- C3 初始版本继续以完整 Item 原子提交为事实边界，因为创建 Event 已封存在 Item 内。
- C5 追加版本只有在版本目录完整有效且存在唯一精确匹配、已封存的 `capture.version-appended` Event 时才对读取侧可见；Event 绑定 N/N+1 和前后 Envelope 哈希，并作为逻辑提交点。
- 有效 `1..N` 前缀后至多一个无 Event 的 N+1 目录视为未完成事务证据：latest/list 使用 N 并发出 `incomplete_version_ignored`，显式 N+1 为 `version_not_found`；由 C6 恢复或隔离，C4 不自动删除或补写。
- Event 存在但版本无效属于完整性故障，读取 fail closed。

这一选择必须同步改写 Capture Envelope 的追加事务，而不是只写进 C4 文档。

### C. 通用版本解析

- 不把 `v000001` 永久硬编码为唯一版本。
- 只接受 `000001`–`999999` 六位 ASCII 目录，识别连续合法版本、缺口、重复 Item/Event、错误分片、reparse/越界和版本号溢出。
- 为 C4A 提供真实两版本 fixture；只实现读取侧 Event/schema，不提前实现 append writer。

### D. `get_capture` 完整性深度

- 在公开正文前重新计算全部 Payload 的实际字节数和 SHA256。
- 校验 Payload Set、Envelope 自哈希、ID/版本/路径一致性及匹配 Event。
- 历史版本返回所读版本；`current_version` 与 `item_state` 表示当前已提交状态，不混淆。
- 投影异常可以内存重建读取结果并返回 warning，但不得静默写盘修复。

### E. `list_captures` 完整性深度

列表不为每次打开收件箱而全量哈希所有 64 MiB payload。裁定：

- 校验 Item/版本/Event/Envelope 结构、规范字节、引用和声明大小与普通文件实际大小。
- 以有界读取生成前 160 个 Unicode code point preview。
- 完整 payload attestation 由 `get_capture` 承担。
- 任一不可变结构损坏时整页 fail closed、不返回部分 items/cursor；可重建投影异常先在内存重建状态再筛选，并形成带 `capture_id` 的 warning。
- 有界前缀之后的等长篡改可能由本操作略过，因此列表不返回完整 Payload `verified` 声明。

### F. 游标

固定使用 `c1.<base64url-no-padding canonical-json>.<sha256-checksum>` keyset cursor，payload 封装：

- Store 身份与末项排序键 `captured_at + capture_id`。
- 不包含 cursor/limit 的规范查询条件指纹。
- cursor schema 与 schema version。

checksum 使用固定领域前缀，只用于完整性而不是认证。格式损坏、版本不支持、Store 或查询条件不匹配统一返回稳定 `invalid_input`；不引入 TTL，合法 limit 可在后续页改变。

### G. 时间边界和快照

- 时间过滤统一为规范 UTC 毫秒。
- `created_after` / `created_before` 均严格排除，筛选版本 1 `captured_at`；after >= before 为 `invalid_input`。
- 分页只保证静态数据集无重复遗漏，不提供跨请求快照。并发创建、追加或路由变化后，要获得新鲜视图应从空 cursor 重启。

### H. warning 归属

列表级 warning 必须携带受影响的 `capture_id` 和稳定 warning code；未完成版本还携带整数 `version`，并按 capture/code/version 稳定排序。不可定位的全局 warning 只用于真正的 Store 级问题。preview 精确保留前 160 Unicode code point 和换行，可能在 grapheme cluster 内截断，不制造不存在的展示保真承诺。

C4-0 完成记录（2026-09-13）：上述 A–H 已同步进操作契约、Envelope、设计权威、实现矩阵和编码批次；C-027–C-031 均有明确裁决。仅修改项目文档，未实现公开读取、未改 schema 代码/fixture、未创建生产配置或 Store；文档护栏、普通与严格 `ResourceWarning` 全量 156 项测试、`compileall`、`pip check` 和 diff 检查均通过。本批由独立本地提交闭合，未执行 push。
