# KnowledgeFlow 渐进式知识提炼规范

> 状态：Draft（方法与实现假设；2026-09-21 修正）
>
> 本文是对“完整策展地图是否适用于所有规模内容”这一方向问题的设计收口。产品承诺、无静默缺口、证据和信任边界已经作为治理红线确认；三类 Profile 的默认适用范围、Source Ledger 物理契约、自动路由、检索栈和候选图谱实现仍为待实验的 Draft。本文件不授权实现 RAG、知识图谱、GBrain、UI 或任何可信知识写入。
>
> 捕获原件、版本、哈希、事务、权限和可信写入仍分别服从 [设计权威与冲突登记](design-authority-and-conflict-register-设计权威与冲突登记.md)、[Capture Envelope v1](capture-envelope-v1-捕获信封数据契约与原子保存事务.md) 和 [捕获与路由规范](capture-and-routing-spec-捕获与路由规范.md)。

## 1. 目的和结论

KnowledgeFlow 的目标不是承诺 LLM 对任意长文完成语义上的“零遗漏”。现实目标是把原料、处理状态、证据、候选知识和人工批准分开，使知识能够以可追溯、可重建、可逐步加深的方式形成。

### 1.1 已确认的方向红线

1. 原始 Capture 和版本是事实真源，任何语义处理都属于派生或提案。
2. 允许延迟、分层和按需提取，但不得通过缩小或省略处理范围来静默丢弃源文区段。
3. RAG、摘要、候选图谱和问答结果都不能自动成为可信知识。
4. 正式知识候选必须绑定精确来源版本和证据区段，并经过明确的提升批准。
5. “语义召回率”是需要通过样本和人工标注测量的质量目标，不是由条目数量或节级密度规则证明的硬保证。

这些红线的主题权威是[需求与治理基线](requirements-and-governance-baseline-需求与治理基线.md)和[设计权威与冲突登记](design-authority-and-conflict-register-设计权威与冲突登记.md)；它们不因本文其余部分保持 Draft 而失效。

### 1.2 待验证的方法假设

以下内容是当前最值得验证的方案，不是已冻结实现契约：

1. 使用 `full-map`、`hierarchical-map`、`retrieval-first` 三个工作名称描述处理策略；
2. 小型有界内容倾向 `full-map`，中型结构化内容倾向 `hierarchical-map`，大型、持续更新或问题尚不明确的内容倾向 `retrieval-first`；
3. 用 Source Segment 和 Source Ledger 表达处理边界，并以 Evidence Bundle 支撑查询和候选知识；
4. 通过真实材料实验确定分段、路由、检索、成本和审核机制，再冻结持久化格式和自动化行为。

## 2. 修正后的产品主张

### 2.1 可以作出的主张

KnowledgeFlow 可以承诺：

- 原料先保存，不能因为暂时无法分类或理解而丢失；
- 对进入处理范围的源文建立确定性区段和处理状态；
- 机器生成的摘要、实体、关系、主张、答案和图谱候选都能回到来源版本；
- 未处理、处理失败、延迟处理和待审核内容具有可见状态；
- 派生索引和候选结构可以从 Capture 真源重建；
- 只有精确批准的对象才能进入可信知识层。

### 2.2 不作出的主张

以下内容不能作为系统保证：

- LLM 已经提取了源文中的全部语义；
- 覆盖报告可以证明没有任何语义遗漏；
- 只看节级提取数量就能判断内容完整；
- 独立 LLM 调用天然消除了共同的模型盲区；
- 不熟悉领域的用户可以在固定几十秒内完成全部语义审核；
- 根据一次问答自动建立的图谱就是可信知识。

## 3. 核心术语

### 3.1 Source Segment

`Source Segment` 是某个 Capture 版本经过确定性规则切分得到的可追踪源文单元。它至少具有：

- `source_version`；
- 稳定的 `segment_id`；
- 可复现的顺序和范围；
- 内容摘要或等价的身份校验；
- 父级文档/章节关系（如果输入具有结构）。

Segment 是处理记账的最小单位，不等于实体、关系或主张，也不等于最终知识页面。

### 3.2 Source Ledger

`Source Ledger` 是源文区段的处理台账。它记录每个 Segment 当前处于何种处理状态，例如：

- `indexed`：已进入检索底座；
- `overviewed`：已生成粗粒度概要；
- `curated`：已进行指定范围的语义提取；
- `deferred`：有意延迟，等待问题、预算或人工触发；
- `out-of-scope`：本次运行明确排除，并记录选择边界和理由；
- `failed`：处理失败，保留失败原因并可重试；
- `reviewed`：对应提案已完成指定人工审核。

确定性 Segment 清单和由事件计算出的状态投影可以重建；人工审核、批准、拒绝或延期决定本身不能从 Capture 字节推导，必须保存在不可变审计事件或等价的规范记录中。Source Ledger 因而应被理解为“Capture/Segment 事实 + 处理事件 + 人工决策记录”的投影，而不是唯一保存人工决定的可覆盖状态表。

这里的字段和事件划分仍是方法论概念，不直接改变 Capture Envelope v1，也不预先冻结未来的物理文件格式。

### 3.3 Processing Profile

`Processing Profile` 是对某个 Capture 版本或某组 Segment 选择的派生处理策略：

| Profile | 目的 | 典型输出 |
|---|---|---|
| `full-map` | 对声明范围尝试高覆盖策展，并完整记录边界 | 策展地图、证据引用、未决/盲区和待审核条目 |
| `hierarchical-map` | 在可接受成本内提供多层理解 | 文档级概览、章节地图、异常/热点清单 |
| `retrieval-first` | 先建立可检索、可追溯的访问底座 | Segment 索引、查询证据包、局部提案 |

Profile 是可重算的派生决定，不是 Capture v1 `user_intent.processing_mode` 的替代品。

### 3.4 Evidence Bundle

`Evidence Bundle` 是一次查询、审核或提案所使用的来源证据集合。它至少绑定 Capture ID、版本、Segment ID 和可回读的原文范围。最终问答文本不能替代 Evidence Bundle。

### 3.5 Knowledge Candidate 和 Curated Knowledge

- `Knowledge Candidate`：由原文、Evidence Bundle 或受控派生产物生成，尚未获得可信身份的候选知识。
- `Curated Knowledge`：经过明确批准、精确绑定来源和变更对象，并按未来 SOP-002 规则写入的可信知识。

候选知识可以被重算、合并、废弃或重新审核；它不能覆盖 Capture 真源。

## 4. 不可破坏的处理原则

### K1：保存优先

Capture 成功只表示原料版本已可靠保存，不表示内容已经理解、路由、索引或入库。

### K2：不得静默丢弃

系统可以延迟、分层、按需或因预算暂不做深度提取，但不得靠不定义范围来隐藏遗漏。处理范围至少由目标 Capture 版本、声明的 Segment 集合或选择规则、选择理由和本次处理目的组成：

- 本次运行声明处理整个 Capture 版本时，该版本的每个确定性 Segment 都必须进入 Ledger；
- 本次运行只选择子集时，必须记录选择边界和理由，未选 Segment 也必须明确标为 `out-of-scope` 或 `deferred`；
- 没有状态且不能由声明边界解释的 Segment 属于处理缺口，而不是“已覆盖”。

### K3：证据优先于叙述

候选知识必须引用具体来源版本和区段。模型生成的摘要、答案或图谱描述不能脱离来源独立获得事实身份。

### K4：派生可重建

分段、embedding、关键词索引、摘要、候选标签、候选图谱和查询缓存都属于派生层，均不得成为唯一原件。

### K5：信任状态隔离

`trusted`、`unreviewed`、`proposal` 和 `candidate` 查询范围必须明确隔离。能被检索到不等于已经批准。

### K6：人审核决策，不审核所有噪声

人工重点审核提升、合并、冲突、低置信度、高影响和不可逆变更。简单重复候选可以留在未审核层，但不能被伪装成可信知识。

### K7：成本和摩擦是产品约束

处理路径必须同时记录计算成本、预估审核成本和用户等待成本。完整性目标不能通过把全部成本转嫁给人工审核来实现。

## 5. 三类处理路径

### 5.1 `full-map`

作为 Draft 假设，它适用于内容有界、价值较高、预计可在合理时间内审核的材料。可以生成传统策展地图，但报告必须说明：

- 覆盖报告是异常信号，不是语义完整性证明；
- 处理了哪些 Segment；
- 哪些 Segment 被延迟或标为盲区；
- 人工审核的实际范围和耗时。

### 5.2 `hierarchical-map`

作为 Draft 假设，它适用于中等规模、章节结构清晰或用户需要快速建立全局理解的材料。先生成：

- 文档身份和版本；
- 章节树和主题概览；
- 关键主张和不确定性摘要；
- 低覆盖、冲突和高风险区段；
- 可继续展开的热点。

只有用户选择某个章节、主题或候选时，才生成详细条目级地图。

### 5.3 `retrieval-first`

作为 Draft 假设，它适用于大型、持续更新、问题尚不明确或完整地图审核成本过高的材料。第一阶段至少完成：

1. 确定性分段；
2. Source Ledger；
3. 关键词/全文和可选向量索引；
4. 来源版本和 Segment 级引用；
5. 查询时的 Evidence Bundle。

它仍然可以在查询后生成局部策展地图或 Promotion Proposal，不意味着永远不做语义提取。

## 6. 路由决策

未来路由器可以综合以下因素提出 Profile 建议；具体算法、阈值和默认值尚未冻结：

- 文本规模和结构；
- 语义密度和内容类型；
- 风险和错误代价；
- 预计审核时间；
- 用户是否已有明确问题；
- 内容是否会持续更新；
- 预计复用频率；
- 可用模型、时间和 token 预算。

字数只能作为初筛信号，不作为唯一硬阈值。用户明确要求深度处理时，表示允许进入语义处理，但不自动等价于 `full-map`；系统仍应显示实际 Profile 和预计成本，必要时允许用户覆盖建议。

## 7. 检索、问答和候选图谱边界

### 7.1 RAG 的职责

RAG 用于从可允许的查询范围中定位相关来源、组织 Evidence Bundle 和辅助回答。它不能把未审核来源隐式提升为可信知识，也不能绕过 Capture 版本绑定。

### 7.2 动态候选图谱

查询可以触发实体、关系和主张候选，但候选应从检索到的原文证据中提取，而不是从最终回答文本直接复制。每个候选至少记录：

- 来源 Capture 和版本；
- Segment 或 Evidence Bundle；
- 提取器/提示词版本；
- 触发查询（如果有）；
- 置信度和支持证据数；
- 冲突证据；
- 当前状态：`candidate`、`corroborated`、`approved` 或 `superseded`。

### 7.3 查询偏置

只根据用户问过的问题建立图谱，会偏向用户已经想到的主题，无法保证全局覆盖。因此大型语料仍应有最低限度的全局结构索引或周期性抽样；查询驱动图谱只能被视为增量候选来源。

## 8. 覆盖和质量指标

不得使用一个“覆盖率”同时表示三种不同含义：

| 指标 | 定义 | 可否作为机械保证 |
|---|---|---|
| 处理记账覆盖 | 有明确状态的 Segment / 全部 Segment | 可以，目标是无静默缺口 |
| 证据绑定覆盖 | 有合法来源定位的候选 / 全部候选 | 可以，正式候选应为 100% |
| 语义召回率 | 人工 gold set 中被发现的目标知识 / 全部目标知识 | 不可以，只能实证估计 |

节级提取密度、全景概括对照和多 Pass 差异属于异常信号，不得单独用来声称语义完整。

## 9. 人工审核界面原则

审核界面应按“先总览、后热点、再决策”的顺序展示：

1. 文档状态、处理 Profile、成本和未处理区段；
2. 结构覆盖异常、冲突和低置信度区域；
3. 用户主动关注的章节或查询证据；
4. 需要批准、忽略、合并或请求更多来源的具体候选。

“覆盖报告约几十秒”只能表示异常筛查时间，不得表示完整语义审核时间。

## 10. 方法论验证要求

在把新流程作为正式 SOP 前，至少需要小规模、可复现的对照实验：

- 小、中、大三类材料；
- 低、高语义密度材料；
- 一次性材料和持续更新材料；
- `full-map`、`hierarchical-map`、`retrieval-first` 三条路径；
- 与直接 RAG 或直接 LLM 策展的基线比较。

记录：

- token/模型成本；
- 首次可用时间；
- 人工审核时间和放弃率；
- 引用正确率；
- 人工 gold set 估计的召回率和遗漏类型；
- 候选知识最终批准、修改、拒绝和冲突比例；
- 用户重复查询后知识是否得到有效沉淀。

单用户、少量样本只能发现明显失败模式，不能成为总体准确率证明。

## 11. 与当前 Capture MVP 的兼容边界

本方向收口不改变：

- Capture Envelope v1 的规范字节和字段；
- `capture-only`、`raw-source`、`deep-curation` 三个既有 `processing_mode` 值；
- C0–C6 已实现的写入、读取、追加、恢复、重建和迁移语义；
- C7 受限 CLI 的范围；
- C8 的 MVP-0 验收目标。

`deep-curation` 只表示用户允许进入较深语义处理；未来路由器根据本规范选择实际 Profile。任何新的持久化 ledger、candidate 或 graph schema 都必须在对应功能门禁单独冻结。

## 12. 后续门禁

1. 先完成 C7–C8，闭合本地 Capture MVP；
2. C8 通过后，可在用户明确授权下初始化生产 Capture Store，并用只暴露现有 Capture 能力的最小收件箱 dogfood；这不授权新增语义处理 schema；
3. 用隔离临时 Store 和获准的非敏感真实材料做规模/结构基线实验，只测量分段、处理成本和审核负担，不新增生产 schema；
4. 根据基线证据，通过独立设计批次冻结 Source Segment、Source Ledger 和三类 Profile 的最小契约；
5. 实现本地检索和 Evidence Bundle POC，并比较三条路径的引用正确率、审核成本和语义召回；不要求先接 GBrain；
6. 再决定候选图谱、GBrain、SOP-001/000B/002 和更完整 UI 的实现范围；
7. 任何正式知识写入仍需精确批准、事务和回滚协议。

## 13. 当前未决问题

- Segment 的默认切分粒度和跨版本稳定规则；
- 本地全文、BM25、向量和层次索引的最小组合；
- Profile 路由是纯规则、用户选择还是规则加建议；
- candidate graph 的合并、冲突和过期策略；
- 各风险类别的审核预算和 gold set 构造方法；
- 何时将方法论从 Draft 提升为 Approved Design。

以上未决问题不能通过修改 Capture v1 或直接创建生产 Store 解决，应在对应实验或功能门禁中单独裁定。
