## 结论

项目的产品方向没有发生根本性偏离，但工程投入已经来到一个必须转向的临界点：

> 前一阶段把“可靠捕获底座”做扎实是合理的；从现在开始，如果继续扩写内核、治理框架和远期架构，而不尽快形成最小可用界面和真实使用反馈，就会真正偏离产品目标。

当前最准确的判断是：

- 产品理论方向：基本正确。
- MVP-0 技术实现：完成度和可靠性较高。
- 用户可用产品：尚未形成。
- 产品核心价值：尚未被真实使用验证。
- P0 总体方向：正确，但现有草案需要一次小幅收口，暂不宜原样进入 P0B 编码。
- 生产 Store：现在仍不应创建。

本次仅做了只读检查，没有修改文件。

## 一、项目真正要解决什么

当前主 PRD 对项目的定位已经比较准确。KnowledgeFlow 不是单纯的笔记软件、文件归档器、RAG 聊天工具或自动 Wiki，而是一个本地优先、治理优先的个人知识工作系统。[主 PRD 的产品定位](../../requirements-and-governance-baseline-需求与治理基线.md#L68)可以概括成五层价值：

1. 用户不必先设计知识库、分类树或 Ontology，就能先保存想法和材料。
2. 保存后的内容能够被找到、浏览、搜索、问答和继续使用。
3. 系统承担阅读、比较、聚类、证据整理和变更准备等机械劳动。
4. AI 生成的摘要、回答、关系和图谱先停留在工作知识或候选层，不能冒充可信知识。
5. 只有值得长期稳定的内容，才经过精确批准、验证和回滚机制进入可信层。

因此完整产品应形成：

```text
来源事实 T0
→ 可立即使用的工作知识 T1
→ 可复核的候选与提案 T2
→ 选择性晋升的可信知识 T3
```

这条方向已经正确吸收了此前关于大型文本和 RAG 的讨论：

- 小型、有界内容可以尝试较完整的整理。
- 中型内容可以形成分层概览。
- 大型或持续增长的语料应优先检索、问答和动态建立候选结构。
- RAG、候选图谱和摘要是派生访问能力，不是真源，也不自动获得可信身份。

这些方法仍保持 Draft，而不是提前冻结成唯一架构，这是正确的。[三类候选处理方式](../../requirements-and-governance-baseline-需求与治理基线.md#L339)

## 二、当前项目真实状态

| 层面 | 当前状态 | 判断 |
|---|---|---|
| 顶层需求 | 主 PRD 已成为唯一 L0 需求入口 | 基本准确、结构合理 |
| 捕获内核 | C0–C8 已完成 | 限定范围为 `Implemented` |
| 验收证据 | 305 项测试、本地严格验收和 Windows CI 已通过 | 工程证据充分 |
| 生产实例 | 配置与 `〈候选生产 Store 路径〉` 均不存在 | 尚未进入真实数据使用 |
| 用户界面 | 不存在 | 普通用户目前无法形成完整产品体验 |
| 搜索/RAG/工作知识 | 未实现 | 符合阶段边界，但产品价值尚未验证 |
| 路由/KB/可信写入 | 未实现 | 现在不应提前做 |
| P0 | 已形成 Review Draft，但尚未提交 | 仍是工作区草案，不是正式基线 |

C8 对状态的表述很准确：当前只是“单机、单用户、Windows、本地文本捕获内核”达到 `Implemented`，不能推导成整个项目已经生产可用或 `Effective`。[C8 状态结论](../../mvp-0-capture-c8-acceptance-report-C8总验收报告.md#L165)

现有代码确实提供了较强的底座：

- Store 初始化和配置；
- `capture_text`；
- `get_capture`；
- `list_captures`；
- `append_capture_version`；
- 进程崩溃残留恢复；
- 派生状态重建；
- Store 迁移；
- 四操作受限机器 CLI。

但它仍然只是 T0 来源事实层，不是完整知识管理产品。

另一个值得正视的事实是：目前约有 13,015 行生产 Python 和 13,054 行测试，核心操作集中在近 4,000 行的 [operations.py](../../../src/knowledgeflow_capture/operations.py#L4173) 和约 2,300 行的 [store.py](../../../src/knowledgeflow_capture/store.py#L2527)。这不等于代码一定过度设计，但说明工程资源高度集中在“保存是否绝对可靠”，而“用户为什么愿意持续使用”仍没有证据。

## 三、目前没有走错的地方

以下方向应继续保持：

- 本地 Capture Store 是来源事实真源。
- 不要求捕获前分类或选择 KB。
- 现阶段不引入数据库是合理的：Capture Store 保存规范原件，未来检索数据库应只是可重建派生索引。
- 不承诺“语义零遗漏”是正确修正。
- RAG 和知识图谱没有被当成可信层，是正确的。
- `capture-only` 不授权模型自动摘要、关系发现或深度处理，是正确的权限边界。
- Windows 是首个验收平台，不代表产品永远只能运行在 Windows。
- GitHub Actions 只是开发门禁，不是产品运行依赖。
- 生产 Store 尚未创建不是遗漏，而是此前有意保持的安全门禁。

## 四、实际存在的偏移和缺口

### 1. 最大偏移：技术底座已经明显领先于产品验证

主 PRD 要证明的是“降低知识工作的总成本”，包括首次可用时间、人工审核负担、理解成本和持续维护成本。[产品成功假设](../../requirements-and-governance-baseline-需求与治理基线.md#L100)

当前真正被充分证明的只是字节、事务、幂等、锁和恢复。用户是否觉得好用、是否愿意持续使用、是否比普通文本文件或笔记软件更省力，仍完全未知。

因此从现在开始：

- 继续增加捕获内核抽象，是偏离。
- 继续大规模扩写治理文档，是偏离。
- 直接开始 RAG、图谱或 GBrain，也是偏离。
- 正确方向是尽快形成一个安全、很薄、可真实使用的垂直闭环。

### 2. P0B 有演变成第二个 C0–C8 的风险

[P0A 当前顺序](../../p0-production-dogfood-plan-P0生产初始化与最小收件箱试用方案.md#L20)总体合理：

```text
管理与备份能力
→ 临时 Store 界面
→ 生产初始化
→ 真实 dogfood
```

但现有 P0B 同时要求完整校验、备份格式、兼容续传、中断、空间不足、目标冲突、恢复报告和安装态管理入口。[P0B 范围](../../p0-production-dogfood-plan-P0生产初始化与最小收件箱试用方案.md#L248)

这些能力有安全价值，但必须限定为“首次 dogfood 所需的最小冷备份闭环”，不能扩展成：

- 通用备份平台；
- 自动调度器；
- 增量备份系统；
- 版本保留策略；
- 备份管理 UI；
- 跨平台运维框架。

第一阶段只需要最小的 `init / verify / backup / restore-to-new-target` 能力，并在临时 Store 上证明恢复可用。

### 3. P0A 的授权问题分层不够准确

[P0A 复核清单](../../p0-production-dogfood-plan-P0生产初始化与最小收件箱试用方案.md#L341)要求在 P0A 批准前确认精确备份位置，但同一文档又说这些问题未确认时仍可继续临时 Store 实验。

更合理的分层应是：

- P0A 现在确认：批次顺序、范围边界、最小管理能力、允许界面技术比较。
- P0B/P0C 可以只使用临时路径实施。
- P0D 前才必须确认：精确配置路径、Store 路径、备份物理位置、目录创建和真实内容隐私等级。

也就是说，精确生产路径不应阻塞 P0A 设计批准，但必须严格阻塞 P0D。

### 4. 真实私人数据的隐私与删除边界还不够明确

主 PRD 明确要求，真实私人内容进入前必须有初始化、备份、恢复和日志隐私方案。[生产前约束](../../requirements-and-governance-baseline-需求与治理基线.md#L402)

目前 P0 草案虽然规定日志不得泄漏正文，也承认没有加密容器和删除功能，但仍缺少几个用户必须提前知道的事实：

- 数据静态保护究竟依赖 Windows 用户权限、NTFS ACL 还是 BitLocker；
- 备份盘是否加密；
- 哪类敏感内容不适合进入当前 dogfood；
- 当前 Capture 是追加式保存，产品内没有删除或彻底擦除流程；
- 停止 dogfood 后如何导出、保留或最终清除数据。

“删除/保留/退出”不应长期只被视为外部扩展，它是本地个人数据所有权的一部分。P0 可以暂不实现删除，但必须在第一次真实捕获前明确提示。

### 5. “待处理”状态存在歧义

[FR-INBOX-001](../../requirements-and-governance-baseline-需求与治理基线.md#L323)要求看到“未分配和待处理项”，而 Capture v1 实际只有：

- `routing_status = unassigned`
- `trust_status = unreviewed-capture`

[P0 界面表](../../p0-production-dogfood-plan-P0生产初始化与最小收件箱试用方案.md#L197)列出了这两个状态，但没有明确“待处理”究竟指什么。

P0 应明确：

> “待处理”只是界面对 `unassigned` / `unreviewed-capture` 的用户可见分组，不新增 `processing_status`，也不能把内部 `outbox/pending` 当成用户处理状态。

否则 UI 很容易在没有获批 schema 的情况下发明第二套状态机。

### 6. UI 端的幂等性还没有真正闭合

内核幂等已经很强，但如果界面在提交后、收到结果前崩溃，界面可能丢失原来的幂等键。重新启动后用新 key 重发，就可能产生重复 Capture。

P0A 已识别这个问题，但没有做出选择。[客户端崩溃边界](../../p0-production-dogfood-plan-P0生产初始化与最小收件箱试用方案.md#L208)

P0C 编码前必须二选一：

- 实现最小的持久请求身份/草稿机制；或
- 明确不支持跨重启自动重试，重启后提示“结果可能未知，请先刷新检查”，绝不自动换 key 重发。

第一版可以选择第二种，但不能保持含糊。

### 7. 文档仍有 C8 后漂移

当前文档地图已经规定 C8 后重新评估并归档完成阶段材料。[文档维护规则](../../README.md#L84)

但目前仍有多份现行文档写着“下一门禁是 C8”，例如：

- [捕获与路由规范](../../capture-and-routing-spec-捕获与路由规范.md#L748)
- [渐进式知识提炼规范](../../progressive-knowledge-refinement-spec-渐进式知识提炼规范.md#L276)
- [Capture Envelope v1](../../capture-envelope-v1-捕获信封数据契约与原子保存事务.md#L1089)
- [四操作契约](../../mvp-0-capture-operations-本地文本捕获操作契约.md#L755)

这不会破坏代码，但对治理优先项目而言属于真实漂移。

此外，当前 P0A 方案仍是未跟踪文件，相关 README、登记和文档检查修改也尚未提交。因此正式 Git 基线仍是 `89da13f`，P0A 尚未成为版本化项目事实。

## 五、建议的后续完整顺序

### 第一步：P0A.1 小型方案修正与事实收口

这是现在最应该做的，不应直接进入 P0B 编码。

只修改现有 P0A 方案及少量状态文档：

1. 明确 P0 只验证“低摩擦本地文本捕获与收件箱”这一条首要旅程。
2. 把 P0A 决策和 P0D 精确路径授权分开。
3. 把 P0B 限定为最小冷备份闭环，禁止扩展成备份平台。
4. 明确“待处理”只是 UI 分组，不新增持久状态。
5. 冻结最小隐私声明、无删除限制和首次捕获提示。
6. 决定跨重启幂等/未知结果处理策略。
7. 将“必须调用 CLI”放宽为“必须经过现有四操作公共边界，绝不能直接写 Store”；具体使用进程 CLI 还是进程内公共 API 由 P0C 小型技术比较决定。
8. 修正仍写着“下一步 C8”的现行文档；C3 执行材料归档另做小型 D2，不与功能代码混在一起。
9. 将当前 P0A 草案和导航修改作为一个独立提交版本化。

这是纯文档批次，只需要：

- `git diff --check`
- `scripts/doc-check.py`
- 文档/维护脚本相关测试

不需要因为这次文档修正再次跑 305 项捕获测试。

### 第二步：P0B-min 最小生产管理闭环

只在临时 Store 实施：

- 幂等初始化；
- 只读完整校验；
- 受控窗口的一致性冷备份；
- 恢复到新的空目标；
- 恢复后运行 capture/list/get/append；
- 证明源 Store 和生产候选路径没有被修改；
- 日志不泄漏正文、完整路径或幂等键。

不创建真实生产 Store。

### 第三步：P0C 最小收件箱

仍然只使用临时 Store，实现：

- 捕获；
- 列表；
- 完整读取；
- 追加版本；
- 空状态和配置缺失提示；
- 错误、warning、版本冲突和未知提交状态展示；
- 最小请求身份与崩溃处理；
- 完全离线运行。

不做搜索、标签、摘要、RAG、路由或知识库。

### 第四步：P0D 精确生产初始化

只有 P0B/P0C 通过后，再由用户明确确认：

- 配置路径；
- Store 路径；
- 备份路径及是否为独立物理介质；
- 静态数据保护方式；
- 是否接受当前没有产品级删除；
- 是否允许创建相关目录。

然后才创建真实 Store，由用户主动输入第一份内容，并立即完成首份备份与恢复验证。

### 第五步：P0V 真实 dogfood

重点不是再测事务，而是验证：

- 捕获和找回是否比普通文件更方便；
- 状态、版本、warning 是否能被普通用户理解；
- 是否发生草稿丢失、重复捕获或操作困惑；
- 备份和恢复是否真的可执行；
- 用户是否愿意持续使用。

P0V 通过也只能把“本机 Capture Store + 最小收件箱”升级为窄范围 `Effective`，不能代表整个 KnowledgeFlow 有效。

## 六、P0 之后的方向

P0 完成后不建议立刻进入 GBrain、知识图谱或可信 Wiki。更合理的顺序是：

```text
代表性用户旅程与材料基线
→ Task / Workspace 最小契约
→ 本地检索与 Evidence Bundle POC
→ 比较小/中/大型材料的处理策略
→ 再决定人工路由、SOP-000A、候选图谱和可信写入
```

尤其大型语料应优先验证 retrieval-first，而不是先建设完整策展地图。

最终判断是：项目没有走错方向，但已经不能再把“基础设施更完整”当成主要进展。下一步应是一次严格限界的 P0A.1 修正，然后尽快转入最小用户闭环，而不是继续扩写底座或远期架构。
