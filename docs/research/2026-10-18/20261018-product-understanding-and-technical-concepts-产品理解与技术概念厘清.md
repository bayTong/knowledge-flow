## 1. 总结论

1. KnowledgeFlow 的核心不是自动生成 Wiki 或建立知识图谱，而是让来源先可靠纳入，再形成可用但不冒充可信的工作知识，最后把值得长期稳定的部分选择性晋升为可信知识。
2. KnowledgeFlow 相对 raw / wiki / schema 文件式模式的关键增量，是在原料与可信写入之间增加一个可回证、可审核、可修改、可中止的持续治理层。
3. 策展地图是这个治理层的典型工件：它是一次材料处理的“带证据审查包”，不是知识图谱、Ontology 或已经执行的可信 Wiki。
4. 策展地图、Wiki、KB Schema、Ontology 和知识图谱首先是职责不同的工件类型；候选、已决定、已批准和已执行是另一条治理状态轴。两者不能合并为单一的“高级度”。
5. 领域 Ontology 是有边界、可版本化的语义工程协议，不是哲学上对“什么真正存在”的形而上学回答。
6. Ontology 和知识图谱在当前产品路径中通常后置，但不是只能在“建库完成”后出现。它们应在稳定语义复用、关系查询、一致性校验或系统互操作出现真实价值时按需引入。
7. 用户对领域越来越熟悉，可能促进更稳定的词表、Taxonomy、Ontology 或图谱，但用户熟悉程度不是唯一决定因素。材料规模、重复使用、关系查询、风险、互操作和维护收益同样重要。
8. 当前项目仍应先用 CUR-MVP-1 证明策展地图能帮助用户理解并回到证据，再用 CUR-MVP-2 证明最小 KB Schema 和可信 Wiki 的获批写入；当前不建设 Ontology 引擎、通用知识图谱或 RAG 平台。

## 2. 产品的核心理解

### 2.1 KnowledgeFlow 解决什么

个人知识工作经常在两个失败方向之间摇摆：

    先完整理解、分类和建模再保存
    → 前置成本过高，材料和想法在整理前流失

    让模型自动提取并直接写入知识库
    → 来源、范围和语义决定不透明，难以信任、维护和回滚

KnowledgeFlow 不要求用户在起点就完成全部理解和建模，也不允许模型在没有证据和批准的情况下直接改写可信知识。它建立的是一条可以随时停止、以后再继续的渐进链路：

    用户任务或材料
      → 来源可靠纳入
      → 可搜索、可浏览、可问答、可审查的工作知识
      → 有证据的策展地图与变更候选
      → 用户对精确对象作决定
      → 受限执行器确定性写入
      → 可信、可维护、可回滚的知识

### 2.2 治理层是持续机制

策展地图、候选、决定记录、精确变更方案和批准不仅服务首次建库。知识库已经存在时，新材料、冲突、过时内容和结构漂移仍然需要同类治理：

    已有 T3 可信知识 + 新 T0 来源
      → 对齐、去重、冲突和缺口分析
      → 新策展地图或维护提案
      → 用户决定
      → 精确更新和新检查点

因此，治理层贯穿知识库生命周期，不是建库完成后即可丢弃的临时脚手架。

## 3. 两条必须分开的轴

### 3.1 工件类型轴

| 工件 | 主要回答的问题 | 典型范围 |
|---|---|---|
| Capture / raw | 用户当时提交了什么 | 一份来源的精确版本 |
| 摘要、问答、提纲 | 当前如何快速使用来源 | 一次任务或一组来源 |
| 策展地图 | 材料讲了什么、证据在哪里、有什么缺口和组织候选 | 一次材料处理任务 |
| Wiki 页面 | 如何向人稳定解释某个主题 | 一个知识库的长期叙事知识 |
| KB Schema | 页面、元数据、链接和组织怎样表示才合法 | 一个知识库的表示政策 |
| Ontology | 稳定概念、关系和约束分别意味着什么 | 跨材料复用的领域语义 |
| 知识图谱 | 具体有哪些对象、事实和关系 | 跨来源的具体实例关系 |
| SOP | 谁在什么条件下执行什么，何时暂停、批准和恢复 | 一条可执行流程 |

地图可以包含概念、关系、页面和结构候选，但“包含某类候选”不等于“地图已经变成该类最终工件”。

### 3.2 治理状态轴

| 状态 | 含义 |
|---|---|
| 派生或工作态 | 可用、可重算或可编辑，但不声称获得可信身份 |
| 候选或提案态 | 已绑定来源、范围和影响，等待接受、修改、拒绝或延期 |
| 已决定 | 用户对精确候选表达了选择，但尚未必然形成可执行变更 |
| 已批准 | 用户批准了绑定最终字节、目标前置状态和差异的变更方案 |
| 已执行或可信态 | 受限执行器已精确应用、回读验证并形成审计检查点 |

同一工件类型可以经历不同治理状态。例如，Ontology 可以先是修改提案，执行后再成为稳定语义规则；图谱关系可以先是模型推断，也可以后来成为获批可信关系。

策展地图在当前设计中仍是 T2 审查容器。map_closed 表示地图已保存并可作为任务终点，不表示地图中的所有内容整体升级为 T3。被用户选中的部分必须转换为独立精确变更对象，再经批准和 Apply 形成 T3。

### 3.3 “可信”也要拆开

对一份工件的信任至少包含三件不同的事：

1. 完整性可验证：字节、版本、哈希和身份可以证明。
2. 流程决定可证明：能证明用户对哪个版本作了什么决定。
3. 获得可信知识身份：内容已被精确批准、执行和验证，可作为长期知识库基线。

一份策展地图可以在前两个意义上非常可靠，但仍不自动满足第三个意义。

## 4. 概念的准确边界

### 4.1 哲学本体论与领域 Ontology

哲学本体论研究存在本身：什么真正存在，对象、属性、关系、事件、时间、同一性和因果具有什么根本性质。它试图提出一般性的形而上学回答。

信息科学中的领域 Ontology 借用了这个名称，但是有限领域内的工程产物。它定义：

- 使用哪些概念类型；
- 允许哪些关系类型；
- 名称、类型和关系分别表示什么；
- 需要遵守哪些一致性约束。

领域 Ontology 可以版本化、迁移、替换或废弃；目标是让人和系统在具体领域中统一表达、查询和校验，不是提供对存在本身的终极回答。

### 4.2 Schema 的三种含义

| 含义 | 作用 | 示例 |
|---|---|---|
| 机器数据 Schema | 校验结构化文件的字段、类型和长度是否合法 | map.yaml、kb.yaml 的字段规则 |
| KB SCHEMA.md | 规定知识库的页面、元数据、链接、导航和组织方式 | 概念页需要哪些字段、来源怎样引用 |
| 语义 Schema / Ontology | 定义领域概念、关系和约束的意义 | “方法解决问题”关系的起点、终点和语义 |

三者可以有关联，但不是同一对象。最小 KB SCHEMA.md 可以只规定 Markdown 页面和来源引用，完全不包含正式 Ontology。

### 4.3 策展地图

策展地图是一次材料处理的有边界审查工件，主要表达：

- 材料讲了什么以及结构如何；
- 作者或说话者的主张；
- 概念、关系、争议、修正和限制；
- 对应精确来源版本的 Evidence locator；
- 已处理、延期、失败和排除范围；
- 可能的页面、导航、Schema、Ontology 或图谱候选；
- 用户可以接受、修改、拒绝、延期或只保存地图的对象。

策展地图不强制所有材料最终入库，也不承诺语义零遗漏。

### 4.4 Ontology

Ontology 定义跨内容稳定复用的概念、关系和约束。它不保存全部具体事实，也不要求一定有图形界面。只有当这些类型和关系需要跨许多材料重复使用、查询或校验时，正式 Ontology 才通常值得维护。

### 4.5 知识图谱

知识图谱保存具体节点和关系，例如：

    [RAG] --包含--> [检索阶段]
    [RAG] --包含--> [生成阶段]
    [检索阶段] --可使用--> [向量数据库]

图谱可以使用正式 Ontology，也可以先使用轻量节点类型和关系规则。“图谱表达形式”与“候选或可信状态”必须分开。

### 4.6 RAG

RAG 解决的是从允许查询的范围中找到相关证据并辅助回答当前问题。它可以生成 Evidence Bundle 和局部候选，但不决定哪些内容获得可信身份。

## 5. 从策展地图到可信知识

### 5.1 现行流程

    精确 Capture 版本（T0）
            │
            ├─ 目标未确定：在无目标工作根生成地图
            │
            └─ 目标已确定：创建 provisional KB，验证 raw/ 映射
                              此时没有正式 SCHEMA.md 或可信 Wiki
            │
            ▼
    SOP-20：范围、证据、概览、主张、关系、缺口和组织候选
            │
            ├─ 保存地图并结束：地图仍为 T2
            │
            └─ 用户选择继续
                    ▼
    决定记录：接受、修改、拒绝或延期精确候选
                    ▼
    SOP-30 Prepare：转换为最终页面、最小 KB Schema 和精确变更集
                    ▼
    用户批准完整变更对象
                    ▼
    SOP-30 Apply：无模型、不扩范围地确定性写入
                    ▼
    T3 可信 Wiki、稳定结构或可选可信关系

一条地图候选关系被接受后，可以最终表现为：

- Wiki 页面中的叙述；
- 两个 Markdown 页面之间的普通链接；
- 结构化元数据；
- 类型化知识图谱边；
- 延期保留，不进入可信层。

选择哪种形式取决于用户任务、目标知识库政策和真实使用需求，不由模型仅因为“发现了关系”而自动决定。

### 5.2 地图是可重复使用的变更入口

地图不只用于从零建库，也应在已有知识库维护中承接：

- 新内容与旧页面的差异；
- 同一主张的新证据或反证；
- 重复、冲突、过时和缺口；
- 页面合并、拆分、重命名和导航调整；
- 词表、Taxonomy、Ontology 或图谱规则的变化候选。

当前首个纵向切片只证明新库与单一材料，但长期产品模型不应把地图限定为“初始化时使用一次”。

## 6. 策展地图怎样写

### 6.1 地图内容的决定依据

| 依据 | 决定什么 | 不能被什么替代 |
|---|---|---|
| 精确来源版本 | 地图有证据可以陈述什么 | 模型常识或外部印象 |
| 用户当前任务 | 地图为何生成、重点回答什么 | 历史习惯或默认推断 |
| 处理授权与声明范围 | 允许处理和延期哪些内容 | “文件已保存”这个事实 |
| 材料类型和结构 | 使用论证结构、时间线、主题层级还是其他呈现 | 统一固定十节模板 |
| Processing Profile | 采用较高覆盖、分层概览还是局部处理 | 单一字数阈值 |
| 目标 KB 上下文 | 可提出哪些页面、导航或结构建议 | 不得反向改写来源原意 |
| SOP 最低契约 | 哪些范围、证据、不确定性和决定对象不能省略 | 处理器文风偏好 |

模型可以决定如何在这些边界内生成良好结果，但不是目标、范围、来源事实或可信身份的权威。

### 6.2 最小人类可读结构

map.md 不必固定为十节，但应让用户依次看到：

1. 来源、任务与处理范围；
2. 一页整体概览；
3. 章节或主题结构；
4. 主张、概念和关系候选；
5. 争议、修正、限制和外部核实点；
6. 页面、导航和结构候选；
7. 未处理、延期、失败和能力缺口；
8. 可接受、修改、拒绝、延期或只保存地图的对象。

map.yaml 保存同一事实的机器表示，至少绑定运行、来源、范围账、处理器与成本、稳定候选 ID、Evidence locator、来源明示或系统推断属性、不确定性和人类呈现锚点。map.md 不能包含 map.yaml 中不存在的“额外已确认结论”。

### 6.3 候选对象应表达什么

每个候选至少应能回答：

- 稳定 ID 和候选类型是什么；
- 候选陈述是什么；
- 是来源明确表达、引用他人，还是系统推断；
- 支持它的精确来源位置在哪里；
- 不确定性和冲突是什么；
- 建议作为 Wiki 叙述、普通链接、结构化关系还是延期；
- 当前决定是待定、接受、修改、拒绝还是延期。

这只是逻辑要求，不在本文件中冻结最终机器字段。

### 6.4 不可破坏的地图原则

1. 概览不能代替处理范围和缺口记录。
2. 具体主张、争议和关系必须能打开精确原文。
3. 必须区分来源明确表达、引用他人主张、可核实事实和系统推断。
4. 未处理、失败、冲突、不确定性和能力限制必须可见。
5. 组织、Schema 和 Ontology 建议必须与来源事实隔离。
6. 地图修改形成新版本，不静默覆盖旧版。
7. 用户决定作为独立不可变记录绑定地图版本。

## 7. Karpathy raw / wiki / schema 与知识图谱

### 7.1 Karpathy 三部分描述的是文件职责

Karpathy 的 [LLM Wiki 原始说明](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)把模式概括为：

- raw：不由 LLM 改写的来源材料；
- wiki：LLM 持续维护的 Markdown 摘要、实体页、概念页、比较和综合；
- schema：告诉 Agent 知识库怎样组织、采用什么约定，以及 ingest、query、lint 怎样工作的配置文档。

这个 schema 比 KnowledgeFlow 中的 KB SCHEMA.md 更宽，同时混合了页面表示规则、内容组织约定和 Agent 工作流。KnowledgeFlow 为了精确授权和审计，将其拆成：

- KB SCHEMA.md：内容表示和组织规则；
- SOP：流程、权限、暂停、验证和恢复；
- 可选 Ontology：领域语义、关系和约束；
- 机器校验规则：文件字段、路径、哈希和引用完整性。

### 7.2 链接图不自动等于知识图谱

Markdown Wiki 的页面和双向链接从数学结构上可以构成图，Obsidian Graph View 也可以展示这种链接图。但产品意义上的知识图谱通常还要求：

- 稳定对象身份；
- 节点和关系类型；
- 关系方向和语义；
- 来源、证据和版本；
- 候选与可信状态；
- 可查询、可校验的结构。

因此，“可以画成图”不等于“已经实现知识图谱”。一个 Wiki 可以长期只使用人类可读页面和普通链接，也可以在真实需求出现后增加轻量关系或正式图谱。

### 7.3 KnowledgeFlow 的增量

    Karpathy 抽象模式：
    raw ─────────────────→ wiki
           schema 指导 Agent

    KnowledgeFlow：
    Capture / raw
      → 受权处理与工作知识
      → 策展地图与候选
      → 用户决定
      → 精确变更方案
      → 批准
      → 确定性 Apply
      → 可信 Wiki / 可选可信图谱

    KB Schema、SOP 与可选 Ontology
    共同约束表达和过渡，但彼此职责分开。

## 8. 知识库的渐进成熟

### 8.1 常见但不强制的演化路径

| 阶段 | 主要目标 | 典型工件 |
|---|---|---|
| 1. 可靠接住 | 原料不丢，身份和版本可证明 | Capture、原始来源 |
| 2. 初步理解 | 看懂材料、找到证据和缺口 | 概览、提纲、策展地图 |
| 3. 可信形成 | 把获批内容稳定写入 | 最小 KB Schema、Wiki、批准与检查点 |
| 4. 持续治理 | 处理新增、冲突、过时、重组和回滚 | 新地图、维护提案、版本历史 |
| 5. 语义形式化 | 稳定重复概念、关系和约束 | 受控词表、Taxonomy、Ontology |
| 6. 关系化运用 | 浏览、查询和分析大量具体对象关系 | 候选或可信知识图谱 |

这不是必经阶梯：

- 知识库可以长期停在结构良好的 Wiki 和持续治理阶段；
- 成熟的医学、法律或企业数据模型可以从已有 Ontology 起步；
- 大量实体关系查询可能比完整叙事 Wiki 更早需要图谱；
- 专家也可能只需要简单页面和链接；
- 新手也可能使用外部已经成熟的词表或 Ontology。

Ontology 和知识图谱表示的是语义形式化和关系化能力，不是所有知识库必须达到的“高级毕业形态”。

### 8.2 何时引入 Ontology 或图谱

下列信号实际影响检索、理解、推理或维护时，才值得形成稳定提案：

- 同义词、别名和重复命名持续产生成本；
- 概念和关系在不同页面中经常被解释得不一致；
- 用户需要稳定的关系查询、路径或影响分析；
- 需要与外部语义模型或业务系统交换数据；
- 一致性约束可以发现普通 Wiki 难以发现的错误；
- 增加结构的收益大于审核和长期维护成本。

## 9. 对当前 MVP 的直接含义

### 9.1 CUR-MVP-1

首个用户可见里程碑应证明：

- 精确本地材料能形成可证明的 Capture 版本；
- 用户可确认目标或暂不选库；
- 选择新库时可创建一个隔离 provisional KB 并验证 raw/ 映射；
- 可以看见处理范围、缺口和地图；
- 重要主张、概念和关系能够打开精确原文；
- 用户可修改、拒绝、延期或只保存地图并结束。

本里程碑不建设 Ontology 引擎、通用图谱、RAG 平台或通用 Schema 编辑器。

### 9.2 CUR-MVP-2

CUR-MVP-1 通过后，再证明：

- 选定地图候选可以转换成最终页面字节、最小 KB Schema 和精确变更集；
- 用户批准的是精确变更对象；
- Apply 不调用模型、不重新生成、不扩大范围；
- 新库首次激活、首批 Wiki、验证、版本检查点和恢复可以闭环。

首个切片中的最小 KB Schema 只需覆盖首批获批内容，不应从一份材料推断永久完整的领域 Ontology。

## 10. 现行文档评估

### 10.1 主 PRD

判断：不应整体重写，只需小幅概念精确化。

[主 PRD](../../requirements-and-governance-baseline-需求与治理基线.md)已经正确表达结构非前置、工作知识先于可信写入、地图不是可信知识、Ontology 和图谱并非必经阶梯，以及可信变化必须精确批准。后续只建议：

1. 在四层信任模型后明确：T0–T3 是治理状态和事实类别，不是工件形式分类；Wiki、Ontology 和图谱不因名称自动获得 T3 身份。
2. 明确地图不只用于初始建库，也用于已有 KB 的新来源对齐和高影响变更。
3. 明确用户熟悉度只是引入 Ontology 或图谱的一个信号，还要考虑语义复用、关系查询、互操作、风险和维护收益。

这些是消除误读，不是改变顶层需求。

### 10.2 概念架构导读

判断：需要局部结构性重写，但不需要推倒全文。

[概念架构导读](../../knowledgeflow-conceptual-architecture-KnowledgeFlow概念架构导读.md)的总体方向正确，但存在三个解释缺口：

1. 没有明说“工件类型”和“治理状态”是两条轴，容易让人误以为地图提高可信度后就变成图谱或 Ontology。
2. Schema 只有一行定义，没有区分机器数据 Schema、KB SCHEMA.md 和领域 Ontology。
3. 没有说明 Karpathy schema 同时包含结构约定和工作流，而 KnowledgeFlow 已将它拆成 KB Schema、SOP、机器校验和可选 Ontology。

建议重写概念图和核心概念边界附近的解释结构，增加两轴模型、三种 Schema、领域 Ontology 限界、Karpathy 映射和持续治理说明；保留现有场景、自动化边界和常见误解部分。

### 10.3 渐进式知识提炼规范

判断：需要小幅定位和顺序修正。

[渐进式知识提炼规范](../../progressive-knowledge-refinement-spec-渐进式知识提炼规范.md)回答的是“面对不同规模和任务的材料，处理多深、怎样记账、如何不静默遗漏”，不是“领域概念怎样定义”。建议：

1. 不重命名文件，但在页首更显著地说明它是方法草案。
2. 把“三条线共享底座”改成“共享来源版本、范围、证据定位和回读不变量；能力在各纵向切片中按需实现”，避免诱导先建通用平台。
3. 把后续门禁第 5–6 项明确合并为一个 CUR-MVP-1 产品里程碑；机械能力可拆小提交，但地图出现后里程碑才完成。
4. 增加一句：Segment、Ledger、Profile 和 Evidence 描述处理方法与范围账；地图、Wiki、Ontology 和图谱描述语义工件或表达形式。

### 10.4 SOP-20

判断：契约基本正确，只需两条防误读说明。

[策展地图 SOP](../../curation/20-sop-deep-curation-map-材料深度理解与策展地图.md)已经正确规定范围账、Evidence locator、地图最小内容、双表示、不可变版本和地图终点。只建议增加：

1. 地图中的概念和关系是候选陈述，不因有节点或边形式就成为知识图谱。
2. map_closed 是合法任务终点，但地图仍是 T2；未来若需要 T3 发布型策展报告，应另行定义工件类型和提升流程。

### 10.5 SOP-30

判断：不需要重写，需要限定首版 SCHEMA.md 的意义。

[批准后写入 SOP](../../curation/30-sop-trusted-write-批准后写入可信知识.md)已经正确分开 Prepare 与 Apply。建议明确：

- 首个新库的最小 SCHEMA.md 首先是页面与来源表示政策，不等于完整领域 Ontology；
- 首个 CUR-MVP-2 不顺手引入 Ontology 语言、通用关系注册表或图数据库；
- 将来若地图提出 Ontology 或图谱变化，仍须作为高影响结构候选精确批准。

### 10.6 SOP-10

判断：本轮不需要修改。

[新建知识库骨架 SOP](../../curation/10-sop-new-kb-bootstrap-新建知识库骨架.md)已经明确 provisional KB 不填造领域、SCHEMA.md 或可信知识，正确支持无结构冷启动。

### 10.7 动态状态与权威记录

判断：需要另行事实同步。

当前已存在提交 37a03e6，但[项目状态](../../project-status-项目状态与当前门禁.md)、[设计权威](../../design-authority-and-conflict-register-设计权威与冲突登记.md)和[实验协议](../../evidence-first-experiment-protocol-Evidence优先实验协议.md)仍有“联合候选待版本化”的时点表述。

应修正为“联合 Review Candidate 已版本化，尚未实现；CUR-MVP-1 仍需单独实施授权”。有 Git 提交不等于 SOP 已经 Implemented。

## 11. 建议的文档修订批次

本文只形成分析和修订边界，不直接修改权威文档。项目所有者确认后，建议只执行一个小型“概念与状态一致性修订”：

1. 同步项目状态、设计权威状态栏和实验协议中的版本化事实。
2. 局部重写概念导读，加入两轴模型、三种 Schema、Ontology 限界、Karpathy 映射和持续治理说明。
3. 对主 PRD 只作三项防误读补充，不改变需求 ID 或产品方向。
4. 修正渐进式规范的“共享底座”和机械/地图分段排程。
5. 为 SOP-20 补地图与图谱的区别，为 SOP-30 补最小 KB Schema 不等于 Ontology；SOP-10 不改。
6. 只运行文档链接、索引、状态和一致性护栏，不为纯文档解释修改重跑全部产品测试。

该批次不创建新的顶层权威文档，也不把本研究稿提升为第二份 PRD。

## 12. 修订后的实施顺序

完成上述小型文档同步后，不再延伸概念设计，直接进入 CUR-MVP-1：

1. 精确 Capture 版本、确定性分段、范围账、locator 和原文回读；
2. 目标已知或未知的建议与人工确认，以及一个隔离 provisional KB 的 raw/ 映射；
3. 在独立核查与处理器、预算确认后，生成可查看、可回证、可修改的策展地图；
4. 验收用户能否看懂范围与缺口、打开证据、修改结果并在地图处结束；
5. 通过后再单独进入 CUR-MVP-2 的最小 Schema、精确批准和可信 Wiki 写入。

当前不因概念讨论提前实现 Ontology、知识图谱、RAG、通用 Ledger 或 Task 平台、多 KB 或完整图形工作台。
