Q:什么是建立 knowledgeflow_curation 的最小契约、错误语义、golden fixtures 和独立测试计数

A:它们是 `CUR1A` 要完成的四件“小而必要的准备工作”。目的不是再建设一套大底座，而是先规定后续代码彼此怎样交接、失败时怎样说清楚，以及怎样防止格式被随意改坏。

## 1. `knowledgeflow_curation` 是什么

这是准备新增的 Python 功能包，专门承载“深入策展”能力。

当前已有：

```text
knowledgeflow_capture
```

它负责：

- 保存 Capture；
- 读取 Capture；
- 追加版本；
- 列出 Capture；
- 管理 Capture Store。

以后新增：

```text
knowledgeflow_curation
```

它负责：

- 把某个精确 Capture 版本作为策展来源；
- 分段并记录处理范围；
- 建立 Evidence locator；
- 创建隔离知识库和归档 `raw/`；
- 生成、保存、修改策展地图；
- 在地图处结束任务。

可以把二者理解为：

```text
knowledgeflow_capture  = 可靠地把原料收进来
knowledgeflow_curation = 对已保存原料进行理解和策展
```

分开不是为了“微服务化”或增加复杂架构，而是为了避免策展实验破坏已经稳定的 Capture 内核。它们仍然在同一个本地项目、同一个 Python 安装环境里运行，不需要启动服务器或数据库。

## 2. “最小契约”是什么

契约就是各步骤之间必须使用的输入、输出和规则。

例如，策展系统不能只收到一句：

> 帮我处理这篇文章。

它至少需要知道：

```text
处理哪个 Capture？
使用哪个版本？
Payload 哈希是什么？
允许处理哪些范围？
用户是否授权深度处理？
是否已经确认目标知识库？
```

Evidence locator 也不能只写：

> 证据在文章中间。

它需要类似以下精确信息：

```yaml
capture_id: cap_xxx
capture_version: 1
payload_sha256: sha256:...
start_byte: 1024
end_byte: 1388
excerpt_sha256: sha256:...
```

这样系统才能机械确认：

- 引用的是不是正确版本；
- 字节范围是否越界；
- 是否切断了一个中文字符；
- 这段原文后来有没有被错误替换；
- 点击证据后能否回到完全相同的内容。

`CUR1A` 只建立当前纵向切片需要的最小契约，大致包括：

- 来源绑定；
- 深度处理授权；
- Segment；
- 处理范围及缺口；
- Evidence locator；
- 目标建议和用户决定；
- 策展地图及候选项；
- 操作结果和回执。

它不会在这一步建立：

- 通用任务平台；
- 通用 Evidence 数据库；
- RAG schema；
- 知识图谱 schema；
- 模型管理平台；
- 远期多知识库协议。

所以这里的“契约”更接近一组严格的数据类和校验规则，不是一套新架构。

## 3. “错误语义”是什么

错误语义就是：发生问题时，系统要明确说明“发生了什么、有没有产生结果、用户应该怎么办”。

例如，不能笼统地返回：

> 处理失败。

而应该区分：

| 情况 | 系统应表达的含义 |
|---|---|
| 文件不是合法 UTF-8 | 输入无效，没有建立 Capture |
| 原件哈希和登记值不同 | 来源身份不匹配，已停止 |
| 用户未授权深度处理 | 未获得处理权限，没有启动策展 |
| locator 超出正文范围 | 证据引用无效，地图没有发布 |
| 用户尚未确认目标库 | 不创建知识库，不写 `raw/` |
| 目标目录已经有未知文件 | 路径冲突，未接管该目录 |
| Git 检查点失败 | 地图或 KB 不能报告为成功 |
| 文件已落盘但最终验证中断 | 提交状态未知，需要恢复检查 |
| 模型输出没有证据 | 处理器输出无效，不发布地图 |
| token 预算耗尽 | 已处理范围保留，其余明确标成缺口 |

尤其需要明确三种结果状态：

```text
确认未保存
确认已保存
状态未知，需要检查
```

这样可以避免最危险的情况：系统提示“成功”，实际却只写了一半；或者提示“失败”，实际已经写入，用户重试后生成重复结果。

## 4. `golden fixtures` 是什么

`golden fixtures` 可以理解为“固定的小型标准样本和标准答案”。

例如准备一个很小的测试原文：

```markdown
# 第一章

这是中文🙂。

第二段。
```

同时保存它应该得到的标准结果：

- 原文字节数；
- SHA-256；
- 每个 Segment 的字节范围；
- 行号；
- locator；
- 规范 YAML/JSON；
- 对应的 `map.md` 示例。

以后代码发生变化时，测试会重新生成结果，并与这份标准答案逐字节比较。

如果有人不小心改变了：

- 字节区间从半开变成闭合；
- Windows 换行被自动改成 LF；
- 中文或 emoji 被截断；
- YAML 字段顺序变化；
- 地图哈希算法变化；
- 未知字段被静默接受；

golden fixture 会立即报错。

它不是用来证明 AI 理解得好不好，而是证明基础格式、证据坐标和序列化行为没有漂移。

首批 fixture 会使用很小的人工样本，覆盖中文、emoji、LF/CRLF、空行、标题、表格、代码块和超长行，不需要把 1.18 MB 的真实长文复制进测试仓库。

## 5. “独立测试计数”是什么

目前项目状态记录的是：

```text
总测试 338
= Capture 测试 323
+ 脚本测试 15
```

开始开发策展功能以后，会新增：

```text
tests/curation/
```

因此应当改为：

```text
总测试
= Capture 测试
+ Curation 测试
+ 脚本测试
```

例如未来可能显示：

```text
tests=370
capture_tests=323
curation_tests=32
script_tests=15
```

具体新增多少项要以实际测试为准，现在不会预填数字。

独立统计的意义是：

- Capture 测试通过，只能证明捕获内核没有回退；
- Curation 测试通过，才证明策展相关能力符合新契约；
- 不能把原来的 323 项 Capture 测试包装成“策展功能已有大量测试”。

## `CUR1A` 完成后会得到什么

会得到：

- 一个很小的 `knowledgeflow_curation` 代码骨架；
- 当前切片需要的数据结构和校验规则；
- 统一、不会虚报成功的错误分类；
- 一组固定的小型标准样本；
- 单独统计的策展测试。

但此时还不会：

- 读取真实长文正文；
- 调用大模型；
- 创建真实知识库；
- 复制到 `raw/`；
- 生成真正的策展地图；
- 写入可信 Wiki。

所以 `CUR1A` 只是 `CUR-MVP-1` 内部的第一个可复核小批次，不是新的“底座项目”，也不能单独宣称产品功能已经完成。用户真正能看到并使用策展地图，要到 `CUR1D`；整条路径通过则要到 `CUR1V`。
