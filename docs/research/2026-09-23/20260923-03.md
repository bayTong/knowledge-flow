# 一、为什么此前需求理解跑偏

## 1. 现有需求文档有没有写错

它的明确表述大部分是正确的。

例如现有需求已经写明：

- 用户不愿意每次记录时先完成分类和整理；
- 捕获时不需要先选 KB、标签或处理方式；
- 理解、分类、提炼和关系建立可以由模型辅助；
- 新 KB 可以先创建无领域承诺的临时骨架；
- 大型材料可以先检索、再按问题生成局部证据和候选；
- 机器可以完成大量语义计算，只是不能未经批准直接获得可信身份。

见：

- [目标用户](C:/Users/REDACTED/knowledge-flow/docs/requirements-and-governance-baseline-需求与治理基线.md:72)
- [用户核心任务](C:/Users/REDACTED/knowledge-flow/docs/requirements-and-governance-baseline-需求与治理基线.md:78)
- [知识策展悖论](C:/Users/REDACTED/knowledge-flow/docs/requirements-and-governance-baseline-需求与治理基线.md:38)
- [SOP-000A](C:/Users/REDACTED/knowledge-flow/docs/sop-000a-provisional-kb-bootstrap-临时知识库骨架初始化.md:20)

因此，现有需求并没有明确要求：

```text
先确定领域
→ 先建立受控词表
→ 先建立 Taxonomy
→ 才能开始知识管理
```

相反，它总体上支持“先捕获、后理解、后组织”。

## 2. 现有需求真正的问题

问题不是“写反了”，而是：

> **通用知识管理目标只以零散原则出现，没有被提升成足够醒目、完整、可追踪的产品能力要求。**

当前需求文档的重心明显集中在：

- Capture Store；
- 身份、版本和哈希；
- 提案与可信知识隔离；
- 人工批准；
- 事务、恢复和回滚；
- 当前 MVP-0 实施状态。

这些都正确且必要，但用户真正期待的完整产品能力写得不够：

- 系统可以服务任意领域，而不是只适合已知领域；
- 用户不懂领域时，系统也能辅助研究和组织；
- 用户熟悉领域时，系统也能大幅减少手工整理；
- 系统承担大部分阅读、聚类、总结、组织和维护劳动；
- 用户可以问答、学习、编辑、重构和回滚；
- 系统可以提出多种组织方案，而不是要求用户预先设计；
- 标签、Taxonomy、Ontology 可以从使用中逐步形成；
- 不同知识需求可以采用不同组织方式；
- 人工审核必须按风险分层，不能让用户审批所有细节。

在当前顶层功能需求目录里，Capture、读取、版本、CLI、证据、提案、可信写入已经有 `FR-*`，但还缺少足够明确的：

```text
研究辅助需求
知识组织需求
问答与学习需求
已知领域加速整理需求
未知领域探索需求
知识维护与重构需求
自适应结构形成需求
人工负担控制需求
```

所以它是一份很强的“治理与捕获需求基线”，但还不是完整表达你最终产品愿景的成熟 PRD。

## 3. 我自己的推理错误

不能把问题完全归咎于文档。我之前犯了几个具体错误。

### 错误一：过度重视当前实现重心

仓库当前绝大部分代码和测试集中在 Capture 内核，因此我不自觉地把：

```text
当前正在实现什么
```

误当成了：

```text
产品最终主要是什么
```

但 Capture 内核只是通用知识管理系统的可靠底座，不是最终产品全部价值。

### 错误二：把“可信入库前必须治理”误写成“处理前必须先有结构”

正确逻辑是：

```text
可以在没有正式结构时捕获、研究、问答、聚类和生成候选；
只有进入可信知识层之前，结构和变更才需要经过治理。
```

我一度把它表达成：

```text
先有 KB Profile、词表和分类
→ 再进行语义处理
```

这是把“可信晋升条件”和“开始知识处理的条件”混淆了。

### 错误三：把治理工件写成了用户前置工作

`KB Profile`、受控词表、Taxonomy 和 Ontology 可以是系统逐步生成、用户按需确认的产物。

我此前的线性图容易给人一种印象：

> 用户必须先把它们准备好。

这与项目降低策展负担的目标相冲突。

### 错误四：把一个 Wiki 模板泛化成通用产品模型

当前 `SCHEMA-template.md` 的四类页面和标签体系，只适合作为一种 Markdown Wiki 参考模式。

它不应该被理解为：

> 所有 KnowledgeFlow 知识库都必须使用相同页面类型、标签和分类方式。

# 二、专业、完整的需求文档应该怎样

## 1. “完整”不等于把所有内容塞进一份超长文档

专业需求体系通常分层：

```text
L0 产品需求 / PRD
    为什么做、为谁做、解决什么、必须具备什么、如何判断成功

L1 功能或主题规范
    某项功能具体怎样工作

L2 技术设计与数据契约
    字段、状态机、错误、事务和接口

L3 实施与验收
    编码批次、测试矩阵、CI 和发布证据
```

当前项目已经采用类似结构，这是正确的。

专业完整性应该理解为：

> 每个重要产品目标都有明确需求 ID、范围、优先级、验收方式和下游追踪，而不是把所有 Schema、算法和测试复制进一份文件。

## 2. 是否需要新建一份完整需求文档

不需要，也不应该。

当前 [需求与治理基线](C:/Users/REDACTED/knowledge-flow/docs/requirements-and-governance-baseline-需求与治理基线.md)已经被指定为：

> 唯一 L0 产品需求与治理入口。

而冲突登记的 C-054 也明确裁决：

> 不再建立第二份并行“完整 PRD”。

因此最专业的做法是：

- 保留现有文件路径；
- 保留它作为唯一 L0 权威；
- 对内容做系统性增强；
- 字段、接口和算法继续留在 L1/L2；
- 不新建另一份“KnowledgeFlow 完整需求.md”。

必要时可以把文档标题调整为：

```text
KnowledgeFlow 产品需求与治理基线（PRD）
```

但不建议改文件名，以免制造大量链接迁移。

## 3. 专业 PRD 应包含哪些部分

现有文档可以整理为下面的结构。

### 1. 文档控制

- 状态；
- 版本；
- 权威范围；
- 最后确认时间；
- 哪些部分已批准；
- 哪些仍是 Draft。

### 2. 产品定位

必须明确写出：

> KnowledgeFlow 是通用、适应性、治理优先的个人知识工作与知识管理系统，而不是仅面向已知领域的知识库初始化工具，也不是要求用户先设计好分类体系的 Wiki 生成器。

### 3. 问题与价值主张

至少覆盖：

- 知识捕获摩擦；
- 策展悖论；
- 陌生领域理解困难；
- 大规模材料审查困难；
- 手工组织成本；
- 黑盒自动策展风险；
- 已有知识库持续维护困难。

### 4. 目标用户和 Jobs to Be Done

不能只有“单机用户”，还要明确用户想完成的工作：

- 随手保存但不丢失；
- 快速整理一批杂乱材料；
- 从陌生领域开始研究；
- 加速整理熟悉领域；
- 围绕问题学习；
- 维护已有知识库；
- 发现重复、冲突和过时知识；
- 编辑、重组、撤销和回滚；
- 在不同组织形式之间迁移。

### 5. 代表性用户场景

至少需要四条完整旅程：

#### 低摩擦捕获

```text
随手输入
→ 自动汇总/聚类
→ 给出路由和组织提案
→ 用户选择保留、忽略、延期或入库
```

#### 陌生领域深入研究

```text
用户提出主题或问题
→ 系统研究并组织证据
→ 形成多层概念地图和学习路径
→ 用户通过问答逐步理解
→ 高价值内容逐步提升
```

#### 熟悉领域快速组织

```text
系统对齐已有结构
→ 自动发现新增、重复、冲突和缺口
→ 生成精确变更
→ 用户批量批准
```

#### 大型持续资料库

```text
先检索和问答
→ 查询触发局部候选
→ 高频知识逐渐稳定
→ 必要时形成标签、Taxonomy 或 Ontology
```

### 6. 产品原则和自主性模型

明确：

```text
低风险机械操作       可以自动
可逆语义整理         可以批量提案
高影响结构变化       需要精确批准
不可逆或大范围变更   需要检查点和回滚
```

避免把“禁止黑盒可信写入”误解为“AI 不能承担大部分整理劳动”。

### 7. 顶层功能需求

建议将功能需求按能力域分组：

| 能力域 | 需要覆盖的需求 |
|---|---|
| Capture | 保存、版本、来源、读取、续写 |
| Research | 搜索、外部研究、证据整理、不确定性 |
| Understand | 摘要、概念、主张、关系、冲突 |
| Organize | 聚类、标签、Wiki、专题、Taxonomy、图谱提案 |
| Interact | 问答、探索、学习路径、局部展开 |
| Govern | 提案、批准、权限、信任层 |
| Maintain | 编辑、合并、拆分、重构、过期和冲突维护 |
| Recover | 事务、历史、撤销和回滚 |
| Adapt | 不同入口、模型、RAG、GBrain 和组织方式 |

例如以后可能需要增加：

```text
FR-ASSIST-*   AI 辅助理解和研究
FR-ORG-*      自适应知识组织
FR-QA-*       问答和探索
FR-LEARN-*    学习路径与多层理解
FR-MAINT-*    编辑和持续维护
FR-STRUCT-*   结构候选与渐进规范化
```

具体 ID 可以在正式补充时再统一设计。

### 8. 顶层非功能需求

除可靠性、安全性外，还应增加或强化：

- 人工负担；
- 首次可用时间；
- 可解释性；
- 结构可演化性；
- 不依赖预设领域；
- 多种组织方式兼容；
- 模型和后端可替换；
- 大体量材料的成本可控。

### 9. 版本范围

清楚区分：

```text
最终产品目标
当前版本范围
下一阶段能力
远期设想
```

目前文档容易让当前 MVP-0 状态淹没长期产品目标。

### 10. 成功指标

“支持任何知识库”和“快速”不能直接作为无法验证的绝对承诺，应翻译成可测指标：

- 无领域/无 Schema 时能否开始；
- 从输入到第一版组织提案需要多久；
- 用户需要多少手工操作；
- 人工审核耗时；
- 提案接受、修改和拒绝比例；
- 问答引用正确率；
- 用户能否找到并纠正错误；
- 结构重组能否回滚；
- 跨多个代表领域是否仍不依赖硬编码类型。

# 三、现有需求文档应该修改多少

现有文档不需要推倒重写，因为它已经具备：

- 核心问题；
- 北极星；
- 目标用户；
- 信任层；
- 治理原则；
- 功能需求 ID；
- 非功能需求；
- 版本范围；
- 成功信号；
- 未决策项；
- 追踪矩阵。

它缺的是“产品能力中段”。

可以概括为：

```text
前端的捕获底座：写得很完整
后端的治理边界：写得很完整
中间的研究、理解、组织、问答、学习和维护：写得不够
```

因此应当是一次“扩充和重新平衡”，不是重新建立整套需求。

# 四、概念架构导读是否需要很大修改

## 结论

> 需要一次范围明确但实质性的修订；不需要推倒重写。

大约三分之二内容仍然有效。

## 可以基本保留的部分

以下内容方向正确：

- Ontology、Schema、SOP 的概念区别；
- 受控词表、Taxonomy、Ontology、知识图谱的递进关系；
- RAG 和 GBrain 的信任边界；
- Karpathy LLM Wiki 的定位；
- T0–T3 信任分层；
- 候选、证据、批准和可信知识的区别；
- `processing_mode` 与 `processing_profile` 的区别；
- 当前状态与目标状态表；
- 文档权威关系说明。

## 需要实质调整的部分

### 1. 一句话定位过于偏向“已有知识库”

当前写的是：

> 根据知识库目标选择处理方式。

见[概念架构导读](C:/Users/REDACTED/knowledge-flow/docs/knowledgeflow-conceptual-architecture-KnowledgeFlow概念架构导读.md:22)。

应改成更宽的表述：

> 用户可以从原始材料、问题、研究主题、已有知识库或模糊意图开始；系统帮助其理解、研究、组织、使用和治理知识，知识库目标和结构可以在过程中逐步形成。

### 2. 把“为什么建立知识库”写成了唯一用户目标

当前多处默认：

```text
用户已经有目标知识库
→ 根据 KB 目标判断材料
```

但实际还应支持：

```text
用户不知道是否需要新建 KB
用户只有一个问题
用户只是想学习某个陌生领域
用户希望先研究再决定怎样组织
用户只想保存和汇总
```

所以“用户目标”应从：

```text
我为什么建立这个知识库
```

扩大为：

```text
我现在想完成什么知识任务
```

### 3. `KB Profile` 被写得过于完整和前置

当前第 5.2 节写了完整的：

- purpose；
- audience；
- questions；
- in/out scope；
- curation policy；
- ontology reference；
- schema reference。

见[KB Profile 示例](C:/Users/REDACTED/knowledge-flow/docs/knowledgeflow-conceptual-architecture-KnowledgeFlow概念架构导读.md:267)。

示例本身有价值，但需要明确支持：

```yaml
purpose:
  status: pending

domain:
  status: emerging

taxonomy:
  status: absent

ontology:
  status: absent
```

并说明：

- KB Profile 可以不完整；
- 可以由系统提案；
- 可以在问答和使用中演化；
- 不阻塞捕获、研究或检索；
- 不一定每个知识工作都要先创建 KB。

### 4. 四层关系被画成了单向强依赖

当前是：

```text
全局需求
→ KB 长期政策
→ Capture user_intent
→ Processing Proposal
```

这容易让人理解为必须先有 KB 长期政策。

应改为多个可选上下文共同影响处理：

```text
用户当前任务 ─────────┐
已有 KB 政策（可无）──┤
已有结构（可无）──────┤
历史使用反馈 ─────────┤
材料规模与风险 ───────┤
                       ▼
               本次处理建议
```

### 5. 完整目标架构强制先路由再处理

当前目标图大致是：

```text
Capture
→ 路由
→ KB 长期政策
→ Processing Proposal
→ 处理
```

但应该允许：

```text
Capture
→ 暂不路由
→ 全局搜索、摘要、问答或研究
→ 形成组织提案
→ 后续再决定是否进入某个 KB
```

以及：

```text
问题/研究主题
→ 研究工作空间
→ 证据和候选
→ 再决定建不建 KB
```

### 6. Ontology 要明确为可选产物

当前虽然说了不应前置，但整篇位置仍让它显得像主要基础设施。

应明确：

- 某些知识库只需要集合和标签；
- 某些需要 Wiki；
- 某些适合 Taxonomy；
- 某些才需要 Ontology/知识图谱；
- Ontology 可以从高价值、高复用的候选中逐渐形成。

### 7. 端到端例子太单一

当前只有：

> 放入 Agent 学习库并深度整理。

需要至少增加：

- 无目标 KB 的随手捕获；
- 完全陌生领域的研究与学习；
- 已有知识库的快速维护；
- 大型语料的 retrieval-first 场景。

### 8. 后续顺序过度强调先冻结 KB 目标政策

当前写着：

```text
在人工路由和 SOP-000A 前冻结最小 KB Registry/目标政策职责
→ 本地检索 POC
```

见[实施顺序](C:/Users/REDACTED/knowledge-flow/docs/knowledgeflow-conceptual-architecture-KnowledgeFlow概念架构导读.md:713)。

需要区分：

- 人工路由需要最小 KB 身份注册；
- 检索和研究 POC 不一定需要完整 KB Profile；
- 用户目标和结构可以在处理过程中形成；
- Ontology/Taxonomy 不应成为本地检索的前置条件。
