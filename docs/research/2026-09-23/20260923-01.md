A：可以先把它们理解为一条逐渐增强的语义链：

```text
自由标签
   ↓ 统一可使用的词
受控词表 Controlled Vocabulary
   ↓ 增加上位/下位分类关系
Taxonomy 分类体系
   ↓ 增加多种关系、属性和语义约束
Ontology 知识本体
   ↓ 填入具体实体和事实
Knowledge Graph 知识图谱
```

KnowledgeFlow 目前已经使用了若干“受控词表”，也出现了 Taxonomy 的雏形，但还没有建立正式、稳定的领域 Taxonomy。

# 一、什么是受控词表

受控词表就是：

> 系统规定一组可以使用的标准词，每个词有确定含义；遇到同义词、别名或不同写法时，统一映射到标准词。

## 1. 最简单的例子

假设不同材料里出现：

```text
RAG
检索增强生成
Retrieval-Augmented Generation
检索增强
```

如果不治理，系统可能把它们当作四个不同概念。

受控词表可以规定：

```yaml
id: rag
preferred_label: 检索增强生成
english_label: Retrieval-Augmented Generation
aliases:
  - RAG
  - 检索增强
definition: 先检索外部资料，再将检索结果提供给生成模型的方法
status: approved
```

以后：

- 页面使用稳定 ID `rag`；
- 中文界面显示“检索增强生成”；
- 搜索“RAG”仍然能找到；
- 新出现的写法可以作为别名提案；
- 不需要重复创建页面。

## 2. “受控”体现在哪里

一个较完整的受控词表通常具备：

- 稳定 ID；
- 推荐名称；
- 清晰定义；
- 别名或同义词；
- 状态：候选、已批准、已废弃；
- 变更记录；
- 谁可以增加或修改；
- 被废弃后由哪个词替代。

如果只有一串词，但任何人都能随意增加、没有定义、没有审批，那么它只是普通标签集合，还不能算治理完善的受控词表。

## 3. 受控词表不一定有层级

例如：

```text
high
medium
low
```

这是受控词表，但没有谁属于谁的父类。

```text
capture-only
raw-source
deep-curation
```

也是受控取值，但不是 Taxonomy。

# 二、什么是 Taxonomy

Taxonomy 通常翻译为“分类体系”或“分类法”。

它在受控词表基础上增加：

> 哪些概念是更大的类别，哪些概念是其下属类别。

例如：

```text
人工智能
├── 机器学习
│   ├── 监督学习
│   └── 强化学习
├── 大语言模型
│   ├── 训练
│   ├── 推理
│   └── 对齐
└── Agent
    ├── 工具调用
    ├── 记忆
    │   ├── 短期记忆
    │   └── 长期记忆
    └── 规划
```

其中表达的是：

```text
短期记忆 是一种 Agent 记忆
Agent 记忆 是 Agent 的一个知识主题
```

常见关系是：

- `broader`：更宽泛的上位概念；
- `narrower`：更具体的下位概念；
- `is_a`：是一种；
- `parent/child`：父分类/子分类。

## Taxonomy 不等于文件夹树

例如：

```text
wiki/
├── entities/
└── queries/
```

这主要是文件组织方式。

真正的 Taxonomy 可能是：

```text
agent-memory
  broader: agent
  narrower:
    - short-term-memory
    - long-term-memory
```

同一个概念还可能同时属于多个上位主题。例如 Graph RAG 可以同时属于：

```text
RAG
知识图谱
检索系统
```

普通文件夹通常只能给文件一个位置，而 Taxonomy 可以支持多个语义父类。

# 三、受控词表、Taxonomy 和 Ontology 的区别

| 能力 | 受控词表 | Taxonomy | Ontology |
|---|---:|---:|---:|
| 统一标准名称 | 是 | 是 | 是 |
| 记录别名/同义词 | 可以 | 可以 | 可以 |
| 上位/下位分类 | 不要求 | 核心能力 | 可以 |
| 表达多种关系 | 很弱 | 主要是分类关系 | 核心能力 |
| 约束关系两端类型 | 否 | 通常不做 | 可以 |
| 支持语义推理 | 否 | 很有限 | 可以 |
| 典型问题 | “应该叫哪个名字？” | “它属于哪一类？” | “它和其他事物是什么关系？” |

例如：

```text
受控词表：
标准词是“检索增强生成”，别名是“RAG”。

Taxonomy：
检索增强生成 属于 检索方法。

Ontology：
检索增强生成 --uses--> Retriever
检索增强生成 --uses--> Generator
检索增强生成 --evaluated_by--> Benchmark
Evidence --supports--> Claim
```

# 四、KnowledgeFlow 当前哪里已经用了受控词表

## 1. SCHEMA 中的标签注册表

这是项目中最明确的知识领域受控词表雏形。

[SCHEMA-template.md](C:/Users/94233/knowledge-flow/templates/SCHEMA-template.md:116)规定：

- 标签必须先注册、后使用；
- 每个标签需要有含义说明；
- 不在体系内的标签不得使用；
- 初始只建立当前真实材料需要的标签；
- 避免标签无限扩张。

例如：

```markdown
| 标签 | 含义 |
|---|---|
| `rag` | 检索增强生成 |
| `agent` | 能够规划并调用工具的智能体系统 |
| `decision` | 页面包含明确选择建议 |
```

这已经符合受控词表的基本思想：

```text
自由输入标签
        ↓
先在 SCHEMA 注册
        ↓
Wiki 页面才可以使用
```

### 当前约束强度

[scripts/lint.py](C:/Users/94233/knowledge-flow/scripts/lint.py:133)会：

- 从 `SCHEMA.md` 的标签体系中读取已注册标签；
- 检查页面是否使用未注册标签；
- 提醒哪些已注册标签从未使用。

因此，这不仅是文档约定，还有现有工具支持。

但当前未注册标签只产生 Warning，不是可信写入阶段的硬拒绝；而且这套 Lint 属于现有 Markdown KB 参考实现，还没有接入未来的新 SOP-002 可信写入事务。

## 2. Wiki 页面类型

[SCHEMA-template.md](C:/Users/94233/knowledge-flow/templates/SCHEMA-template.md:81)定义了四种页面类型：

```text
concept
comparison
entity
query
```

这也是受控词表，因为页面不能随意填写：

```text
type: note
type: person
type: tutorial
```

现有 [lint.py](C:/Users/94233/knowledge-flow/scripts/lint.py:55)用固定 `PAGE_TYPES` 检查页面类型。

但这四种页面类型只是一个扁平列表：

```text
concept
comparison
entity
query
```

它们没有父子关系，所以不是完整 Taxonomy。

## 3. 置信度和页面状态

例如：

```text
high
medium
low
```

以及：

```text
contested: true / false
```

这些是受控值。它们统一系统对置信度和争议状态的表达，但不构成领域分类体系。

## 4. 提取接口中的实体类型

实验性 [extraction-interface.md](C:/Users/94233/knowledge-flow/prompts/extraction-interface.md:15)规定标识符前缀：

```text
concept
tool
model
platform
storage
```

这是一套实验性受控实体类型词表。

例如：

```text
@concept:rag
@tool:langchain
@model:gpt
@storage:vector-database
```

但它有几个限制：

- 只存在于旧 SOP-001 实验格式中；
- 允许“扩展新类型时显式标注”，约束并不严格；
- 尚未成为正式 Knowledge Candidate Schema；
- 类型之间没有父子结构；
- 没有经过当前可信知识晋升流程。

所以它是**候选受控词表**，不是已批准的全局 Ontology。

## 5. 不确定原因分类

[extraction-interface.md](C:/Users/94233/knowledge-flow/prompts/extraction-interface.md:43)定义：

```text
来源不可靠
Agent 理解局限
原文模糊
信息不完整
总结压缩损失
```

这是设计得比较完整的一套受控分类词表，因为每个值都有：

- 名称；
- 含义；
- 使用场景；
- 人工处理策略。

但它依然属于旧实验资产，未来应在 Evidence Bundle/候选契约冻结时重新复核，而不是直接当作正式生产枚举。

## 6. 关系类型

[extraction-interface.md](C:/Users/94233/knowledge-flow/prompts/extraction-interface.md:77)定义了：

```text
uses
complements
contains
contrasts_with
enables
improves
evolves_from
serves_as
optimizes
```

这是一套“受控关系词表”。

它已经比普通标签更接近 Ontology，因为它还记录：

- 关系方向；
- 关系含义；
- 使用示例。

例如：

```text
uses：A → B
complements：A ↔ B
contains：A → B
```

但是它没有约束：

```text
uses 的 A 允许是什么类型？
uses 的 B 允许是什么类型？
contains 是否具有传递性？
complements 是否严格对称？
evolves_from 的反向关系叫什么？
```

因此它属于：

> Ontology 雏形，而不是完整 Ontology。

## 7. Capture 内核中的受控值

代码中也有很多受控取值，例如：

```text
processing_mode:
- capture-only
- raw-source
- deep-curation
```

见 [models.py](C:/Users/94233/knowledge-flow/src/knowledgeflow_capture/models.py:13)。

还有：

```text
payload role:
- primary
- attachment

fidelity:
- byte-exact
- channel-exact
- canonical-snapshot

routing.status:
- unassigned

trust.status:
- unreviewed-capture
```

这些从广义上说也是受控词表，但应注意：

> 它们是机器协议和工作流状态词表，不是知识领域词表。

它们解决的是“系统状态怎样统一表达”，不是“Agent、RAG、模型等知识怎样分类”。

# 五、项目当前哪里体现了 Taxonomy

## 1. Wiki 模块是很浅的分类结构

SCHEMA 模板允许：

```text
01-核心架构
02-检索
03-Agent
04-评测
```

页面按模块分组，这可以看作浅层主题分类。

但模板明确不设二级子目录，因此当前模块结构更像：

> 扁平的信息架构或导航分类。

还不是正式 Taxonomy，因为没有稳定概念 ID、父子关系、别名或跨模块多重归属。

## 2. 主题标签和性质标签是 Faceted Classification

模板把标签分为：

```text
主题标签：页面在讲什么
性质标签：页面具有什么特征
```

例如：

```text
主题标签：rag、agent、memory
性质标签：comparison、decision
```

这属于“分面分类”雏形：

- 主题是一个维度；
- 页面性质是另一个维度。

它比完全自由的标签更有组织，但仍不是层级 Taxonomy，因为没有表达：

```text
agent-memory narrower_than agent
long-term-memory narrower_than agent-memory
```

## 3. 策展地图中的“所属层次”

实验提取接口要求每个实体选择“所属层次”，并规定必须从该次处理已经声明的层次列表中选择，见 [extraction-interface.md](C:/Users/94233/knowledge-flow/prompts/extraction-interface.md:17)。

这说明旧策展地图会为一份材料临时生成类似：

```text
第一层：基础概念
第二层：系统组件
第三层：实现工具
```

这可以视为：

> 单次材料范围内、由模型生成的临时 Taxonomy。

但它不是正式 KB Taxonomy，因为：

- 不同材料可能产生不同层次；
- 层次名称可能不一致；
- 没有稳定 ID；
- 没有跨文档合并规则；
- 没有版本和废弃规则；
- 没有经过正式人工批准；
- 目前只是实验性策展地图内容。

## 4. SOP-000A 有意延迟 Taxonomy

SOP-000A 明确规定：创建临时 KB 时，不要求提前确定：

- 完整领域；
- 页面类型；
- 关系类型；
- 标签分类法；
- 模块目录。

见 [SOP-000A](C:/Users/94233/knowledge-flow/docs/sop-000a-provisional-kb-bootstrap-临时知识库骨架初始化.md:61)。

这是一个合理的设计：

```text
先创建安全容器
    ↓
放入代表性原料
    ↓
提取候选概念、标签和层次
    ↓
人工审核
    ↓
再建立获批 SCHEMA / Taxonomy
```

它避免系统在不了解领域时，让 LLM 凭空创造一个看起来完整、实际不适用的分类体系。

# 六、当前项目还没有什么

KnowledgeFlow 当前还没有正式实现：

- 跨文档稳定的领域 Taxonomy；
- 标准概念 ID；
- 推荐名称与别名映射；
- `broader/narrower` 父子关系；
- 多重父分类；
- 分类版本；
- 分类废弃与替代；
- Taxonomy Change Proposal；
- KB Registry 中的 taxonomy/ontology 引用；
- 用 Taxonomy 约束 RAG 和候选图谱；
- 获批 Taxonomy 与 Wiki 页面之间的完整校验。

因此准确判断是：

| 能力 | 当前程度 |
|---|---|
| 操作状态受控值 | 已实现 |
| Wiki 页面类型受控词表 | 有模板和 Lint |
| Wiki 标签受控词表 | 有注册表和 Lint |
| 实验性实体/关系词表 | 有，但属于 Draft 提示词资产 |
| 单次材料层次分类 | 有实验格式 |
| KB 级正式 Taxonomy | 尚未建立 |
| 正式 Ontology | 尚未建立 |
| Taxonomy/Ontology 驱动 RAG | 尚未实现 |

# 七、它们怎样与 KnowledgeFlow 结合

最合理的组合不是一开始建立大型 Taxonomy，而是逐级治理。

## 第一阶段：受控词表

从真实材料中统一高频词：

```yaml
id: agent-memory
preferred_label: Agent 记忆
aliases:
  - 智能体记忆
  - Agent Memory
definition: Agent 保存和调用历史状态与知识的机制
status: approved
```

用途：

- 消除同义词重复；
- 统一标签；
- 改善搜索；
- 避免生成多个近义页面；
- 为以后 Taxonomy 提供稳定节点。

## 第二阶段：建立必要的 Taxonomy

只有确实需要层级导航和检索时才增加：

```text
Agent
├── Agent 记忆
│   ├── 短期记忆
│   ├── 长期记忆
│   └── 情景记忆
├── 工具调用
└── 规划
```

用途：

- 用户从宽泛主题逐层浏览；
- RAG 查询“Agent 记忆”时可以扩展到子类；
- 策展地图可以把候选放到正确主题；
- 识别知识库哪些类别为空或过度拥挤。

## 第三阶段：扩展为轻量 Ontology

只有分类层级不够时，再增加：

```text
Agent --uses--> Tool
Agent --has_memory--> Memory
Memory --implemented_by--> VectorDatabase
Claim --supported_by--> Evidence
Method --evaluated_by--> Benchmark
```

## 第四阶段：填充候选和可信知识图谱

```text
AutoGPT --uses--> WebSearchTool
MemGPT --has_memory--> LongTermMemory
某论文观点 --supported_by--> 某实验表格
```

这些具体事实先进入候选图谱，人工批准后才能成为可信图谱。

# 八、它们应当怎样进入项目治理

推荐未来采用“候选先行、批准后生效”：

```text
原文出现新词或新分类
        ↓
模型尝试匹配现有受控词表
        │
        ├─ 能匹配 → 使用稳定 ID
        │
        └─ 不能匹配 → 生成候选词条
                         ↓
               Vocabulary/Taxonomy Proposal
                         ↓
                    人工审核
             ┌───────────┴───────────┐
             ▼                       ▼
          批准加入                  拒绝/合并
             │
             ▼
      更新正式 SCHEMA/注册表
             │
             ▼
      必要时迁移已有页面和索引
```

新增或修改：

- 标签；
- 页面类型；
- 分类节点；
- 父子关系；
- 关系类型；
- 别名；
- Ontology 约束；

都属于语义结构变更，不能由模型后台直接执行。现有需求基线已经规定：新增页面类型、关系类型、标签体系或模块必须先提案，见 [需求与治理基线](C:/Users/94233/knowledge-flow/docs/requirements-and-governance-baseline-需求与治理基线.md:110)和[权限矩阵](C:/Users/94233/knowledge-flow/docs/requirements-and-governance-baseline-需求与治理基线.md:230)。

# 九、与 KB Profile、RAG 和策展的关系

未来比较清晰的职责关系可以是：

```text
KB Profile
├── purpose                 为什么建立这个 KB
├── in_scope/out_of_scope   收什么、不收什么
├── vocabulary_ref          使用哪套标准词
├── taxonomy_ref            使用哪套分类体系
├── ontology_ref            使用哪些概念与关系
├── schema_ref              页面和数据怎样表示
└── curation_policy         什么条件下值得提升
```

处理一份材料时：

```text
用户目标
    决定处理目的

受控词表
    统一原文中的不同名称

Taxonomy
    把概念放入合适分类层级

Ontology
    识别实体之间的多种关系

策展策略
    判断哪些候选值得审核和提升

RAG
    利用别名扩展、父子分类和关系找到证据

人工批准
    决定哪些候选最终进入可信知识
```

RAG 可以分别利用：

- 受控词表：同义词扩展和概念归一；
- Taxonomy：上位词、下位词和分类过滤；
- Ontology：沿关系检索相关实体；
- 策展策略：决定哪些检索结果值得形成候选。

# 十、当前最合适的方向

不建议现在马上建设完整 Taxonomy 或新增实现批次，因为：

- 当前还没有正式 KB Profile；
- Processing Profile、Segment、Ledger 和 Evidence Bundle 尚未冻结；
- 没有真实生产 KB 运行数据；
- 领域分类很容易因提前设计而失真；
- 当前主线仍是 C7/C8 捕获 MVP 收尾。

更合理的顺序是：

```text
先完成 C7/C8
    ↓
真实 Capture dogfood
    ↓
选择一个小型代表性知识库
    ↓
收集真实出现的词、别名、标签和分类冲突
    ↓
先验证最小受控词表
    ↓
再验证哪些概念确实需要父子层级
    ↓
形成 Taxonomy 候选
    ↓
最后决定哪些非分类关系需要 Ontology
```

最终判断：
