## 二、对第一份评估的判断

### 准确且重要的部分

#### H1：初始化事务清理过早删除所有权标记

这个判断成立。

初始化事务树在 [_safe_transaction_tree](C:/Users/94233/knowledge-flow/src/knowledgeflow_capture/store.py:1062) 中将 `transaction.yaml` 纳入文件列表，而 [_remove_owned_transaction](C:/Users/94233/knowledge-flow/src/knowledgeflow_capture/store.py:1169) 会先删除文件、后删除目录。若在标记删除后、其他内容删除完成前失败，可能留下无法再确认所有权的残留树。

但第二份方案称它是“一行修复”并不准确。正确修复应像现有 capture staging 清理那样分成：

1. 内容文件；
2. 内容子目录；
3. 所有权标记；
4. 事务根目录。

否则只把标记移动到当前目录循环之后，根目录仍会因为标记存在而无法删除。可参考 [_cleanup_capture_staging](C:/Users/94233/knowledge-flow/src/knowledgeflow_capture/store.py:924) 的结构。

#### H2：配置临时文件所有权隔离不足

这个判断也成立。

[_cleanup_config_temp_candidates](C:/Users/94233/knowledge-flow/src/knowledgeflow_capture/store.py:1284) 在共享父目录中扫描统一命名模式，并以配置字节内容作为主要识别条件；不同目标配置文件使用不同初始化锁，但可能生成相同内容，因此存在一个初始化请求删除另一个请求临时文件的窗口。

不过，第二份方案建议的“16 位截断标签”仍不够严谨。更合理的是让临时文件绑定：

- 精确目标配置路径；
- 完整请求身份或足够强的全长摘要；
- 预期配置内容；
- 必要时再核对文件身份。

旧格式临时文件应保守处理，不能因为无法识别就积极删除。

#### 文档和提示词漂移

多数事实核查成立，例如：

- [CHANGELOG.md](C:/Users/94233/knowledge-flow/CHANGELOG.md:23)仍写“停在 C3V 授权前”。
- 中英文 README 的文档树缺少 C3-0 决策文档。
- 四套实体表模板声称遵守七字段接口，实际缺少“不确定原因”列。
-提示词中的 schema 占位符和 README 清单不一致。
- `implements` 示例不属于已定义的关系类型。
- Mode B assembler 没有明确重复 `<80%` 的规则。
- “提取确定性”和“来源可靠性”存在真实的语义冲突。
- Agent 建议的隔离原则没有被模板稳定执行。

这些问题应登记，但它们属于 Draft 提示词体系，不能全部升级为 C4 前阻塞项。

### 被夸大的部分

#### M1 不是“死代码”

`_same_identity` 的路径统计错误可能已被 `_InitFailure` 转换，但 `_remove_owned_transaction` 中的 `unlink()`、`rmdir()` 本身仍可能抛出 `OSError`。所以相关异常处理并非完全不可达。

应先构造明确复现，再决定是否修改公共路径统计函数；不适合顺手全局重构。

#### M4 的重试分类不能把 WinError 5 一概纳入

[DurabilityError](C:/Users/94233/knowledge-flow/src/knowledgeflow_capture/durability.py:54)目前固定 `retryable=False`，与文档中的临时共享冲突语义确有差距。

但 WinError 5 也可能是长期 ACL 拒绝，而非短暂共享冲突。建议只先覆盖能够证明是临时共享冲突的 WinError 32/33，再通过测试扩展，不应宽泛分类。

#### “生产路径测试空转”并不成立

测试比较执行前后的真实配置和 Store 状态，能够证明没有遗留生产制品。它确实不能证明过程中从未发起过路径访问，但这并不等于测试无效。

#### “SQLite 约 500 行即可替代”缺少依据

SQLite 可能简化一部分索引和事务，但正文 payload 仍是外部文件时，会产生数据库与文件系统之间的跨资源原子性、备份、迁移和审计问题。现在没有足够证据证明切换后能保留已有保证，因此不应改变存储架构。

## 阶段 C4-0：读取契约收口

这是下一项真正需要完成的设计门禁。

需要一次性冻结：

1. `get_capture` 的正文传输方式  
   建议返回元数据，并把正文写入调用方提供的二进制 sink；内部允许有界临时缓冲，但不能把 64 MiB 正文整体载入内存。

2. 完整性失败语义  
   在正文对外可见前完成验证；完整性失败时不得输出部分正文。

3. 版本提交判定  
   版本目录存在不能自动等于已提交。应以精确匹配的封存 Event 作为逻辑提交证据。

4. 通用版本解析  
   C4 不应把 `v000001` 永久硬编码为唯一版本。至少要能识别合法版本链、缺口、未知文件和未来 `capture.version-appended` 事件。

5. `list_captures` 的完整性深度  
   列表负责结构、Envelope、Event、声明大小和有界 preview；完整 payload hash 由 `get_capture` 完成。这样才能避免列表扫描所有大文件。

6. 游标  
   使用带版本号的 base64url keyset cursor，并绑定查询指纹；查询参数改变、游标版本不支持或格式损坏时返回固定 `invalid_input`。不建议引入无依据的 TTL。

7. 时间过滤  
   明确基于 `captured_at` 的 UTC 毫秒边界，并冻结包含/排除规则。

8. 警告归属  
   投影或单 Item 异常必须携带 `capture_id`，不得形成无法定位的全局 warning。
