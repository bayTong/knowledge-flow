# 二、我必须承认的四个错误

### 错误 1（严重）：H1 的修复方案机械上不成立

我写的是"把 marker 的 unlink 移到内容目录全部 rmdir 之后、事务目录 rmdir 之前"——**前半句我写对了，但紧接着的操作指令写错了**："在 `store.py:1193` 的目录循环之后插入 marker 的 unlink"。而 `store.py:1155` 明确把事务根追加进了 `directories`，所以"目录循环之后"= 根 rmdir 之后 = marker 已经删不掉了。

正确修复必须**拆分列表**：

```
files           = [marker] + content_files        → 拆成 content_files 与 marker
directories     = content_dirs + [transaction_root] → 拆成 content_dirs 与 root

正确顺序：
  1. unlink(content_files)
  2. rmdir(content_dirs, 深度逆序)
  3. unlink(marker)                 ← 此时根目录已空但仍在
  4. rmdir(transaction_root)
```

这不是"行级改动"，而是要在 `_safe_transaction_tree` 的返回结构上区分"事务根"与"内容目录"——**评审说它是结构性改动，正确**。我把一个需要改数据结构的改动说成"一行"，这是对工作量的实质性低估。

### 错误 2（严重）：B4 整批建立在对写入顺序的错误假设上

我提的四个 `_CaptureFaultPoint` 里，`AFTER_PAYLOAD_WRITTEN`（"payload 落盘后、marker 前"）**描述了不存在的状态**——marker 最先写。我读 `operations.py` 时看过 `_create_capture_staging`（`store.py:708-787`），但没有把它与 `_write_candidate_metadata`（`operations.py:780-795`）的顺序在脑子里对齐，就直接排了故障点表。

这是**读代码不彻底导致的方案错误**，比单纯的口径分歧严重。

### 错误 3：把"故意提交失败测试"当作工程手段

我建议"先写会失败的测试把缺口钉住"，让红测试进主线。这在任何项目里都劣于"登记到测试矩阵"，在一个**治理优先、每个批次都要独立授权复核**的项目里更是直接违背其运作方式（`coding-plan` 已明确把业务事务恢复留给 C6）。评审这一条完全正确。

### 错误 4：战略判断被"严谨度偏好"绑架

我把 X 实验设为 C4 的**前置条件**（D7）。评审的反驳是对的：**即使人审带宽结论是负面的，系统仍然需要 `get_capture` / `list_captures` 来支持观察、调试和收件箱**。这两个只读操作的价值不依赖于方法论假设是否成立。

而且这里有一个**我完全没想到、但评审点破了的关键依赖**：

> 人审实验本身需要读回捕获内容——没有 C4，dogfood 闭环根本跑不起来。

所以正确关系不是"X 阻塞 C4"，而是"**C4 是 X 的前置**"。我把依赖方向搞反了。X 真正应该阻塞的是：SOP-001 正式重构、新 SOP-002、审核 UI 工作流定型、自动路由方案——**这四个评审列得很准**。

# 四、我必须记功：评审补上了我的一个真实空白

`docs/capture-envelope-v1-*.md:720-721` 把追加事务写成两步：

```
6. 回读校验后原子提交到新版本目录。
7. 追加 `capture.version-appended` 事件。
```

即**版本目录的提交与 Event 的写入是两个步骤**。而 `:865` 又要求 `saved: true` 必然对应一个可读取、可解析、哈希通过的不可变版本目录。

我在评估中写了"版本链 + `expected_current_version` 乐观并发；`RequestFingerprint` 已为它预留字段（`models.py:291-323`），设计成本低"——**这恰恰是把最关键的语义问题当成"设计成本低"给放过了**。
