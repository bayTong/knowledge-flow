### 我逐行核对的关键实现点

**1. "错误前零输出"是真正落实的，不是声称的**

`_run_get_capture`（`operations.py:2294-2393`）的顺序是：

```
定位 Item → 加载并验证完整版本链 → 确定目标版本
→ 创建 Store 外 spool → _verify_target_payloads(全部载荷写入 spool 并校验)
→ 构造结果（含 metadata）
→ 【只有到这里】_emit_verified_body(spool → sink)
```

这精确实现了 C-028 的裁决。任何完整性失败都发生在 `sink` 收到第一个字节之前。

**2. sink 契约的细节实现得很严谨**（`_emit_verified_body:1477-1503`）

- 从 spool 按 `DEFAULT_CHUNK_SIZE` 读取，每次写入最多一个块；
- 处理**短写**：内层循环消费未写完的后缀（`written <= len(chunk) - offset`）；
- 返回值必须是 `int` 且落在 `1..len(chunk)-offset`——`0`、`None`、`bool`、越界值一律判失败；
- 任何异常捕获后返回 `False` → `OUTPUT_WRITE_FAILED`（retryable）；
- **核心不 close、不 flush 调用方的 sink**——C4V 测试用 `_DigestSink` 的 `close_calls == 0` / `flush_calls == 0` 断言了这一点。

**3. 版本链识别做了真正的完整校验**（`_load_disk_capture_version_chain:1037-1125`）

- `versions/` 每个目录名必须是六位十进制（`_parse_capture_version_directory_name`）；
- 重名版本 → `EVENT_REFERENCE_MISMATCH`；
- `events/` 每个文件名必须 `evt_` UUIDv7 且 `.yaml`，且 `event_id` 必须等于文件名 stem；
- 空 events → `EVENT_MISSING`；
- 版本 1 的 `received_at` 的 `YYYY/MM` 必须与 Item 分片一致；
- 对每个已提交版本调用 `_payload_files` 校验结构与路径。

**4. "未知 schema"与"已知非法"被正确区分**（`_machine_identity_is_unsupported`，`:699-731`）

`schema_version != 1` 或 schema 名不符 → `_UnsupportedMachineSchema` → `UNSUPPORTED_STORE_VERSION`；而不是被误判成损坏。这正是 C4-0 契约第 6 条要求的区分。

**5. 光标与过滤语义正确**

`_run_list_captures:2429-2481`：严格 `>` / `<` 时间边界（对应契约"严格排除"）、游标比较用 `candidate.sort_key < (last_captured_at, last_capture_id)`、`captured_at DESC, capture_id DESC`、只在还有剩余时才发 `next_cursor`。

**6. 预览是"精确 160 code point 且不伪称完整证明"**

`_CAPTURE_PREVIEW_CODE_POINTS = 160`、`_CAPTURE_PREVIEW_MAXIMUM_BYTES = 160 * 4`，只读当前主正文最多 640 字节——与 C-029 一致。

## 三、C4V 验收质量：本轮最值得肯定的部分

`test_read_acceptance.py` 的两项验收测试，我用真实 4 MiB / 64 MiB 数据核对过断言内容：

### `test_c4v_real_4_and_64_mib_public_write_list_get_round_trip`

端到端跑通 **`capture_text → list_captures → get_capture`** 三个公开操作，并断言：

- 输入流被**有界**读取：`maximum_read <= DEFAULT_CHUNK_SIZE`（1 MiB）、只读一次 EOF；
- 列表项 `preview == "x" * 160`（精确 160 code point）；
- `get_capture` 返回的 `primary_payload_sha256` / `payload_set_sha256` / `envelope_sha256` **与写入回执逐字段相等**；
- `_DigestSink` 收到的字节数与哈希**等于原写入回执的哈希**——这是"写入→读取"字节级闭环的证明；
- sink 的 `maximum_write <= 1 MiB`、`close_calls == 0`、`flush_calls == 0`；
- 用同一幂等 key 重试 4 MiB，`_STABLE_RECEIPT_FIELDS` **逐字段不变**。

**这是整个项目至今最强的一条证据链**：真实 64 MiB、真实三个公开操作、哈希与字节双向锚定、sink 契约与幂等稳定性同时被验证。

### `test_c4v_static_pages_and_controlled_creation_use_keyset_boundaries`

验证静态数据集多页遍历**无重复无遗漏**，且页间受控新增严格按 keyset 边界可见、从空游标重启得到新鲜视图——正是 C-030 冻结的"仅对静态数据集保证"承诺的正面验证。

### 一个我特别指出的闭合项

`test_get_15_reparse_item_is_never_followed` —— **这关闭了我在最初全面评估中列为 R4 的安全缺口**（"所有 `_is_reparse_point` 守卫均 False-only，无测试创建真实 symlink/junction，安全防线从未被证明有效"）。现在 reparse 防御有了行为验证。

## 七、总体判断

**这轮进展是实质性的，而且是项目性质的转变。**

C4 的四个批次完成了两件事：

1. **技术上**：捕获内核第一次成为完整的读写库。"存进去的东西能被验证地读出来"——这是任何知识管理系统的底线能力，此前三个月的工作都在为它铺路。
2. **证据上**：C4V 用真实 4 MiB / 64 MiB 数据把 `capture_text → list_captures → get_capture` 的**哈希与字节双向锚定**，这比任何单项测试都更有说服力。

同时，C5-0 的八条冲突显示团队已经学会了**在编码前识别机制复用陷阱**——C-038（尾部续封归属）和 C-042（staging 类型复用）都是那种"不提前冻结就会静默损坏数据"的问题。

**但仍要如实指出**：项目至今**没有任何终端用户可用的东西**。三个操作都是库 API，需要 `config_path` 与 `PathPolicy`；没有 CLI、没有生产 Store、没有收件箱界面。产品可用性我只从 1/10 调到 2/10，因为"能通过 Python 调用"与"能被人使用"之间还差 C7 那道门。

**建议的下一步（按优先级）：**

| 优先级 | 动作 | 理由 |
|---|---|---|
| **1** | **提交 C5-0**（独立文档提交） | 契约内容与验证已完成；带着未提交契约进 C5A 会混淆问题归属 |
| **2** | **授权 C5A**（append staging + 预封存 Event + 冲突检查） | 权威门禁；C-035–C-042 已把风险前置消化 |
