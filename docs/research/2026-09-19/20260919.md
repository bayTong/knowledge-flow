A:不是“整个需求不成立”，而是报告在警告：**项目目前把一个合理目标写成了过强、尚不可验证的保证。**

更准确地说：

> “减少 LLM 的静默遗漏、让结果可追溯和可人工审查”是合理且可行的；  
> “人类不需要懂领域，只凭策展地图和覆盖报告，就能验证 LLM 已提取一切”目前既未被实现，也很难作为绝对保证成立。

## 一、“立论失败”具体指什么

报告所说的“立论”不是 Capture Store 能不能写入、崩溃恢复能不能工作，而是 README 中这条因果链：

1. LLM 的遗漏比噪音更难发现；
2. 所以先让 LLM 穷举提取；
3. 生成带原文引用和覆盖报告的策展地图；
4. 人类通过审查策展地图，就能知道有没有遗漏；
5. 因而可以安全地批准后续知识入库。

前两三步是合理的。但 README 又进一步写道：

> “你只需要信任它确实提取了所有东西（可通过逐段覆盖率和原文引用验证）。”

见 [README-zh.md](C:/Users/94233/knowledge-flow/README-zh.md:47) 和 [README-zh.md](C:/Users/94233/knowledge-flow/README-zh.md:52)。

问题就在“验证它提取了所有东西”这一句。当前机制能证明的主要是：

- 已提取的条目有没有原文引用；
- 哪些原文章节完全没有提取项；
- 各节提取项数量是否明显失衡；
- 不同 LLM Pass 的结果是否出现明显分歧。

但它不能证明：

- 某一节中所有重要概念都已提取；
- 没有漏掉限定条件、反例、例外、否定表述；
- 没有把一个复杂论点压缩成一个过度简化的条目；
- LLM 确实对长文的每一部分进行了充分语义处理。

所以报告说的“第一种未来”是一个条件性风险：

> 如果项目以后只不断加固捕获内核，却一直把“策展地图能够验证无遗漏”当作已成立事实，那么工程可以成功，核心方法论承诺却仍然没有得到证明。

这不是说它现在已经失败，而是说它有可能成为“极其可靠地保存一个质量未知的提取结果”。

## 二、当前覆盖规则为什么支撑不了“提取了一切”

现有覆盖规则主要统计每个源文章节有多少提取项：

- 均值 = 总提取项数 ÷ 覆盖节数；
- 低于 `0.3 × 均值` 标为“偏低”；
- 完全没有提取项则可能标为“盲区”。

见 [extraction-interface.md](C:/Users/94233/knowledge-flow/prompts/extraction-interface.md:155) 和 [extraction-interface.md](C:/Users/94233/knowledge-flow/prompts/extraction-interface.md:178)。

假设有 20 节，总共提取了 60 项，平均每节 3 项：

```text
偏低阈值 = 3 × 0.3 = 0.9
```

由于提取项数是整数：

- 0 项会触发；
- 1 项不会触发；
- 2 项不会触发。

但某一节原本可能包含 20 个需要提取的事实，LLM 只提取了 1 个。此时已经漏掉 95%，覆盖规则却仍不会把它判为“偏低”。

此外，“数量正常”也不代表内容完整：

```text
原文包含：定义、限制条件、反例、适用范围
LLM 提取：4 条重复定义
```

数量看起来够了，但语义覆盖仍然可能很差。

所以密度规则适合作为异常提示器，却不适合作为完整性证明。

## 三、是不是需求本身不合理

应当分层判断。

| 层次 | 判断 |
|---|---|
| 发现并减少 LLM 静默遗漏 | 合理且有价值 |
| 在写入知识库前提供中间审查面 | 合理且可行 |
| 每个提取项绑定原文位置和版本 | 可行，而且很值得做 |
| 机械发现未处理、未读取的源文区段 | 可行 |
| 通过多个独立 Pass 降低遗漏概率 | 可行，但只能降低风险 |
| 对任意陌生长文保证“穷举所有语义” | 不适合作为绝对要求 |
| 让不懂领域的人在约 30 秒内验证“所有东西都提取了” | 当前不现实 |
| 用提取项数量证明语义完整性 | 设计依据不足 |

因此，**底层需求是成立的，绝对化的需求表达不成立。**

真正需要修改的不是“策展地图”这个方向，而是把：

> 验证 LLM 提取了一切

改成：

> 使所有输入区段都有可核查的处理记录，使每个提取结果都能追溯到源文，并通过独立检查和实证评测显著降低静默遗漏风险。

后一种承诺是可实现、可测试、也更诚实的。

## 四、这份报告说得准确的地方

关于“立论风险”，报告方向上是准确的：

1. 当前方法论仍是 Draft。

   权威登记本身已经明确写着“策展地图内部格式和覆盖审计方法：Draft，待重构”，见[设计权威与冲突登记](C:/Users/94233/knowledge-flow/docs/design-authority-and-conflict-register-设计权威与冲突登记.md:73)。因此这不是已完成、已验证的方法论。

2. 目前缺少机器可校验的策展地图契约。

   还没有解析器、schema validator、golden fixture 和 CI 能证明策展地图结构符合预期。

3. 缺少实际效果验证。

   目前没有一组人工标注的基准材料，用来测量：

   - 召回率；
   - 遗漏率；
   - 误提取率；
   - 人工审查耗时；
   - 策展地图相对“直接让 LLM 建知识页面”到底改善了多少。

4. 长文读取本身没有确定性记账。

   把完整长文放进提示词，不等于可以证明模型充分处理了所有部分。

5. “源文引用”只能验证已提取项。

   它可以证明“这条内容来自哪里”，却无法自动显示“还有哪条内容根本没被提取”。

## 五、报告说得过重的地方

报告的结论也有几处需要降级理解。

### 1. “项目立论失败”这个范围过大

即使策展方法论最终效果不好，Capture Store 仍然具有独立价值：

- 本地优先捕获；
- 不可变版本；
- 哈希校验；
- 幂等写入；
- 崩溃恢复；
- 可审计历史。

所以更准确的说法是：

> KnowledgeFlow 关于“策展地图可以验证穷举提取”的强主张可能失败。

而不是整个项目、全部工程和所有需求都会失败。

### 2. “覆盖报告都是被审计方自己生成”并不完全准确

Mode A 的提取 Agent 和 auditor 是分开的，不是同一次调用；Mode A-fast 才是明确的自检。

但即使分成两个调用，它们可能仍使用：

- 同一模型；
- 同一提示设计；
- 相似注意力偏差；
- 同一不完整的覆盖指标。

所以“完全是自我审计”说得过重，但“独立性还不足以构成完整性证明”仍然成立。

### 3. 确定性分段也不是完整答案

报告提出：

> 确定性分段 + 覆盖记账，就能让覆盖报告成为 join 输出。

这非常有价值，但它只能证明：

- 所有区段都被投递过；
- 所有区段都有处理结果；
- 没有区段完全失踪。

它仍然不能证明每个区段里的所有语义都被正确提取。因此还必须增加人工 gold set 和实证评测。

换句话说：

```text
确定性分段
    解决“有没有处理这一段”

源位置绑定
    解决“这条结果来自哪里”

独立复核
    降低共同遗漏概率

人工标注基准
    测量到底漏了多少

上述全部加起来
    仍然是风险降低与可审查，不是数学意义上的零遗漏证明
```

## 六、项目应该怎样修正立论

建议把核心承诺改成四层，并分别验收。

### 第一层：输入完整性

机械保证：

- 源文被稳定分段；
- 每个分段都有稳定 ID、范围和哈希；
- 每段状态必须是已处理、明确跳过或处理失败；
- 不允许无状态区段。

这一层可以做到接近 100% 确定。

### 第二层：输出可追溯性

机械保证：

- 每个实体、关系、主张都绑定一个或多个源文区段；
- 最好进一步绑定字符或字节范围；
- 引用必须能回读并校验；
- 不允许没有来源的事实项混入。

这一层也可以严格实现。

### 第三层：遗漏风险检测

只能做风险检测，不能声称绝对完整：

- 独立模型复核；
- 不同提取策略交叉；
- 区段级结果差异；
- 低密度、异常密度；
- 未处理段、失败段；
- 反例、限制条件、否定表述等专门检查器。

### 第四层：实证质量

建立人工标注基准，测量：

- 实体召回率；
- 关系召回率；
- 主张召回率；
- 限定条件和反例召回率；
- 引用正确率；
- 噪音率；
- 人工审查时间；
- 与“直接 LLM 策展”基线相比的改善程度。

只有这一层的数据，才能判断核心方法论是否真的有效。

## 七、这对当前路线意味着什么

不需要因此推翻 C7、C8。

合理顺序仍然是：

1. 以严格范围完成 C7 机器适配器；
2. 完成 C8，把捕获 MVP 正式闭合；
3. 不继续无限加固内核，也不立刻建设完整 UI、GBrain 或生产知识库；
4. 增加一个独立的“方法论可行性验证阶段”；
5. 先做最小策展地图 schema、分段台账、解析器和基准实验；
6. 根据实验结果决定：
   - 保留原立论；
   - 降级为“降低遗漏风险”；
   - 修改覆盖机制；
   - 或重新定义产品重点。

第一种未来不是必然结果。它只会在项目**把尚未验证的强主张长期当作既定事实，同时持续把绝大部分资源投向捕获内核**时发生。

我的综合判断是：**需求动机合理，架构方向也有价值；当前不合理的是“已经能够验证提取了一切”这一绝对表述。它需要被改成可操作、可度量、可证伪的质量目标。**

## 一、方向应该怎样调整

### 1. 从“穷举一切”改成“绝不静默丢弃”

当前 C5 的表述是“不按重要性过滤、穷举提取”。这个目标在大文本中会导致：

- token 成本随全文体量增长；
- 策展地图可能和原文一样难读；
- 人工审核成为新的瓶颈；
- 提取很多用户永远不会使用的低价值知识；
- 即便全部提取，也不等于帮助用户快速理解。

建议把原则改成：

> 系统可以延迟提取、按需提取、分层提取，但不能在没有记录的情况下静默跳过内容。

也就是允许每个源文区段具有以下状态：

- 已索引，尚未语义提取；
- 已生成概要；
- 已进行详细提取；
- 已人工审核；
- 明确忽略；
- 处理失败，等待重试。

这样不再要求第一次就把所有语义展开，却仍然可以知道哪些部分没有被深度处理。

### 2. 把策展地图从“完整中间产品”改成“分辨率可变的审查视图”

策展地图不应永远是一份巨大的十节 Markdown，而应有至少三层分辨率。

#### 文档级地图

用于几分钟内理解整份材料：

- 这是什么；
- 主要章节；
- 核心主题；
- 关键结论；
- 争议和不确定性；
- 哪些部分值得继续展开；
- 哪些部分尚未深度处理。

#### 章节级地图

用户点击某个章节或主题后再生成：

- 本节概念；
- 主张；
- 实体关系；
- 例外和限制；
- 原文引用；
- 与其他章节的联系。

#### 条目级提案

只有准备写入正式知识库时才生成：

- 精确实体；
- 精确关系；
- 精确主张；
- 合并目标；
- 冲突处理；
- 来源版本；
- 待批准变更。

这会把“审查整份巨大策展地图”变成“先看总图，再展开热点，最后只批准具体变更”。

### 3. 人工审核从“审核所有条目”改成“审核决策与异常”

人类不应该逐条审核数千个低风险提取项。更适合人工审核的是：

- 新概念是否值得进入长期知识库；
- 两个实体是否应合并；
- 两条主张是否冲突；
- 推测是否可以升级为事实；
- 是否建立跨文档关系；
- 是否覆盖或废弃既有知识；
- 高价值但低置信度的内容；
- 系统无法确定如何路由的内容。

简单、重复、有明确来源的低风险候选可以保持在“未审核候选层”，无需立即打扰用户。

### 4. 把“覆盖率”拆成三种，不再混为一谈

今后不应只使用一个“覆盖率”。

#### 输入处理覆盖率

可以机械保证：

```text
已记账区段数 / 源文总区段数
```

目标可以是 100%。

#### 引用覆盖率

可以机械验证：

```text
有合法来源定位的知识候选数 / 全部知识候选数
```

正式候选应要求 100%。

#### 语义召回率

这是“重要知识漏了多少”，只能通过人工标注样本和实验估计，不能从条目数量直接推导。

这三项分开后，项目的承诺会清晰很多：

- 100% 处理记账；
- 100% 来源可追溯；
- 语义召回率通过评测不断提高，但不承诺绝对无遗漏。

### 5. 把知识分成四层状态

建议长期架构采用：

```text
不可变原料
Capture + Version
        │
        ▼
可重建检索层
分段、关键词索引、向量索引、结构索引
        │
        ▼
未审核候选层
实体、关系、主张、摘要、问答中发现的联系
        │
        ▼
已策展知识层
用户批准的实体、关系、页面和规则
```

必须保持：

- Capture 是事实源；
- RAG 索引是可删除、可重建的派生物；
- 动态知识图谱首先是候选物，不是事实；
- 只有经证据核查和批准的内容才进入正式知识层。

这和项目当前“不可变事实与派生投影分离”的思想非常一致。

### 6. 把 token、审核时间和复用价值变成正式路由条件

不要只按文本 token 数决定路径，还要考虑：

- 内容是否结构化；
- 信息密度；
- 是否高风险；
- 是否会反复使用；
- 用户当前有没有明确问题；
- 文档更新频率；
- 是否需要跨全文理解；
- 完整策展地图预计需要多少人工审核时间。

最实用的判据不是“超过多少 token”，而是：

> 生成的策展地图是否仍能在可接受时间内被人完整审查？

可以先以审核预算做实验性分层：

- 预计 10–15 分钟内可审完：完整策展地图；
- 预计 15–45 分钟：分层地图，只审核概要和异常；
- 预计超过 45 分钟或内容持续增长：RAG 优先、按需策展。

这些不是最终硬阈值，应通过实际使用数据校准。

## 二、中小内容继续策展，大内容走 RAG 是否合理

结论是：**合理，但应该做成三条路径，而不是二选一。**

| 路径 | 适用情况 | 首次处理 | 后续处理 |
|---|---|---|---|
| A：完整策展 | 小体量、高价值、容易完整审查 | 生成完整策展地图 | 人工批准后入库 |
| B：分层策展 | 中等体量、结构清楚、需要整体理解 | 生成文档级地图和章节目录 | 按需展开章节地图 |
| C：检索优先 | 大体量、持续增长、用户需求尚不明确 | 分段、索引、建立处理台账 | 查询时提取候选知识 |

这三条路径可以共享同一个 Capture Store 和来源身份。

## 三、大文本不能只是“普通 RAG”

你的“直接走 RAG”方向是对的，但普通向量 RAG 有一个明显限制：它擅长回答局部问题，却不擅长“整本书主要有哪些主题”“多份材料的共同趋势是什么”之类的全局问题。

Microsoft 的 GraphRAG 研究也把这一点作为出发点：常规 RAG 对局部事实查询有效，但面对需要跨整个语料进行综合的全局问题时表现较弱；GraphRAG 通过实体关系图和社区摘要解决全局理解问题。[Microsoft GraphRAG 论文](https://www.microsoft.com/en-us/research/publication/from-local-to-global-a-graph-rag-approach-to-query-focused-summarization/)

但完整 GraphRAG 同样有你担心的成本问题。其官方文档估算，图谱提取大约占标准索引成本的 75%，更便宜的快速模式则会得到更嘈杂、较不适合独立使用的图。[GraphRAG 索引方法](https://microsoft.github.io/graphrag/index/methods/)

所以大文本更适合：

> 低成本索引优先 + 查询时深化 + 逐步沉淀知识

而不是一开始就对全文执行昂贵的实体、关系、主张和社区摘要提取。

Microsoft 后续提出的 LazyGraphRAG 也是类似方向：索引阶段尽量减少 LLM 使用，把昂贵推理推迟到查询时。其公开结果表明这种方式可以大幅降低预处理成本，不过这些具体倍数属于其特定数据与实验条件，不能直接当作本项目承诺。[Microsoft LazyGraphRAG](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)

## 四、动态知识图谱应该怎样建立

你提出“根据 RAG 问答动态建立知识图谱”，我基本赞同，但有一个关键修正：

> 不应从最终问答文本直接建立正式图谱，而应从问答所使用的原文证据中生成候选图谱。

正确流程应是：

```text
用户问题
  ↓
RAG 检索相关区段
  ↓
构造带来源的证据包
  ↓
根据证据提取实体、关系、主张
  ↓
写入候选图谱
  ↓
合并、冲突检测、重复验证
  ↓
满足条件后人工批准
  ↓
进入正式策展知识图谱
```

不能这样做：

```text
用户问题 → LLM 最终回答 → 直接把回答写成知识图谱
```

因为最终回答已经包含模型的：

- 压缩；
- 推断；
- 遗漏；
- 表述重组；
- 潜在幻觉。

动态候选图谱中的每个节点和边都应保存：

- 来源 `capture_id`；
- 精确版本；
- segment ID；
- 原文范围；
- 来源哈希；
- 提取器版本；
- 提取时间；
- 触发它的查询；
- 置信度；
- 支持它的来源数量；
- 是否存在冲突证据；
- 当前状态：候选、已佐证、已批准、已废弃。

## 五、仅依赖问答动态建图也有风险

如果图谱完全根据用户问过的问题建立，会出现“查询偏置”：

- 用户没问过的领域永远不会进入图谱；
- 早期问题会塑造图谱结构；
- 高频兴趣可能被过度建模；
- 重要但用户尚不知道要问的知识不会出现；
- 同一个概念可能在不同问答中重复创建；
- 全局主题和跨文档关系可能长期缺失。

因此大文本仍需一个非常轻量的预处理底座：

1. 确定性分段；
2. 标题和层级结构；
3. 每段哈希与处理状态；
4. 关键词/BM25 索引；
5. 向量索引；
6. 可选的低成本实体共现索引；
7. 文档级或章节级粗粒度导航摘要。

这不是完整策展，也不要求用户审核全部内容，但可以避免知识系统完全被历史提问塑造。

对于长文的多层理解，也可以参考 RAPTOR 这种“原始片段 + 多层摘要树”的思想：查询时可以同时检索细节和高层摘要，不必只在扁平 chunk 中搜索。[RAPTOR（ICLR 2024）](https://openreview.net/pdf?id=GN921JHCRw)

## 六、建议形成的最终产品形态

我建议把 KnowledgeFlow 重新定义为：

> 一个渐进式知识提炼系统，而不是一次性全量知识提取器。

它的核心流程可以变成：

```text
捕获
  ↓
可靠保存原料及版本
  ↓
确定性分段与低成本索引
  ↓
┌──────────────────┬──────────────────┬──────────────────┐
│ 小内容           │ 中等内容         │ 大内容           │
│ 完整策展地图     │ 分层策展地图     │ RAG 优先         │
│ 一次审核         │ 按章节展开       │ 查询时深化       │
└──────────────────┴──────────────────┴──────────────────┘
  ↓
统一形成带来源的知识候选
  ↓
按价值、冲突、复用频率和风险进入审核队列
  ↓
已批准知识库 / 知识图谱
```

策展地图在这里没有被放弃，而是改变了角色：

- 小内容：完整审查载体；
- 中等内容：渐进式导航与审核载体；
- 大内容：针对某个主题、问题或知识变更动态生成的审核包。

## 二、新规范应冻结哪些内容

建议新规范至少包含以下章节。

### 1. 修正后的问题定义

增加“策展成本三角”：

```text
语义覆盖程度
审核摩擦
计算/token 成本
```

三者不可能在任意规模下同时最大化。系统目标不是假装消除矛盾，而是：

- 保存全部原料；
- 对全部源文区段进行处理记账；
- 按价值和需要逐步增加理解深度；
- 把语义提升控制在可追溯、可批准的边界内。

### 2. 明确哪些是确定性保证

可以作为硬要求：

- 原始 Capture 和版本不可丢失；
- 每个源文区段都有稳定身份和处理状态；
- 未处理、失败和延迟处理必须显式可见；
- 每个知识候选必须绑定来源版本和证据；
- 未审核候选不能冒充可信知识；
- 索引、摘要和候选图谱可删除、可重建；
- 最终语义写入必须绑定精确批准对象。

### 3. 明确哪些只是质量目标

不能再写成硬保证：

- 语义零遗漏；
- “提取了一切”；
- 覆盖报告能证明完整性；
- 不懂领域的人可以在几十秒内完成全面审核；
- 多 Pass 一定比单 Pass 完整；
- 知识图谱自动生成后天然可信。

这些只能通过评测测量，不作为绝对承诺。

### 4. 三种处理 Profile

建议新增派生概念 `processing_profile`：

- `full-map`：完整策展地图；
- `hierarchical-map`：文档级地图 + 按需章节地图；
- `retrieval-first`：先索引，查询时生成证据包和局部策展提案。

注意：它不能直接替换现有 Capture v1 的 `processing_mode`。

当前源码和 Envelope 已冻结：

```text
capture-only
raw-source
deep-curation
```

其中 `deep-curation` 应重新解释为：

> 用户授权内容进入较深语义处理，但不预先承诺一定生成全量策展地图；后续由处理路由器选择 full-map、hierarchical-map 或 retrieval-first。

这样不需要修改已经哈希绑定的 Envelope schema、golden fixture 和 C0–C6 代码。

### 5. 多分辨率策展地图

规范三种产物：

- 文档级概览；
- 章节/主题级地图；
- 准备入库的精确条目级提案。

同时规定：

- 不要求大文本一次生成完整十节大地图；
- RAG 查询可以触发局部策展地图；
- 局部地图必须声明只覆盖哪些 source segments；
- 多个局部地图可以合并，但合并本身仍是派生产物。

### 6. 三种“覆盖率”

正式拆开：

1. **处理记账覆盖率**：有处理状态的区段数 / 总区段数；
2. **证据绑定覆盖率**：有合法来源引用的候选数 / 总候选数；
3. **语义召回率**：相对人工 gold set 实际提取出的知识比例。

前两项可以成为机械门禁，第三项只能通过实验估算。

### 7. 检索和动态图谱边界

冻结以下原则：

- RAG 检索结果是证据候选，不是可信知识；
- 知识图谱候选必须从检索到的原文证据中提取；
- 不得仅根据最终问答文本直接创建正式图谱节点；
- 动态图谱初始状态为 `candidate`；
- 建议状态至少有：
  - `candidate`
  - `corroborated`
  - `approved`
  - `superseded`
- 用户没问过的内容可能永远不会进入动态图谱，必须把这种“查询偏置”记录为能力边界；
- 可通过周期性粗粒度扫描补充全局主题，但不得宣称消除全部遗漏。

### 8. 路由因素

不得再只以字数判断。

建议使用：

- 内容规模；
- 章节结构；
- 语义密度；
- 风险等级；
- 预计审核时间；
- 预计复用频率；
- 用户是否已有明确问题；
- 内容更新频率；
- 是否需要跨全文综合。

字数只能作为初筛信号，不能成为唯一决策依据。
