# 2026-10-10 完整需求、处理线路与价值实验方向复核

> 状态：Historical Research Input（非权威）<br>
> 形成时点：P0C-UX0 已完成契约收口、EVIDENCE-0 仍为未提交评审候选<br>
> 使用边界：本文保存当时对产品需求、BitLocker、三类处理线路和后续顺序的分析，不是当前项目状态、执行授权或正式实验协议；可采纳结论必须由主 PRD、设计权威、项目状态及获批实验协议承接

先给结论：

- BitLocker 只是 Windows 的磁盘静态加密能力，不是 KnowledgeFlow 的核心技术，也不应成为跨平台前置。
- 项目的总体需求方向没有错，但当前 `EVIDENCE-0` 候选过度突出检索，确实需要修正。
- 你理解的“低摩擦内容定时整理”和“高价值材料深入策展”应当并存，但不是两套完全独立系统，而是“共同底座 + 多条并行处理线路”。
- “AI 可以定时直接写”必须进一步区分：可以自动写入未审核工作层/提案层，不能默认直接写入可信 Wiki。

## 一、BitLocker 是什么

BitLocker 是 Windows 自带的磁盘加密功能。

它加密的通常是整个磁盘分区：

```text
硬盘上的原始数据
→ BitLocker 加密
→ 没有解锁密钥时无法直接读取
```

适合防范：

- 电脑或硬盘丢失；
- 别人把硬盘拆下来读取；
- 未登录系统时离线访问磁盘；
- 设备报废后残留数据被恢复。

它不能防范：

- 用户已经登录、磁盘已经解锁后，恶意软件读取文件；
- 当前用户账号本身被攻破；
- 应用错误地把正文写入日志；
- 明文备份被复制出去；
- KnowledgeFlow 自身权限或删除功能设计错误。

它也不是：

- 数据库；
- 单个文件的业务级加密；
- 用户权限管理系统；
- 跨平台标准。

其他平台有类似能力：

- Linux：LUKS/dm-crypt；
- macOS：FileVault；
- Windows：BitLocker。

因此 KnowledgeFlow 应当规定的是：

> 正式私人或高敏感环境需要经过验证的静态数据保护。

至于由 BitLocker、LUKS、FileVault 还是其他方式实现，应属于平台部署 Profile，不写死进核心格式和业务逻辑。

当前低敏感度 Pilot 不需要为了 BitLocker 停下价值验证。

# 二、重新梳理 KnowledgeFlow 的完整需求

当前产品的真正目标不是“文件捕获工具”，也不是“自动生成 Wiki”，而是：

> 把零散材料、长篇资料、问题、研究任务和已有知识库，逐步转化为有证据、可使用、可审核、可维护的个人知识。

完整产品可以分成八层能力。

## 1. 来源入口

用户可以从不同起点开始：

- 随手笔记、灵感；
- 对话内容；
- 长文章、论文、报告；
- URL、网页；
- PDF、Office 文档、附件；
- 音频及转写；
- 一组研究材料；
- 一个问题或研究主题；
- 已有知识库；
- API、QQ、GBrain 等外部入口。

当前实际实现的只有：

- 单机；
- 单用户；
- 文本；
- 本地收件箱和机器 CLI。

URL、PDF、音频和外部入口仍未实现。

## 2. 来源事实层 T0

所有需要保留的新材料首先进入可靠来源层：

```text
输入
→ Capture Item
→ 不可变版本
→ 正文哈希
→ Envelope / Event
→ 可回读、可追加、可恢复
```

这一层已经基本实现，包括：

- 文本捕获；
- 列表和读取；
- 追加版本；
- 幂等与并发处理；
- 备份和新目标恢复；
- 最小 Tk 收件箱；
- 低敏感度 Pilot 验收。

T0 只证明：

> “这段原始材料被可靠保存了。”

不证明：

- 内容正确；
- 已经理解；
- 已经分类；
- 已经策展；
- 已经进入可信知识库。

## 3. 来源状态与处理授权

保存以后，系统需要区分三个问题：

1. 材料保存在哪里；
2. 是否允许对它进行语义处理；
3. 是否允许写入可信知识。

现有三个主要捕获意图是：

| 模式 | 含义 |
|---|---|
| `capture-only` | 先可靠保存，不自动深度处理 |
| `raw-source` | 作为正式原料保存，可以进入后续研究 |
| `deep-curation` | 用户明确允许进行深入语义处理 |

需要特别强调：

- `capture-only` 不等于永远不处理；
- 它只是没有自动授予深度处理权限；
- 用户以后可以批量选择；
- 也可以设置可见、范围明确、可撤销的自动规则。

例如：

> 每天晚上把当天的低敏感度随手笔记聚类并生成摘要候选。

这条规则可以授权定时处理，但结果只能先进入工作层或提案层。

详细边界目前位于[捕获与路由规范](../../capture/capture-and-routing-spec-捕获与路由规范.md)和[主 PRD 的处理授权](../../requirements-and-governance-baseline-需求与治理基线.md)。

## 4. 共同的派生处理底座

无论后面走策展还是检索，都需要一个共同底座：

```text
精确 Capture 版本
→ 确定性分段
→ 处理范围记录
→ 证据定位
→ 可回读原文
```

它需要解决：

- 当前处理的是哪个 Capture、哪个版本；
- 原文被拆成哪些 Segment；
- 哪些部分已经处理；
- 哪些部分未处理、失败或延期；
- 摘要、主张和回答引用了哪里；
- 派生结果删除后能否从原件重建。

这层目前尚未实现。

## 5. 工作知识层 T1

T1 是“立即有用但尚未获得可信身份”的内容，例如：

- 来源卡片；
- 索引；
- 摘要；
- 文档提纲；
- 策展地图；
- 查询结果；
- Evidence Bundle；
- 学习路径；
- 临时集合；
- 候选标签；
- 候选概念和关系；
- 问答结果。

这些内容可以重算、修改或删除，不得覆盖 T0 原文。

## 6. 提案隔离层 T2

当系统准备进行更稳定的组织或知识变化时，必须形成提案：

- 路由提案；
- 策展地图；
- 页面候选；
- 概念、主张、关系候选；
- Wiki 变更 diff；
- Schema、Taxonomy、Ontology 变化；
- 合并、拆分、废弃或重命名建议。

每个提案必须包含：

- 精确来源；
- 证据；
- 处理范围；
- 已知缺口；
- 模型和提示词信息；
- 拟产生的具体变化；
- 风险和回滚边界。

## 7. 可信知识层 T3

只有用户批准的内容才能进入可信层，例如：

- 正式 Wiki 页面；
- 获批概念和主张；
- 稳定关系；
- Taxonomy/Ontology；
- 已批准的维护变更；
- 批准记录和回滚检查点。

完整写入过程应当是：

```text
提案
→ 人工查看证据
→ 修改/接受/拒绝
→ 冻结精确 diff
→ 用户批准
→ 受限执行器写入
→ 回读验证
→ 形成版本和回滚点
```

这一部分尚未实现，SOP-000B 和新版 SOP-002 仍待设计。

## 8. 持续治理与维护

产品最终还要支持：

- 查找重复内容；
- 发现冲突；
- 识别过时信息；
- 检查断链；
- 比较新材料与已有知识；
- 页面合并、拆分、重命名；
- 结构迁移；
- 可信变更回滚；
- 来源更新后的派生物重建。

# 三、不同内容应走什么处理链路

## 1. 随手笔记、灵感、短对话

```text
快速捕获
→ T0 原文
→ Global Intake
→ capture-only
→ 等待批量处理或用户后续触发
```

允许的后续自动化：

- 每日/每周摘要；
- 相似笔记聚类；
- 重复项提示；
- 待办或主题候选；
- promotion proposal；
- 建议归入某个任务或知识空间。

技术候选：

- 当前 Capture Store；
- 后续本地任务队列/调度器；
- 可选模型摘要和聚类；
- 结果写入 T1/T2，不直接写可信 Wiki。

## 2. 大量低摩擦内容的定时整理

```text
多条 capture-only
→ 命中用户配置的定时规则
→ 批量读取指定范围
→ 轻量摘要/聚类/相似项发现
→ 生成每日或每周工作知识
→ 用户批量保留、忽略、延期或提升
```

这里可以使用 AI，但必须满足：

- 规则由用户明确开启；
- 可看到处理范围；
- 可以关闭或撤销；
- 有预算和隐私边界；
- 不把历史授权扩展到所有内容；
- 不直接写可信 Wiki。

调度技术不应写死为 Windows 任务计划程序。未来可以采用：

- 应用内部任务队列；
- 应用启动时补跑；
- 可选的 Windows/Linux/macOS 调度适配器。

## 3. 一篇中长篇高质量材料

```text
原文捕获
→ raw-source
→ 用户选择 deep-curation
→ 确定性分段
→ 文档概览
→ 章节地图
→ 概念、主张、关系和争议
→ 策展地图
→ 每项绑定证据
→ 人工审核
→ 值得长期保存的部分形成 Wiki 提案
```

技术候选：

- Markdown/文本解析；
- 标题与段落分段；
- LLM 策展处理；
- 多轮或分层处理；
- Evidence Bundle；
- 覆盖范围和缺口记录；
- Markdown 策展地图；
- 后续提案 diff。

这里的核心不是“搜索”，而是帮助用户快速建立整体理解。

## 4. 论文、书籍章节、复杂报告

可以走更深入的策展路径：

```text
来源事实
→ 结构识别
→ 分章节处理
→ 文档级概览
→ 关键主张和证据
→ 方法、限制、冲突和未决问题
→ 与其他来源比较
→ 学习路径或策展地图
```

处理可以较慢、成本较高，因为用户已经明确选择深度研究。

## 5. 大型或持续增长语料

```text
大量来源
→ 每份来源形成 T0
→ 确定性分段
→ 本地全文/关键词索引
→ 可选 embedding
→ 查询时形成 Evidence Bundle
→ 有引用的回答或局部策展
→ 重复出现的高价值内容形成候选
```

技术可以逐级增加：

1. 精确查找；
2. 本地关键词/BM25；
3. embedding；
4. 语义检索；
5. 重排序；
6. RAG；
7. 查询驱动候选关系或局部地图。

不能一开始就默认必须建设完整 RAG 平台。

## 6. URL、网页、PDF、附件和音频

这些能力尚未实现，但合理链路是：

```text
保存原始文件/URL/音频
→ 保存来源和哈希
→ 网页快照 / 文本提取 / OCR / 转写
→ 派生文本
→ 后续进入轻量、策展或检索路径
```

原文件始终是 T0，OCR、转写和网页正文都是可重建派生结果。

## 7. 用户直接询问已有来源

不需要再创建 Capture：

```text
已有 Capture/来源
→ 当前任务内读取或检索
→ Evidence Bundle
→ 回答
→ 任务结束
```

除非用户明确要求保存摘要、地图或研究结果，否则查询不应自动产生永久后台状态。

## 8. 已有可信知识库的维护

```text
新材料
+
已有可信 Wiki
→ 对齐和比较
→ 新增/重复/冲突/过时分析
→ 精确变更提案
→ 人工批准
→ 事务写入
→ 验证和回滚点
```

# 四、两条线是否应该并行

答案是：产品运行时应并行，但开发上应共享底座后分批闭环，不能建设两套重复系统。

更准确地说，不是两条，而是三条工作线路：

```text
                        ┌→ 线路 A：低摩擦批量整理
Capture + Evidence 底座 ├→ 线路 B：中长篇深度策展
                        └→ 线路 C：大体量检索优先
```

## 线路 A：低摩擦批量整理

特点：

- 高频；
- 单条价值可能不确定；
- 不应打断捕获；
- 适合每天/每周批处理；
- 输出摘要、聚类和候选；
- 人工批量决定。

## 线路 B：深入策展

特点：

- 用户明确选择；
- 材料价值较高；
- 允许更高模型和人工成本；
- 需要整体理解；
- 输出策展地图、争议、证据和学习路径。

## 线路 C：检索优先

特点：

- 材料很多；
- 问题可能尚不明确；
- 全部策展成本过高；
- 先建立可搜索和可引用能力；
- 根据实际查询逐步形成局部知识。

三条线路共同复用：

- Capture ID 和版本；
- Segment；
- 证据定位；
- 处理授权；
- 处理状态；
- 模型/提示词记录；
- 成本与失败记录；
- T1/T2/T3 信任边界。

## 什么能并行，什么不能并行

可以并行：

- 不同 Capture 的定时轻量整理；
- 用户正在执行的深度研究；
- 大型语料索引；
- 已有派生索引重建。

必须串行依赖：

```text
来源保存
→ 获得处理授权
→ 生成派生结果
→ 形成提案
→ 批准
→ 可信写入
```

不能为了并行而让 AI 绕过授权、证据或可信写入审批。

# 五、当前项目方向的准确判断

已完成的 Capture 内核和低摩擦收件箱是必要底座，没有走错。

但下一阶段如果只做关键词检索，会出现新的偏差：

- 没有验证中长篇策展地图；
- 没有验证用户是否更容易形成整体理解；
- 没有验证 AI 是否真的减少阅读和整理劳动；
- 容易让产品过早退化为本地搜索/RAG 工具。

因此建议把下一顺序调整为：

1. 修订当前 `EVIDENCE-0` 候选；
2. 冻结共同证据底座；
3. 优先完成一份真实中长篇高质量材料的策展地图实验；
4. 同时设计低摩擦内容的定时批量整理线路；
5. 再用精简多来源材料验证关键词检索；
6. 根据失败证据决定是否引入 embedding/RAG；
7. 策展结果有实际价值后，再设计可信 Wiki 写入、批准和回滚。

当前主 PRD 的产品方向基本支持这个结构，尤其是[核心用户旅程和工作知识需求](../../requirements-and-governance-baseline-需求与治理基线.md)。真正需要修正的是当前实验与实施顺序，而不是推翻整个需求体系。
