## 1. “形成精确来源版本”不只是计算 SHA256

SHA256 只是其中一个组成部分，可以理解为内容的“指纹”。

一份精确来源版本通常包括：

```text
capture_id          这份来源是谁
version             这是它的第几个版本
payload_sha256      正文内容指纹
envelope_sha256     来源记录和元数据指纹
来源路径/描述        从哪里取得
捕获时间             什么时候纳入
```

例如，同一份文件经过修改：

```text
cap_123 / v1 / SHA256=A
cap_123 / v2 / SHA256=B
```

系统以后就能准确说明：

> 这张策展地图依据的是 `cap_123` 的 `v1`，不是后来修改过的 `v2`。

### 为什么仅有 SHA256 不够

SHA256 只能回答：

> 两份字节是否相同？

它不能回答：

- 这份内容属于哪个来源；
- 它是第几个版本；
- 什么时间纳入；
- 哪张地图使用了它；
- 用户批准的是哪个版本；
- 同样内容在两个任务里分别是什么身份。

所以正确顺序是：

```text
保存精确正文
→ 分配 Capture ID 和版本号
→ 自动计算 SHA256
→ 保存来源和版本元数据
→ 后续地图、批准和写入都引用这个版本
```

用户不需要手动计算 SHA256，这应由系统自动完成。

对于当前本地 Markdown 文件，第一版还可以同时记录两个哈希：

- 原始文件字节的 SHA256：证明磁盘上的原文件；
- 导入 Capture Store 后正文的 SHA256：证明系统实际处理的文本。

如果导入时发生换行或编码转换，两者可能不同，但映射关系必须明确记录。

## 2. 三个权限的区别

最简单的理解是：

| 权限 | 决定什么 | 系统可以做什么 | 不能做什么 |
|---|---|---|---|
| 放进某个库 | 放在哪里 | 建立路由、显示在 KB Inbox、归档原料 | 不能自动深入分析或改 Wiki |
| 允许深度处理 | 可以怎样分析 | 调用模型、分段、摘要、生成策展地图和候选 | 不能把候选当成可信知识 |
| 批准写入可信知识 | 最终接受什么 | 按批准的正文和 diff 修改 Wiki/Schema/索引 | 不能超出批准范围重新发挥 |

### 第一层：放进某个库——组织权限

用户说：

> 把这份材料放进“大模型应用开发”库。

这说明了材料的归属，但没有说明是否要花费模型成本深入分析。

系统可以：

- 记录目标 KB；
- 把它显示在该 KB 的 Inbox；
- 将精确原料归档到 `raw/`；
- 保存来源、版本和哈希。

系统不应因此自动：

- 生成摘要；
- 提取实体和关系；
- 创建 Wiki 页面；
- 修改 Schema；
- 把材料变成可信知识。

它相当于把一本书放到某个书架上，并不等于已经阅读、整理和出版读书笔记。

### 第二层：允许深度处理——分析权限

用户说：

> 深入分析这份材料，生成策展地图。

这授权系统：

- 读取正文；
- 进行分段和语义分析；
- 调用模型；
- 生成概览、主题、主张、关系、争议和缺口；
- 产生页面和结构候选。

但这些结果仍属于工作成果或待审核提案。

系统不能因为用户允许分析，就直接修改可信 Wiki。

这相当于允许研究员读书、做笔记和准备编辑方案，但还没有授权出版社正式出版。

### 第三层：批准写入可信知识——变更权限

策展地图完成后，系统展示：

```text
准备新建：
- wiki/RAG.md
- wiki/Agent.md

准备修改：
- wiki/大模型应用架构.md

准备新增：
- 2 个标签
- 3 条页面关系

以下内容暂不写入：
- 尚未核实的性能数字
- 与目标 KB 无关的历史讨论
```

用户查看最终正文和 diff 后说：

> 确认按这个方案执行。

这才授权受限执行器真正修改可信知识库。

批准必须绑定：

- 具体目标 KB；
- 具体来源版本；
- 具体地图和方案版本；
- 具体文件；
- 具体最终正文或 diff。

批准之后，执行器也不能临时新增页面、改变正文或扩大 Schema。

### 一句话命令可以包含前两个权限

例如用户说：

> 深入整理这份文件并放到“大模型应用开发”库。

这已经包含：

- 路由授权；
- 深度处理授权。

系统不需要重复询问这两件事。

但这句话通常不能提前包含最终可信写入批准，因为此时用户还没有看到系统最终准备写入什么。系统仍应在生成最终变更方案后，进行一次写入确认。

## 3. “策展地图可以是最终成果”是什么意思

这里的“最终成果”是指：

> 这次用户任务可以在策展地图完成后成功结束，不强迫继续写入 Wiki。

它不是说策展地图已经变成可信知识。

### 策展地图解决的是“理解材料”

一张策展地图可以包含：

- 材料整体讲了什么；
- 章节和主题如何演进；
- 核心概念；
- 重要主张及原文证据；
- 前后矛盾或修正；
- 不确定内容；
- 尚未处理或没有覆盖的部分；
- 值得继续追问的问题；
- 可能的知识组织方式。

用户可能已经通过地图达成目的：

> 我只是想弄懂这份长文，现在已经理解了，不需要把它拆成几十个 Wiki 页面。

此时任务就可以结束。

### 哪些情况下适合只保留地图

例如：

- 只是一次性的研究材料；
- 还不确定是否值得长期维护；
- 内容与已有知识大量重复；
- 原料质量不够高；
- 存在很多未核实主张；
- 用户只想理解，不想组织知识库；
- 尚未决定应该归入哪个 KB；
- 当前没有时间审核正式 Wiki 变更。

系统应保留地图，并允许以后再继续：

```text
策展地图
→ 以后选择目标 KB
→ 重新检查目标 KB 当前状态
→ 生成精确变更方案
→ 用户批准
→ 写入可信知识
```

### 地图和可信知识的区别

| 策展地图 | 可信知识 |
|---|---|
| 针对一份或一组来源的理解成果 | 面向长期使用的稳定知识 |
| 可以包含候选、争议和未知 | 必须明确哪些内容被接受 |
| 可以暂时没有目标 KB | 必须属于明确的知识空间 |
| 不进入默认可信搜索 | 可以进入可信搜索 |
| 可以重算和继续修改 | 必须版本化、审计和可回滚 |
| 完成地图不需要批准写入 | 写入必须批准精确变更 |

因此，“策展地图可以是最终成果”真正表达的是：

> KnowledgeFlow 不要求每次阅读都制造 Wiki 页面。帮助用户理解材料，本身就是一项完整且有价值的产品任务。只有真正值得长期维护的内容，才继续晋升为可信知识。
