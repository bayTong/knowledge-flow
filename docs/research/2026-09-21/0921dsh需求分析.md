我不写文件，只给你我的理解。以下是我读完全部核心文档与源码后，对这个项目**到底在要求什么**的重构。

---

## 一、先纠正一个容易误判的地方

这个项目**不是**在要求"一个更好的知识管理工具"。

如果按知识管理工具去理解它，会得出"功能缺失严重、没有 CLI、没有 UI、检索也没有"的结论，然后误判它工程方向错了。但读遍它的治理红线后，我认为它真正在要求的是：

> **一条可审计的「原料 → 可信知识」提升管道。**
> 系统不负责组织你的知识，只负责**证明**每一段进入可信层的内容，来自哪个不可变版本、依据哪段原文证据、由谁在什么范围批准。

三个动词构成主干：**保存（preserve）→ 记账（account）→ 提升（promote）**。"组织"和"检索"被**刻意**留白或外包（GBrain 可选、RAG 属于派生层、图谱属于候选层）。

这个定位能解释一件看起来矛盾的事：**为什么一个"个人知识库"项目会把资源全部投在一个本地捕获内核上，做得异常精密，却没有 CLI、没有策展地图解析器。** 因为捕获内核是整个系统的**信任锚点**——如果它不可靠，"证据绑定"和"精确批准"就都是空话。其余部分可以晚做、可以用别的东西替代，这一块不能。

---

## 二、完整需求可以分成六层，每层的"确信等级"差别极大

这是我理解这个项目最关键的结构。它**不是**一张平铺的需求清单，而是六层确信度递减的东西：

**第 1 层：产品意图（已由用户确认，不可被工程反推）**
- 缓解"策展悖论"：高质量策展需要领域理解，但采用工具的人恰恰还不懂领域。
- 长期目标是**可外置、可审计、可持续演化的第二大脑**，不是 QQ 机器人、不是 Obsidian 复刻、不是 GBrain 前端。
- 明确非目标：不追求"全自动整理一切"。

**第 2 层：治理红线（P1–P9，最高约束力）**
这一层是项目的**宪法**，任何设计不得违反：
- 立即保存 ≠ 可信入库（P1）
- 语义计算可自动，**语义落库必须受控**（P2）
- 禁止自动黑盒策展写入（P3）——具体禁止 6 类行为
- 批准必须绑定**精确对象**，不是"方向同意"（P4）
- 机械操作可自动，但必须确定、幂等、可重建（P5）
- Markdown + Git 是规范真源（P6）
- 权限按状态授予，不一次性给整库写权限（P7）
- 允许延迟提取，**但不得静默丢弃**（P8）
- 检索和候选图谱 ≠ 可信知识（P9）

**第 3 层：领域流程需求（设计意图清晰，但多数未实现）**
- 捕获先于归属：可以不选 KB 就保存
- Global Intake 是**逻辑队列**，不是第二个知识库
- `proposals/` 是语义工件隔离区，与 `raw/` 分离
- KB 生命周期：`provisional` →（SOP-000B 人工激活）→ `active`
- 深度策展需要**两级审核**：策展地图审核 + 精确变更审核
- 最小状态链：`captured → routed → pending-curation → pending-approval → approved → applying → applied → verified`

**第 4 层：机器契约（已逐字节冻结，最硬）**
- Capture Envelope v1：稳定 ID、版本、四类哈希、Payload 清单、意图、投递请求
- 四个文本操作：`capture_text` / `get_capture` / `list_captures` / `append_capture_version`
- 边界：4 MiB 内联阈值、64 MiB 可配置上限，**超限不得截断、摘要或自动拆分**
- 三态提交语义：`committed` / `not-committed` / `unknown`
- 幂等键优先级、keyset 游标编码

**第 5 层：渐进式处理方向（Draft，明确未经实验验证）**
- 不承诺语义零遗漏
- 三类 Processing Profile：`full-map` / `hierarchical-map` / `retrieval-first`
- Source Segment / Source Ledger / Evidence Bundle
- 三种"覆盖率"必须分开：处理记账（可机械保证）、证据绑定（可机械保证）、语义召回（只能实证估计）

**第 6 层：尚不存在的需求（被正确地留白）**
- SOP-000B（KB 激活）——`Blocking Draft`，未定义
- 可信写入 / 精确批准 / 事务 / 回滚（新 SOP-002）——`Blocking Draft`，未定义
- 策展地图机器格式——`Draft，待重构`
- URL/文件/音频捕获、大小上限、敏感内容策略——未定案

**这六层混在一起放，是当前最大的理解障碍。** 任何人第一次读这个项目，都会把第 5、6 层当成第 2、4 层来理解，然后得出"承诺了但没做到"的结论。

## 三、我认为这个项目最核心、也最少被明确写出的需求

### 需求的核心其实是「压缩一个人工闸门的积压」

把 P1 + P2 + P3 放在一起看，会得到一个不常被点破的推论：

> 每一次**语义写入**都需要人批准；每一次**捕获**都不需要。
> 所以要让人工闸门可持续，系统必须让**绝大多数内容永远不走到需要批准的那一步**，同时让**必须批准的那部分尽可能少、尽可能有依据**。

我认为这是整个系统设计张力的真正来源，而它**从未被写成一条需求**。所有其他设计都是这条隐含需求的实现手段：

- **分层处理**（小内容全量地图、中内容分层、大内容检索优先）= 让审核成本随价值分配，而不是随体量线性增长
- **未审核候选层**（低风险重复候选留在候选层不打扰人）= 合法地不批准一部分内容
- **"审核决策与异常"而非"审核所有条目"**（K6）= 把人的注意力对准高影响、不可逆、冲突、低置信度
- **证据绑定**（K3）= 让每次批准是**核对**而不是**重新理解**，从而把单次审核时间压下来

**为什么我认为这是关键**：如果人工闸门成为瓶颈，项目会走向两种失败之一——要么用户放弃（回到"让 LLM 直接写"），要么闸门退化为形式（用户盲点"批准"）。**两种失败都会让 P2/P3 变成装饰。** 而当前需求文档里，没有吞吐量目标、没有积压管理、没有"审核疲劳"的度量要求（`20260919.md` §三-4 提过"审核预算"和"放弃率"，但只在 Draft 层的实验测量项里，不是需求）。

### 第二个隐含需求：系统的可信度必须等于它最弱的数据通路

项目对**写入**路径的要求极高（逐字节金标准、26 个真实崩溃注入点、证据式提交分类），但对**读取**路径和**外部输入**路径的要求低得多。

这是一个**不一致**，而不是设计选择。表现：

- 写入时对字符集、路径、reparse point 层层拒绝；但接收 `channel.external_ref` 这类自由文本时只校验长度
- 一条无法解析的 envelope 会让**整个 Store 不可列出**（我实测过）
- 策展地图——整个立论的载体——**零机器校验**：没有解析器、没有 schema、没有 fixture、没有 CI

如果"证据绑定"是核心承诺，那么**证据的载体本身必须可校验**。当前它不可校验。这是我理解的这个项目**最大的需求完整性缺口**，比缺 CLI 严重得多。

## 四、边界与不确定性：项目自己都不确定的东西

这一层很重要，因为它们是**要求项目保持开放**的部分，而不是需求缺陷：

| 项 | 状态 | 我的理解 |
|---|---|---|
| 每个 KB 是否独立 Git | 候选架构，非既定 | 文件里明确警告 SOP-000A 不得擅自创建嵌套 `.git/` |
| RAG / 向量 / 图谱 | **明确不授权实现** | 必须先用真实材料做方法论对照实验 |
| `deep-curation` 语义 | 已澄清为"用户授权深处理" | **不等于**必须生成完整地图 |
| GBrain 是否采用 | 未定 | 要与本地替代方案做 POC 比较后再定 |
| 单机单用户 | MVP-0 硬限制 | 多设备/远程身份显式排除 |
| 敏感内容 / 大文件 / 保留周期 | 未定 | 开放对应入口前必须定案 |

**关键判断**：这个项目对"未定义"的处理是**诚实的**——它用 `Blocking Draft`、`Draft，待确认`、`未授权` 明确标注，而不是假装已定。这是它最值得保留的品质。所以我不认为这些"缺口"需要被填补；需要被填补的只是**第 3 节我指出的那两个真正的缺口**。

## 五、如果把全部需求压缩成一段话

> **KnowledgeFlow 要求自己成为一个"可信知识提升的治理管道"：任何原料可以在无摩擦、无归属要求的前提下被可靠地、不可变地、可崩溃恢复地保存；任何进入语义处理的源文都必须有确定性分段和可检查的处理状态，绝不允许静默丢弃；任何机器生成的语义结果都只能停留在可重建的派生层或候选层；任何进入可信知识层的内容都必须绑定精确的来源版本与证据，并经过人对**精确变更对象**的批准，且该批准可回滚、可审计。系统按内容规模、风险、复用价值与审核预算在完整策展、分层策展、检索优先之间分层选择，随使用逐步沉淀知识，并明确**不承诺语义零遗漏**——它承诺的是保存、记账、证据绑定与受控提升这四件可机械验证的事。**

---

## 六、我必须诚实标注的不确定处

- **第 3 层（领域流程）的实现优先级我不确定。** 权威登记把 C7 CLI → C8 验收排在最前，人工路由和 SOP-000A 排在其后。但按我的分析，"人工闸门积压"这个核心风险在 C7/C8 里完全没被触及——**这个顺序是否合理，取决于项目当前是"验证工程可行性"还是"验证产品可用性"，这一点文档里没有明说。**
- **`requirements` §5 四类内容表把低摩擦捕获落点写成 GBrain，与 §8/§13.2 冲突**（我上一轮核实过）。我无法从仓库判断这是遗留笔误还是尚未清理的旧设计意图——**如果是后者，第 3 层的"本地优先"就还不算真正冻结。**
- **我不知道你实际的输入规模和审核意愿。** 第 3 节那个"核心需求"的判断建立在"人工闸门是瓶颈"这一前提上；如果实际使用中捕获量很小，这个判断的重要性会大幅下降。仓库里没有任何真实使用数据可以验证——唯一的样例明确声明"原始材料未收录，不能补造覆盖数据"。

**一句话**：这个项目的需求不缺内容，缺的是**把六层确信度分开呈现**，以及**承认并写出那条一直隐含的"人工闸门吞吐量"需求**。前者是文档结构问题，后者是需求完整性问题——而后者比缺 CLI 严重得多，因为它决定了 P2/P3 是真实约束还是装饰。
