# 策展地图生命周期与知识库导航边界分析

> 状态：Historical Research Input（非权威）  
> 形成日期：2026-10-20  
> 形成时点：提交 `9344f43` 之后、`CUR1D-PREFLIGHT` 的地图角色文档收口之前  
> 作用：保存策展地图、知识库 README/导航及后续语义结构职责的分析  
> 非作用：本文不建立产品需求、主题契约、当前状态或实现授权；可采纳结论只以随后修订的现行权威文档为准。

你的理解更准确。我需要修正前面容易造成误解的说法：

> 策展地图不是知识库建成后需要长期维护的一张“全库全文地图”，而是每次重要材料进入可信知识前，用于理解、审核、组织和决策的任务级治理工件。

## 1. 策展地图的准确位置

严格来说，不应只说“入库前”，而应说“写入可信知识前”，因为原料可能已经作为 `raw/` 存入 provisional KB，但还没有进入可信 Wiki。

```text
捕获原料 T0
  ↓
确认目标知识库，可选地归档到 raw/
  ↓
针对本批材料生成策展地图 T1/T2
  ↓
人工查看、修改、接受、拒绝或延期
  ├─ 保存地图后结束
  └─ 请求准备可信写入方案
       ↓
     批准精确变更
       ↓
     写入可信 Wiki T3
```

知识库启用以后：

- 出现一份重要新材料：为这份新材料建立新的策展地图。
- 新材料与既有知识冲突：地图同时展示新材料证据、受影响页面和冲突候选。
- 需要重组页面或结构：建立一次范围明确的维护型策展地图或变更提案。
- 只是小修改、机械维护：不一定需要完整策展地图，可以走更轻的受控变更流程。

旧地图保留为“当时如何理解和决策”的审计记录，不需要持续改造成全库导读。现行概念导读实际上已经表达了这一点：[概念架构导读](../../knowledgeflow-conceptual-architecture-KnowledgeFlow概念架构导读.md)（成文时约第 158 行）。

因此，策展地图有四个明确边界：

| 维度 | 策展地图 |
|---|---|
| 对象 | 一份材料、一批材料或一次明确变更 |
| 时间 | 当前这次理解和治理任务 |
| 信任层 | T1/T2 工作知识与提案 |
| 作用 | 决定哪些内容值得怎样进入或修改可信知识 |

它不是永久的全库主页，也不是 Ontology 或知识图谱。

## 2. `README.md` 是不是知识库的“全文地图”

在当前 KnowledgeFlow 设计中，新知识库确实有根级 `README.md`。目前实现只写入知识库名称和 provisional 状态提示：[targeting.py](../../../src/knowledgeflow_curation/targeting.py)（成文时约第 673 行）。

但需要区分：

- KnowledgeFlow 选择创建根级 `README.md`；
- 这并不表示 Karpathy 的 `raw/wiki/schema` 模式天然规定 README 必须承担“全文地图”职责；
- 当前的 README 还只是入口文件，不是已经实现的完整知识库导航。

未来比较合理的职责是：

| 工件 | 主要职责 |
|---|---|
| 根级 `README.md` / 知识库首页 | 说明知识库目的、范围、状态和顶层导航 |
| Wiki 页面 | 保存获批、可阅读、可维护的可信知识 |
| 来源目录/台账 | 完整列出有哪些来源、版本和处理状态 |
| `SCHEMA.md` | 约束页面、来源引用、链接、导航及维护方式 |
| Taxonomy | 提供稳定的层级分类 |
| Ontology | 定义跨材料复用的概念、关系和约束 |
| 知识图谱 | 保存并查询具体对象和关系 |
| RAG | 按问题动态定位证据、组织回答 |
| 策展地图 | 审查某批材料怎样影响知识库 |

所以，README 可以承担“全库入口和顶层导航”，但不应塞入所有来源、主张、关系和证据，否则它会迅速膨胀并难以维护。

词表、分类、本体和知识图谱也不是更严格的“全文地图”。它们是不同用途的结构化视图：

- Taxonomy 解决“怎样分层浏览”；
- Ontology 解决“概念和关系怎样统一定义”；
- 知识图谱解决“哪些具体对象之间有什么关系”；
- 来源台账解决“是否把全部来源记清楚”；
- README/Wiki 导航解决“人应该从哪里开始阅读”。

更准确的“全库地图”不是某一个文件，而是：

```text
知识库首页
+ Wiki 导航
+ 来源目录
+ 搜索/RAG
+ 按需增加的词表、分类、本体或图谱
```

它们共同构成知识库的长期导航与访问能力。

## 3. 策展地图现在仍然有价值吗

有，而且按你现在的理解，它反而不再那么繁重。

其核心价值不是“重新概括整个知识库”，而是：

1. 防止重要材料未经理解和审核直接污染可信 Wiki。
2. 快速说明这批材料讲什么、证据在哪里。
3. 显示它与现有知识的新增、重复、冲突和结构影响。
4. 让用户选择接受哪些、修改哪些、延期哪些。
5. 把最终写入限制为经过批准的精确变更。

对于陌生长文，默认地图应当是“薄地图”：

- 全文范围有机械台账，不静默漏段；
- 用户首先看到材料概览和主要部分；
- 每个主要部分有大致范围和简短说明；
- 跨部分的重要主张、演进、冲突和盲区可见；
- 只有重要或用户选中的部分进入深层展开；
- 不要求用户审核每个段落、实体和关系。

这和“局部地图”不是两张不同地图。应当是一份策展地图同时具有：

- `declared_scope`：本次覆盖整份材料还是指定部分；
- `coverage_depth`：哪些范围只是机械记账、粗略理解、深入处理、延期或失败；
- `presentation_level`：默认薄展示，需要时再展开证据和细节。

## 4. 下一步应该做什么

下一步不应该马上运行模型，也不应该开始 RAG、Ontology、知识图谱或可信 Wiki 写入。

应先做一次很小的 `CUR1D-PREFLIGHT` 文档纠偏：

1. 在 SOP-20 明确：

   - 策展地图是材料批次/变更任务级治理工件；
   - 它位于可信 Wiki 写入前，而不一定在 `raw/` 归档前；
   - 知识库更新时生成新的范围化地图，不重建全库地图；
   - 不再区分两个强制的“局部地图/全局地图”产品；
   - 默认采用薄地图呈现。

2. 在渐进式提炼规范中修正容易误导的 `full-map`：

   - 建议改为“有界高覆盖地图”；
   - “高覆盖”只表示声明范围没有静默缺口，不表示语义上提取了一切。

3. 修正实验协议中的人工阅读基线：

   - 改为限时的初始理解对照；
   - 不要求你人工完成一遍完整深度策展；
   - `C-K1–C-K8` 只是独立质量核查点，不是要求你预先学完全部答案。

4. 收缩 CUR1D 首轮目标：

   - 整体概览；
   - 覆盖全文主要部分的粗粒度目录；
   - 少量跨段主题、演进或冲突；
   - 明确缺口和延期范围；
   - 可打开证据；
   - 至少支持一次用户修改；
   - 可以在地图处结束。

5. 同步项目状态，再由你单独授权真实处理器和一次真实材料运行。
