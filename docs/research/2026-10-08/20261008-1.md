## 1. 项目进度应与主 PRD 分离

结论是：**依照需求记录进度，不等于把进度写进需求文档。**

主 PRD 负责描述稳定的产品义务：

- 为什么做；
- 用户需要什么；
- 做什么、不做什么；
- 功能与非功能需求；
- 验收标准；
- 需求成熟度和依赖关系。

项目进度负责描述动态事实：

- 当前进行到哪个阶段；
- 上一个完成点是什么；
- 下一步是什么；
- 哪些代码已实现；
- 哪些只通过本地测试；
- 哪些通过远端 CI 或真实用户验证；
- 当前有哪些阻塞和已知问题。

现有主 PRD 已明确说明不负责提交、CI、编码批次和工程进度，这是正确的：[主 PRD 的职责边界](../../requirements-and-governance-baseline-需求与治理基线.md)。

### PRD 中可以保留什么“状态”

可以保留需求本身的成熟度，例如：

- `Draft`
- `Approved Design / Needs Detail`
- `Approved Design / Ready`

这些回答的是“需求是否已经定义清楚”，不是“代码做到哪了”。

以下内容不应写入主 PRD：

- P0V-2 已完成；
- 下一门禁是 P0V-3；
- 某提交是否 push；
- 测试数量；
- GitHub Actions 运行号；
- 当前本机 Store 有几个 Item。

### 合理的追踪关系

```text
主 PRD 的 FR/NFR 需求 ID
          │
          ▼
独立项目状态表：计划中 / 实现中 / 已实现 / 已验证
          │
          ├── 当前活动方案
          ├── 代码提交
          ├── 自动化测试与 CI
          └── Pilot / 用户验收证据
```

例如：

| 需求 | 实现状态 | 验证状态 | 证据 |
|---|---|---|---|
| `FR-INBOX-001` | P0C 已实现 | P0V-1/2 已完成部分真实验证 | P0 记录、测试、CI |
| Capture 历史恢复 | 尚未实现 | 已由 P0V 发现真实需求 | `P0V1-UX-01` |
| `FR-EVID-001` | 未实现 | 尚未开始实验 | 后续 Evidence-first 切片 |

这样既能依据需求管理项目，又不会污染 PRD。

## 2. “谁负责维护当前状态”应该怎样改

建议新增一份很短的唯一状态文档，例如：

`docs/project-status-项目状态与当前门禁.md`

它成为唯一的动态状态真源，控制在约 100～150 行以内。

### 文档职责重新分配

| 信息 | 唯一负责文档 | 什么时候更新 |
|---|---|---|
| 产品为什么做、必须满足什么 | 主 PRD | 稳定需求发生变化时 |
| 当前阶段、完成点、下一步、阻塞项 | 项目状态文档 | 每个检查点完成时 |
| 当前阶段具体怎么执行 | 活动实施方案 | 方案或执行结果变化时 |
| 哪份规范优先、冲突怎样裁决 | 设计权威登记 | 新冲突或新裁决出现时 |
| 历史上发生了什么 | `CHANGELOG.md` | 独立批次完成时 |
| 测试和验收证明 | 验收报告、测试、CI | 实际验证完成时 |
| 面向读者的项目介绍 | 双语 README | 阶段或公开能力发生较大变化时 |

### 唯一状态文档应包含什么

建议只包含以下字段：

```text
当前阶段：P0 低敏感度 Pilot
最近完成：P0V-2
当前检查点：P0V-3
当前状态：等待精确授权
下一动作：关闭收件箱、验证源 Store、创建新的操作副本
随后动作：P0V-R 恢复演练
已知问题：P0V1-UX-01、P0V2-UX-01
本地/远端状态：本地 main 比 origin/main 超前 10 个提交
最近远端验证：d149036 / Windows CI 37185470445
```

机器可读锚点只保留在这一份文件，例如：

```html
<!-- knowledgeflow-status stage=P0 completed=P0V-2 next=P0V-3 -->
```

其他文档只写：

> 当前状态与下一门禁见项目状态文档。

不要再在五六份文档中复制“下一门禁是……”。

### 谁实际负责更新

建议采用以下责任规则：

1. 实施者或代理完成某检查点后，整理证据并提出状态变化。
2. 项目所有者确认涉及真实数据、产品状态或新阶段的升级。
3. 状态变化与证据记录放在同一个提交中。
4. CI 只检查唯一状态文件格式、链接和证据引用，不尝试在多份散文中比较同一句话。
5. PRD、设计权威和 README 不因每个小检查点反复修改。

现在的文档检查之所以没发现问题，是因为它只验证五份文件都写着宽泛的 `next_gate=P0V`，[没有验证 P0V 内部的具体检查点](../../../scripts/doc-check.py)。这需要在文档治理批次中修正。

## 3. 当前 P0 链到底进行到哪里

先解释编号：

- `P0`：低敏感度本地 Pilot 阶段；
- `V`：真实使用验证；
- `0/1/2/3/4`：验证检查点；
- `R`：Restore，恢复演练。

当前进度可以简化成这一条线：

```text
P0A 方案                     ✓
→ P0B 管理/备份/恢复能力      ✓
→ P0C 最小收件箱              ✓
→ P0D 真实 Pilot 初始化       ✓
→ P0V-0 验证协议              ✓
→ P0V-1 正常捕获/读取/续写    ✓
→ P0V-2 重启/离线/错误理解    ✓
→ P0V-3 新操作副本            ← 当前下一步
→ P0V-R 恢复到新目标
→ P0V-4 汇总证据并关闭 P0
```

[P0 方案顶部](../../p0-production-dogfood-plan-P0生产初始化与最小收件箱试用方案.md)在该时点准确写明：P0V-1 和 P0V-2 已完成，下一门禁是 P0V-3。

### P0V-3 要做什么

不开发新功能，只做一次当前状态的备份验证：

1. 正常关闭收件箱，停止写入；
2. 只读验证当前活动 Store；
3. 确认一个全新的备份目标叶目录；
4. 执行一次 `backup`；
5. 验证 Backup Manifest；
6. 再次确认源 Store 前后没有变化。

它的意义是：P0D 的旧备份只有最初的 1 个 Item；现在 Store 已有 4 个 Item、6 个 Version，需要证明当前 dogfood 后的完整状态也能生成一致操作副本。

### P0V-R 要做什么

从已验证的备份恢复到另一个全新目录：

- 不覆盖活动 Store；
- 不修改当前配置；
- 不切换程序使用位置；
- 验证恢复后的 Item、Version、字节、哈希和 Store 身份；
- 验证恢复目标可以正常读取。

这是证明“备份真的能恢复”，不是建立完整灾备平台。

### P0V-4 要做什么

只做收口：

- 汇总 P0V-1/2/3/R 证据；
- 记录两个重要 UX 问题；
- 更新唯一状态入口；
- 明确 P0 通过范围和未证明范围；
- 单独提交。

### 当前附加状态

- 工作树干净；
- 本地 `main` 比 `origin/main` 超前 10 个提交；
- 本地生产 `src/` 与远端已验收的 `d149036` 没有差异；
- 因此网络问题不阻塞 P0V-3，但最新 P0 文档与验证记录还没有同步到远端。

完成标准是产生一张“原文档 → 新权威位置 → 归档位置”的映射表。

- 设计权威登记只保留权威矩阵、有效决策、未解决冲突；
- 已解决冲突和逐批日期移入历史归档；

- 渐进式提炼规范把“当前 P0 状态”改成稳定前置条件；
- 双语 README 只保留高层能力和唯一状态链接；
- `docs/README.md` 只负责阅读顺序和文档职责。

### D2-5：调整文档护栏

修改 `doc-check.py`：

- 只允许一个机器可读状态锚点；
- 检查唯一状态文档存在且被 README 路由；
- 不再要求历史编码方案携带当前状态；
- 检查归档文件都有对应归档 README；
- 检查所有现行链接已更新；
- 检查 `docs/` 顶层不再出现已完成执行方案；
- 可以禁止稳定契约出现“当前下一门禁”一类动态措辞。

### D2-6：验证与提交

文档归档批次建议只运行与风险匹配的检查：

1. 文档护栏；
2. `test_doc_check.py`；
3. Markdown 相对链接检查；
4. README 路由与结构树检查；
5. `git diff --check`；
6. 归档前后文档清单核对。

无需仅因为移动文档就重复运行全部 338 项 Capture 测试；若修改了 Python 文档检查器，则运行其聚焦测试即可。

建议拆成三个独立提交：

1. `docs(governance): 建立唯一项目状态入口`
2. `docs(contracts): 提取长期管理与收件箱契约`
3. `docs(archive): 归档MVP-0与P0历史实施材料`

## 推荐的实际顺序

现在不要立刻移动文档。最稳妥的顺序是：

1. 做一次极小的当前状态纠正，明确 `P0V-2 已完成、下一步 P0V-3`；
2. 完成 P0V-3；
3. 完成 P0V-R；
4. 完成 P0V-4；
5. 按上述 D2 方案归档；
6. 再实施 Capture 历史浏览与“恢复为新版本”。

这样既不会让文档归档打断正在进行的 P0，也能保证 P0 完成后不再把大量历史实施材料带入下一个 Evidence-first 阶段。
