# KnowledgeFlow 最小本地收件箱产品规范

> 状态：`Implemented`（限定 P0C 当前已实现与已验收范围）；`P0C-UX0` 最小交互扩展为 `Approved Design`，尚未实现<br>
> 契约提取日期：2026-10-09<br>
> P0C-UX0 契约收口日期：2026-10-09<br>
> 适用范围：单机、单用户、Windows-first、本地离线文本 Capture 的薄桌面界面<br>
> 文档职责：长期维护当前收件箱的用户任务、四操作绑定、界面状态、重试安全和已知限制；不维护当前项目门禁、历史实施顺序或未来完整编辑器设计

## 1. 产品角色与目标

最小本地收件箱让用户不必理解机器协议或直接浏览 Store 文件，就能完成一条最短的本地文本旅程：

```text
启动并检查配置
  → 浏览未分配的 Capture
  → 新建并保存一条文本 Capture
  → 打开并完整读取正文
  → 基于当前版本追加一个完整新版本
  → 理解保存结果、警告或可行动错误
```

它是现有 Capture 内核之上的可替换薄壳，不是知识库、语义处理器、可信写入器或第二套存储层。Capture Store 继续是规范真源；界面只能通过四个公共 Capture 操作工作。

当前范围已经在临时 Store 自动化测试和本机低敏感度 Pilot 中形成初步可用性证据，但这不表示完整版本管理、长期使用、正式私人内容环境或整个 KnowledgeFlow 已经生产就绪。

## 2. 入口与运行边界

安装入口固定为 `knowledgeflow-inbox`：

```text
knowledgeflow-inbox
knowledgeflow-inbox --config <Windows-local-absolute-path>
knowledgeflow-inbox --help
```

- 无参数时读取当前 Windows Profile 的标准配置 `%LOCALAPPDATA%\KnowledgeFlow\config.yaml`。
- `--config` 只选择一个受信路径策略允许的本地绝对配置路径；不能切换测试策略或指定正文。
- `--help` 完全离线，不构造运行会话或打开 GUI；帮助和错误流固定为 UTF-8，以避免依赖 Windows 控制台区域编码。
- 无效参数返回 exit `2` 和固定、无路径的错误；启动内部失败返回 exit `1` 和固定错误；正常帮助或 GUI 正常结束返回 exit `0`。
- 界面不要求账号、GitHub、网络、模型、GBrain 或常驻服务，不打开 localhost 端口。

当前可见界面使用 Python 标准库 Tk。Tk 是本批最小实现选择，不是主 PRD 的永久前端约束；未来替换界面时仍必须遵守本文的操作、安全和状态边界。

## 3. 唯一持久化边界：四个公共操作

收件箱通过 `InboxSession` 一对一调用四个公共操作：

| 用户动作 | 公共操作 | 界面职责 | 内核继续负责 |
|---|---|---|---|
| 新建并保存 | `capture_text` | 收集正文、生成进程内请求身份、展示结果 | 输入校验、幂等、ID、锁、原子提交、回执和 warning |
| 刷新/翻页 | `list_captures` | 请求 `routing_status=unassigned` 的稳定分页并显示摘要 | 游标、投影读取、完整性和 warning |
| 打开条目 | `get_capture` | 用内存 `BytesIO` 接收完整 UTF-8 正文并展示 | 指定版本读取、哈希/大小校验和正文交付语义 |
| 追加新版本 | `append_capture_version` | 绑定已打开 Capture 和所见当前版本，提交完整新正文 | CAS、不可变版本、幂等、原子提交和回执 |

适配层不得解析或直接写 Store，不得导入私有事务函数，不得复制 C7 机器帧，也不得以界面状态替代核心结果。新建与追加固定使用 `channel.type=app`、`channel.instance_id=knowledgeflow-inbox` 和 `processing_mode=capture-only`；这只保存来源，不授权自动摘要、关系发现或深度语义处理。

## 4. 可见界面能力

### 4.1 收件箱列表

- 首屏和分页只列出 `routing_status=unassigned` 的条目；当前会话默认每页 25 项。
- 每项可以显示 Capture ID、当前版本、时间、preview、路由/信任状态和 Envelope 哈希的必要可见表示。
- “未分配”精确映射 `routing_status=unassigned`。
- “待处理”只是 `trust_status=unreviewed-capture` 的用户文案，不创建 `processing_status`，也不映射内部 `outbox/pending`。
- 列表刷新不读取全部正文；打开条目时才调用 `get_capture`。

### 4.2 阅读

- 打开条目必须读取并展示完整 UTF-8 正文，以及 Capture ID、所读版本、当前版本、正文大小、Payload/Envelope 哈希和路由/信任状态。
- 正文先由核心完整验证，再进入内存 sink；失败或不完整结果不能作为成功正文展示。
- 当前可见 Tk 界面打开的是条目当前版本。底层 `get_capture` 能按明确版本读取，但当前 UI 没有历史版本列表或版本选择器。

### 4.3 新建

- 用户输入文本并主动保存后，界面调用 `capture_text`。
- 成功必须显示 Capture ID、版本 `v1` 和已提交状态；warning 不能被隐藏成“完全无事发生”。
- 配置缺失时只显示“尚未初始化”和管理入口指引，不能自行创建配置、目录或 Store。

### 4.4 追加新版本

- 用户先打开 Capture，再明确进入追加模式；界面使用所读到的 `current_version` 作为 `expected_current_version`。
- 保存的是一个完整、不可变的新版本，不覆盖或删除旧版本。
- 若其他会话已经追加，核心返回 `version_conflict`；界面要求刷新、重新阅读并由用户决定，不能静默覆盖。
- 当前界面成功后显示新版本号，但不提供历史浏览、版本差异、回退或“恢复旧版正文为新版本”的入口。

## 5. 写入身份、重试与结果不明

每次写入在调用核心之前生成一个新的稳定幂等键。正文、目标 Capture、预期版本和幂等键只保存在当前 `InboxSession` 进程内，不进入公开展示对象。

### 5.1 已知成功或确认未保存

- 成功回执必须能证明 `commit_state=committed`，随后清除当前 pending 请求。
- 核心明确返回 `not-committed` 时，界面可以保留正文供用户修正或重试；若用户改变请求，使用新的幂等键。
- 不能把失败、warning 或未知状态改写成保存成功。

### 5.2 `unknown` 提交状态

若公共操作抛出未分类异常、返回无法验证的结果或明确给出 `commit_state=unknown`：

1. 界面保留原正文、原目标、原预期版本和原幂等键；
2. 编辑/目标切换被锁定，不能用新正文替换尚未核实的请求；
3. “重试上次保存”必须复用完全相同的请求和 key；
4. 用户也可以先刷新列表或重读 Capture，完成一次人工核对；
5. 只有核对后才允许明确放弃 pending 身份，再开始新请求。

刷新或读取只是让当前进程记录“已核对”，并不自动证明旧请求已保存，也不自动重发。

### 5.3 关闭与崩溃

- 关闭会话会丢弃内存中的当前文档、正文和重试身份；这不是安全擦除，也不会删除已提交数据。
- 未保存草稿没有持久化保证；用户确认关闭后可以正常丢弃。
- 界面进程崩溃或重启后不得自动重发上一请求。用户必须先刷新和人工核对，再决定是否重新提交。
- 当前不建立持久草稿库、客户端 outbox 或请求日志。

## 6. 错误、警告和隐私

界面把核心结构化错误映射为固定、可行动、无正文和路径的中文提示，至少区分：

- 配置缺失/无效、Store 未初始化/不可识别/不受支持/暂不可用；
- 输入无效、正文过大；
- Capture/版本不存在、版本冲突、幂等冲突；
- 完整性失败、原子提交失败、正文输出失败；
- 写入结果不明和界面内部失败。

以下 warning 仍然是成功结果的一部分，但必须显式展示并建议停止或进入管理流程：

- `projection_needs_rebuild`；
- `outbox_needs_rebuild`；
- `incomplete_version_ignored`。

正文不得进入命令行参数、stdout/stderr、日志、traceback、遥测或磁盘临时 spool。新建/追加正文以进程内字符串传入公共 API；读取正文只进入进程内 `BytesIO`。公共提示不得包含完整本机路径、配置字节、幂等键或异常细节。

## 7. P0C-UX0 最小交互契约与剩余缺口

P0V 观察到的两项真实摩擦已经由 `P0C-UX0` 收敛为以下 `Approved Design`；这只允许后续按本文实现和验收，不表示当前 Tk 界面已经具备这些能力，也不自动授权编码。

| 编号 | 当前事实 | 契约状态 |
|---|---|---|
| `P0V1-UX-01` | Store 保留全部不可变版本，`InboxSession.open_capture(..., version=N)` 和公共读取支持明确版本，但当前可见界面没有历史入口；用户容易把追加误解为覆盖 | 第 7.1–7.4 节已冻结历史只读浏览及“以旧版正文恢复为新版本”；尚未实现 |
| `P0V2-UX-01` | 真正的空字符串会以 `invalid_input + not-committed` 安全拒绝，但当前组合文案重复提交状态，且修正动作不够明确 | 第 7.5 节已冻结单一、可行动提示；尚未实现 |
| 大正文交互 | I/O 当前在 Tk 界面线程同步执行，大正文可能短暂冻结窗体 | 只有真实使用证明阻塞后，再设计受控后台执行、取消和结果归属 |
| 草稿恢复 | 草稿和请求身份只在当前进程内 | 只有真实摩擦证明需要时，再设计受治理的持久草稿/请求日志及隐私、恢复和删除边界 |

### 7.1 复用边界与版本来源

`P0C-UX0` 不增加第五个公共操作、不修改 Capture schema，也不允许界面解析 Store：

1. 打开最新版本继续调用 `get_capture(capture_id, version=null)`；打开历史版本调用同一操作的明确 `version=N`。
2. 成功读取返回的 `version` 是正在查看的版本，`current_version` 是该次读取时已证明的最高连续已提交版本。由于公共读取已经验证版本链恰好为 `1..current_version`，界面可以据此提供版本编号选择，不建立版本索引或第二真源。
3. 返回最新版本必须重新以 `version=null` 读取，不能只把旧的内存正文改标为“最新”。
4. 历史读取、恢复草稿和后续追加都只能经过四个公共操作；任何完整性失败、未知 schema 或读取 warning 继续服从现有失败关闭和显式提示语义。

### 7.2 历史版本只读浏览

打开任一 Capture 后，阅读区必须同时让用户分清“正在查看版本”和“当前最新版本”：

- 最新视图至少显示“当前版本 `vN`”和“共 `N` 个版本”；只有一个版本时也不得使用暗示会覆盖历史的文案。
- 存在多个版本时提供明确的“历史版本”入口；版本选择按版本号确定性展示，默认最新在前，表现形式可以是选择器或列表，但不得预读全部历史正文。
- 选择 `vK` 后调用明确版本读取并展示其完整正文、版本号、正文大小和既有哈希信息；当 `K < N` 时醒目标注“正在查看历史版本 `vK`（只读），当前最新为 `vN`”。
- 历史正文始终只读；切换版本本身不创建草稿、不写 Store，也不改变哪个版本是当前版本。
- “返回最新版本”重新读取当时的最新版本。历史读取失败时不得把部分正文或错误结果显示成成功历史版本，也不得覆盖此前已成功显示的正文。
- 切换到另一个 Capture 时清除上一条目的历史选择，不能把版本号或正文串到新条目。

### 7.3 以旧版正文恢复为新版本

历史视图可以提供“以此版本恢复为新版本”，但“恢复”严格表示追加，不表示倒退或改写历史：

1. 该动作先把已成功读取的 `vK` 完整正文复制到现有追加编辑器，并明确显示“将为同一 Capture 新增 `vN+1`；`v1..vN` 均会保留”；进入编辑器本身不得写入。
2. 编辑器中的可见完整正文就是随后要提交的正文。用户可以原样保存，也可以先修改；只有再次主动执行“保存为新版本”才调用 `append_capture_version`。
3. 追加请求绑定同一 `capture_id`，并以读取历史正文时返回的 `current_version=N` 作为 `expected_current_version`；不得以所选历史版本 `K` 作为 CAS 基线。
4. 若其他会话已经追加，`version_conflict` 必须保留当前草稿并要求用户刷新、重读后自行决定；界面不得自动改变基线或静默重试为另一个版本。
5. 成功后新版本成为 `vN+1`；原 `vK` 和中间版本的身份、正文及哈希保持不变。界面不得使用“已回滚到 vK”这种会掩盖新增版本事实的成功文案。

这项能力用于纠正误改或恢复旧正文，不是 Store 备份恢复、可信 Wiki 回滚或 Git 回滚。

### 7.4 历史交互状态边界

- 当前进程只需保存已打开 Capture、所读版本、该次读取返回的 `current_version` 和已验证正文；关闭后不持久化历史选择或恢复草稿。
- 查看历史不改变列表排序、`routing_status`、`trust_status`、时间事实或任何投影。
- `unknown` 写入状态出现时，现有 pending 请求仍拥有界面控制权；不得用历史选择或恢复草稿替换尚未核实的请求。
- 不新增版本差异比较、批量恢复、跨 Capture 复制、编辑既有版本、删除、归档/取消归档、回收站或安全擦除。

### 7.5 空正文修正提示

当前公共契约只拒绝真正的空字符串；只含空格或换行但长度非零的正文仍是允许保存的 `channel-exact` 内容。因此界面不得把本项提示扩大成“纯空白不允许”。

当界面提交的正文精确为空并获得 `invalid_input + not-committed` 时：

- 主提示固定表达为：`未保存：正文不能为空。请输入至少一个字符后再次保存。`
- `not-committed` 只表达一次；标题、错误映射和最终渲染器不得分别重复附加“提交状态：确认未保存”。
- 若保留诊断码，`invalid_input` 只能作为一次次要信息出现，不能割裂主提示或代替修正动作。
- 当前编辑器正文和编辑能力保持不变；用户输入正文后再次保存属于修改后的新请求，使用新的幂等键。
- 本规则只特化界面能够确定的空正文场景；其他 `invalid_input` 仍使用安全、无正文和无路径的通用提示，不能猜测不存在的具体原因。

### 7.6 后续实现验收矩阵

| ID | 自动化验收 | 可见人工验收 |
|---|---|---|
| `UXH-01` | 打开最新 `v2` 时模型同时保留 `version=2`、`current_version=2`，不读取历史正文 | 用户能看到“当前 v2 / 共 2 个版本” |
| `UXH-02` | 选择 `v1` 精确调用 `get_capture(..., version=1)`，返回正文和哈希与既有 `v1` 一致 | 用户能看到“历史 v1，只读；最新 v2”，并能返回最新 |
| `UXH-03` | 仅查看或切换版本时 Store 前后字节快照一致 | 用户不会把查看理解为恢复或写入 |
| `UXH-04` | 从 `v1` 建立恢复草稿不写入；主动保存后以 `expected_current_version=2` 新增 `v3`，且 `v1`、`v2` 仍可精确读取 | 用户能说明这是“新增 v3”，不是覆盖或删除 v2 |
| `UXH-05` | 恢复草稿保存遇到并发追加时返回 `version_conflict`，保留草稿且不自动重放 | 用户得到刷新、重读和重新决定的明确指引 |
| `UXE-01` | 空字符串被拒绝，Store 不变；最终可见文本只出现一次“未保存”并包含明确修正动作 | 用户无需猜测即可输入正文后重试 |
| `UXE-02` | 失败后草稿保留；修正后的保存使用新 key 并正常形成版本 | 用户没有看到错误保存成功或草稿丢失 |
| `UXE-03` | 非空的纯空格/换行仍按现有 `channel-exact` 契约处理，避免 UX 修复改变核心输入语义 | 不向用户宣称尚不存在的“纯空白禁止”规则 |
| `UXB-01` | 适配层仍只调用四个公共操作，未解析 Store、未增加 schema/依赖/网络 | 历史查看和提示修正完全离线可用 |

实现候选至少运行收件箱定向自动化、现有文档护栏和一次临时 Store 可见 smoke；是否运行产品全量测试按实际代码影响决定。只有代码、测试、人工验收和精确提交远端门禁全部通过，才能把本节从 `Approved Design` 升级为 `Implemented`。

历史查看与“恢复为新版本”是版本管理可用性能力，不等于备份恢复，也不等于删除或可信知识回滚。删除、归档/取消归档、产品级回收站和安全擦除仍需独立数据生命周期设计，不能夹带进最小历史 UI。

## 8. 明确不在本规范内

- 自动摘要、标签、embedding、RAG、图谱、语义路由或模型调用；
- 新建/激活知识库、SOP-000A/SOP-001/SOP-002 或可信写入；
- 搜索、全文编辑器、双向链接、文件/URL/音频入口或 Obsidian 式完整 UI；
- 删除 Capture、覆盖历史版本、原地回滚、归档状态机或安全擦除；
- 账号、组织、多用户权限、多设备同步、冲突合并或远程服务；
- 自动初始化、修复、重建、迁移、备份、恢复或配置切换；
- Linux/macOS 已验证支持、发布级安装包、自动升级或高敏数据保护声明。

## 9. 可移植性和成熟度

当前交付 Profile 是 Windows-first，Tk 界面已在 Windows 安装态和低敏感度 Pilot 中验证。核心四操作、Capture/Bundle schema 和本文的失败关闭语义不得依赖固定盘符、用户名、GitHub 或网络；未来平台可以替换路径、锁、窗口和打包实现，但在完成独立验收前不能宣称该平台受支持。

当前实现入口位于：
