## 1. 为什么先写这份文档

此前的产品目标、GBrain 集成方案、SOP 和交互设想分散在多份文档中，且部分文字把“设计设想”“已确认需求”和“已经实现”混在了一起。继续开发前，应先建立一份可审阅、可追踪的需求基线。

本文件承担六项职责：

1. 固定系统真正要解决的问题，避免项目退化为普通的知识库工具或 QQ 机器人。
2. 明确哪些写入可以自动执行、哪些必须先形成方案并由人确认。
3. 把深度策展、低摩擦捕获、机械维护放入同一条可解释的状态链。
4. 用稳定需求 ID 描述顶层能力和非功能约束，并指向负责细节的主题规范。
5. 区分“已批准需求”“已实现能力”“待实验方法”和“远期设想”。
6. 列出当前方案尚未解决或相互冲突的部分，供后续逐项确认。

### 1.1 文档分层与完整性的含义

项目不把“完整需求”理解为把所有字段、流程、错误码和测试复制进一个超长文件，而采用三层结构：

| 层级 | 回答的问题 | 当前载体 | 权威边界 |
|---|---|---|---|
| L0 产品需求与治理 | 为什么做、为谁做、必须具备什么、哪些红线不可突破 | 本文件 | 唯一顶层需求入口；其他文档不得反向改变这里的产品目标和治理红线 |
| L1 主题规范 | 某一能力在业务和数据层具体如何工作 | 捕获与路由、Capture Envelope、操作契约、SOP-000A、渐进式知识提炼等 | 只在[设计权威与冲突登记](design-authority-and-conflict-register-设计权威与冲突登记.md)分配的主题内有效 |
| L2 实施与验收 | 如何编码、分批、测试和证明 | 实现拆解、编码执行方案、测试矩阵、CI | 证明实现状态，不能自行创造产品需求 |

因此，本文件是“完整的顶层需求基线”，但不是所有实现细节的合集。新增顶层需求应先在这里取得稳定 ID；新增字段或算法则进入相应 L1/L2 文档，避免再建立一份并行总需求。

## 2. 核心问题：知识策展悖论

本项目提出并试图缓解的“知识策展悖论”是：

> 高质量策展需要先充分理解材料，但充分理解往往又依赖持续整理、关联、使用和修订；如果入库门槛过高，灵感和原料会因为摩擦而流失，如果门槛过低或交给模型自动完成，知识库又会被不透明、不可控的语义判断污染。

系统不试图用一次模型调用“消灭”这个矛盾，而是通过分层、状态、人工闸门和可回滚版本，把矛盾变成可管理的流程：

- 捕获可以立即发生，不要求当场完成策展。
- 理解、分类、提炼和关系建立可以由模型辅助，但先产出可审方案。
- 可信知识的语义写入必须由人确认。
- 机器可自动完成无语义或可证明等价的机械操作。
- 所有变化都有来源、方案、批准对象、执行结果和 Git 历史可追溯。

## 3. 产品北极星与非目标

### 3.1 北极星

长期目标是形成一个可外置、可审计、可持续演化的“第二大脑”：

- 知识易捕获，不因当下无法分类而丢失。
- 深度材料能以可追溯、分层且先审后写的方式逐步进入可信知识层；系统不承诺一次性完成语义零遗漏。
- 临时灵感、对话和想法能低摩擦保存，再在合适时间审核和提升。
- 用户始终知道系统准备改什么、为什么改、批准后实际改了什么。
- 误操作和不满意的策展结果能够回滚。
- 检索、图谱、联想和自动分析服务于知识管理，但不能绕过治理边界。

### 3.2 非目标

- QQ 不是产品本体，只是验证低摩擦捕获和问答效果的一种可选入口。
- GBrain 不是可信知识的唯一真源，也不直接取得黑盒策展权限。
- Obsidian 不是必须复刻的宿主；目标是借鉴其本地 Markdown 交互体验，同时补足状态、权限、审核和回滚。
- 项目不追求“全自动整理一切”。自动化程度必须服从可解释、可批准和可恢复。

### 3.3 目标用户与使用环境

当前首要用户是希望长期积累个人知识、又不愿在每次记录时先完成分类和整理的单机用户。其典型环境是用户控制的 Windows 设备、本地文件系统和可选 Git；断网、未登录 GitHub、未配置 GBrain 或模型服务时，核心捕获仍应可用。

MVP-0 明确按单用户、单设备、文本输入设计。团队协作、多租户权限、多设备冲突合并、移动端和远程服务不是当前承诺；若以后增加，必须另设需求与迁移门禁，不能默默改变本地数据和信任模型。

### 3.4 用户要完成的核心任务

1. **先记下来**：无需先选 KB、标签或处理方式，就能可靠保存原始文本。
2. **找回并续写**：按稳定身份读取、列出和追加版本，不把派生投影视为唯一事实。
3. **整理收件箱**：看到尚未归属或尚未处理的内容，人工决定保留、路由、延期或归档。
4. **按价值选择处理深度**：短小或高价值材料可以做高覆盖策展；大型材料可以先检索、再围绕问题形成局部证据和候选，而不是强制生成一张完整地图。
5. **审证据再批准**：检查处理范围、来源证据、已知缺口和精确变更对象，再决定是否提升为可信知识。
6. **恢复与迁移**：在崩溃、投影损坏或存储位置变化后，能从规范事实恢复，而不是依赖黑盒服务或人工猜测。

### 3.5 产品层与信任层

| 层 | 典型内容 | 规范身份 | 可以自动产生什么 | 不得被误称为什么 |
|---|---|---|---|---|
| T0 捕获事实层 | 原始 Payload、不可变 Version/Envelope/Event | 本地 Capture Store | 原子保存、校验、读取、追加、恢复、迁移 | 已理解、已归类或可信知识 |
| T1 可重建派生层 | 索引、embedding、摘要、检索结果、候选图谱 | 从 T0 或可信层重建 | 检索、分析、质量信号 | 唯一原件或已批准结论 |
| T2 提案隔离层 | 路由、策展、promotion、精确变更提案 | 绑定来源版本、证据和提案版本 | 模型生成、人工修改、拒绝或批准 | 已执行的可信写入 |
| T3 可信知识与治理层 | 获批 wiki、SCHEMA、批准/审计记录、发布检查点 | 本地 Markdown/规范记录 + Git 历史 | 只执行已批准的精确变更和确定性维护 | 可由 RAG/GBrain 自动覆盖的缓存 |

T0 与 T3 都是规范事实，但回答不同问题：T0 证明“用户当时保存了什么”，T3 证明“哪些知识和治理决定已被明确接受”。T1/T2 可以提高效率，却不能绕过从证据、提案到精确批准的边界。

## 4. 不可破坏的治理原则

以下原则视为当前已经对齐的产品约束；若未来调整，必须形成显式决策记录。

### P1：立即保存不等于可信入库

用户原始表达、链接、文件或对话可以立即保存。立即保存只证明“原料已被捕获”，不证明它已经被正确理解、分类或策展。

### P2：语义计算可以自动，语义落库必须受控

模型可以自动做摘要、分类建议、关系发现、策展地图和变更方案，但这些结果只能进入派生层或提案隔离区。凡会改变可信知识的含义、边界、结构、关系或检索身份的写入，必须先提交方案，由人确认后执行。

### P3：禁止自动黑盒策展写入

系统不得让模型在后台自行决定并直接完成以下行为：

- 将原料提升为可信 wiki 页面。
- 改写已有可信页面的语义内容。
- 自动扩展知识库领域。
- 新建或合并知识库。
- 新增页面类型、关系类型、标签体系或模块。
- 将一个知识条目自动路由到某个知识库并视为最终归属。

### P4：批准必须绑定精确对象

人工批准的对象应是可复核的方案、具体条目或精确 diff，而不是一句宽泛的“方向同意”。批准后不得再让模型根据该方向重新生成另一版正文并直接写入。

### P5：机械操作可以自动，但必须确定、幂等、可重建

哈希、时间戳、格式校验、索引重建、引用扫描、确定性文件移动等不涉及语义判断的操作，可由规则引擎或硬编码执行。自动操作应满足：

- 同一输入重复执行不会产生额外副作用。
- 规则和结果可检查。
- 派生产物可以从真源重新生成。
- 失败时不会留下“半批准、半写入”的状态。

### P6：按事实类别区分规范真源

Capture Store 是原始捕获、不可变版本和捕获事件的规范事实来源；获批 wiki、结构规范、批准与审计记录以本地 Markdown 或其他获批规范记录为载体，并由 Git 提供版本、diff、发布检查点和回滚能力。GBrain、RAG 索引、摘要和候选图谱只承担可选镜像或派生分析，其可重建数据不得反向覆盖 Capture 事实或可信知识与治理记录。

### P7：权限按状态授予，而不是一次性给 Agent 整库写权限

Agent 的权限至少区分捕获、提案、执行已批准变更、机械维护四类。处于临时状态的知识库不得获得正式发布、联邦检索或自动传播权限。

### P8：允许延迟提取，但不得静默丢弃

语义处理可以按规模、风险、审核预算和用户问题分层或延迟执行，但不得通过缩小未声明的“处理范围”来隐藏遗漏。一次处理若声明覆盖整个 Capture 版本，则该版本的每个确定性源文区段都必须有可检查的状态；若只处理子集，则必须记录目标版本、选择边界或规则、选择理由，并为未选区段明确记录 `out-of-scope` 或 `deferred` 等状态。没有状态且不能由已声明边界解释的区段属于处理缺口，不得被覆盖率或摘要暗示为已完成。

### P9：检索和候选图谱不等于可信知识

RAG 结果、摘要、问答、实体关系候选和动态图谱都属于可重建的派生层或提案隔离区。它们必须保留 Capture 版本和证据定位，不能仅因可被检索或被模型生成就获得可信知识身份。

## 5. 四类内容与对应流程

| 情况 | 典型输入 | 初始落点 | 语义处理 | 可信入库方式 |
|---|---|---|---|---|
| 深度处理 | 有界高价值材料、重要论文或访谈 | 先进入本地 Capture Store；已获路由授权时由 KB `inbox/` 逻辑队列呈现，验证后才机械归档至 `raw/` | 允许按规模和审核预算采用完整策展、分层策展或检索优先；当前 Profile 名称、默认路由和阈值仍待实验，只生成提案 | 人审核证据和精确变更后，由后续受控写入流程执行 |
| 低摩擦捕获 | 临时灵感、随手想法、短对话、语音转写 | 本地 Capture Store；未分配项由 Global Intake 逻辑视图呈现，保存后可选异步镜像到 GBrain 未审核范围 | 可自动生成摘要、候选标签和路由提案，但保持未审核 | 人选择忽略、保留为原料、提升到已有 KB 或创建新 KB |
| 外部资料收集 | URL、PDF、附件、剪藏 | 对应 Payload 类型获批实现后仍先进入本地 Capture Store，再由 Global Intake 或已授权 KB `inbox/` 逻辑呈现 | 抓取、转码、哈希可自动；分类和提炼只形成提案 | 路由确认后按届时获批的处理策略进入分层处理；可信写入仍需新 SOP-002 |
| 机械维护 | 校验、断链扫描、分段台账、索引、哈希、备份 | 派生区或审计日志 | 规则引擎执行 | 不改变语义时可自动；发现语义问题只报告或提案 |

“用户自己刚写下的原文”属于来源事实，可以立即保存；模型对原文作出的概括、归类和改写属于机器语义判断，不因保存入口低摩擦而自动获得可信身份。

## 6. 最小捕获与路由链路

### 6.1 先捕获，后决定归属

捕获时有三种情况：

1. **用户明确指定已有 KB**：先提交本地 Capture Store 原件并记录用户意图；本地保存成功后，确定性路由步骤才把它呈现在该 KB 的 `inbox/` 逻辑队列并按批准方式归档。
2. **归属未知或存在多个候选 KB**：先提交同一个本地 Capture Store；它通过 Global Intake 逻辑查询呈现，不创建第二份 Intake 原件，模型只能提交路由建议。
3. **用户明确要求新建 KB**：仍先提交本地 Capture Store；确认创建意图和名称后执行 SOP-000A，建立无领域承诺的临时骨架，再路由捕获项。

系统不得因为模型认为“像某个领域”就自动新建知识库，也不得把未知归属原料直接塞入某个可信 KB。

### 6.2 不是所有捕获都先走 SOP-000

- 捕获到全局 Intake：不需要先执行 SOP-000。
- 捕获到已有 KB：不需要再次执行 SOP-000。
- 只有“创建一个新的 KB 容器”才执行 SOP-000A。
- SOP-000A 只创建最小临时骨架，不提前虚构领域、标签或页面类型。
- 第一份有代表性的原料进入临时 KB 后，只能按用户选择或届时获批的规则选择处理策略并生成派生/策展提案；当前 Profile 名称、默认路由和阈值仍是 Draft，不得伪装成已批准能力。其中的领域与 SCHEMA 建议仍必须经过人工确认。
- 人工确认领域和结构方案后，再执行后续待定义的 SOP-000B，将 KB 从 `provisional` 激活为 `active`。

### 6.3 最小状态机

```text
捕获
  ├─ 已明确已有 KB ──> KB inbox ──> raw ──> 策展提案
  ├─ 归属未知 ───────> Global Intake ──> 路由提案 ──> 人确认
  └─ 明确新建 KB ───> SOP-000A ──> provisional KB
                                           │
第一份代表性原料 ──> 按届时获批策略生成有范围和证据的派生/策展提案
                                           │
                                      人工确认
                                           │
                                  SOP-000B（待定义）
                                           │
                                        active KB
```

## 7. 隔离区的用途

隔离区不是“另一个正式知识库”，也不只保存一份笼统方案。它保存所有**已经生成、尚未获准改变可信知识**的语义工件，例如：

- `routing/`：建议进入哪个已有 KB，或是否建议新建 KB。
- `curation-maps/`：对长文、论文等原料的策展地图。
- `promotions/`：把灵感、捕获页或原料提升为可信知识的候选内容。
- `changes/`：对现有 wiki、SCHEMA、关系或标签的精确变更方案/diff。
- `maintenance/`：模型发现重复、冲突、过时内容后提出的处理方案。

隔离区具有以下性质：

- 内容可以由模型自动写入，但默认状态必须是 `pending`。
- 隔离区内容不能被检索层当作已确认知识返回，必须在查询结果中明确标识。
- 拒绝的方案可归档或删除，但审核记录应保留。
- 批准的是具体版本；方案变化后原批准自动失效。
- 执行结果和批准版本不一致时，事务应失败，而不是静默接受漂移。

旧版 `raw/_curation-maps/` 把“不可变原料”和“可编辑提案”混在一起，职责冲突。新流程已经确定使用 `proposals/curation-maps/`；已有知识库的旧目录只在实际迁移前保留兼容读取，不再作为新产物路径。

## 8. 系统组件的职责边界

| 组件 | 主要职责 | 不应拥有的权限 |
|---|---|---|
| KnowledgeFlow | 治理规则、状态机、审核、精确执行、审计与回滚 | 不把模型判断伪装成确定性规则 |
| LLM Wiki / SOP | 按获批处理策略生成概要、候选提取和策展地图；提供可追溯质量信号；受控写入另行受 SOP-002 门禁约束 | 把 Draft Profile 当成已实现路由；把候选或检索结果伪装成可信知识；未经批准直接策展入库 |
| GBrain | 低摩擦捕获、混合检索、图谱、派生分析、审核队列承载 | 将未审核内容自动提升为可信知识；覆盖 Markdown 真源 |
| DeepSeek Harness | 对话交互、工具编排、模型调用和执行会话 | 持有无边界整库写权限；批准后重新自由发挥 |
| Git | 版本、diff、审计、恢复和发布检查点 | 替代业务状态机或人工批准 |
| QQ 等入口 | 快速捕获、通知、简单查询和验证使用习惯 | 成为唯一入口或决定核心架构 |

## 9. 写入权限矩阵

| 操作 | 可否自动 | 说明 |
|---|---|---|
| 保存用户原始文本或附件 | 可以 | 写入未审核捕获层，保留原始内容和来源 |
| 抓取网页、转码、计算 SHA256 | 可以 | 规则确定且保留来源；抓取失败需显式报告 |
| 生成摘要、标签、关系、路由建议 | 可以生成 | 只能写入派生层或提案隔离区 |
| 将原料归到某个 KB | 条件允许 | 用户在捕获时明确指定可直接归入；模型推断必须待确认 |
| 新建 KB | 不可由模型自行决定 | 用户确认后由 SOP-000A 机械执行 |
| 修改 SCHEMA、领域、标签或关系类型 | 不可以直接执行 | 先给出精确变更方案，再由人确认 |
| 新建或改写可信 wiki 页面 | 不可以直接执行 | 先审策展地图，再审精确写入对象或 diff |
| 重建索引、embedding、图谱缓存 | 可以 | 只能作用于派生层，且应可从真源重建 |
| 自动修复格式、排序、规范化 | 视规则而定 | 只有能证明不改变语义的规则才可直接执行 |
| 回滚已批准批次 | 用户触发或策略触发 | 回滚对象必须是明确批次/commit，保留审计记录 |

## 10. 审核对象与执行约束

深度策展至少需要两个不同层级的确认：

1. **处理结果/策展地图审核**：核对声明的处理范围、来源证据、已知缺口和明显误读，决定哪些候选值得进入精确变更阶段，并审核领域和 SCHEMA 建议。该审核只能发现和降低遗漏风险，不能证明语义上“没有任何遗漏”。
2. **精确变更审核**：确认将创建、修改、移动或删除哪些文件，以及每个文件的具体内容或 diff。

执行器只消费“已批准且版本未变化”的变更集。建议每个批准批次至少记录：

- `proposal_id`
- 原料哈希和当前 KB 基线 commit
- 方案版本或内容哈希
- 审核人、审核时间和审核范围
- 允许的文件路径及操作类型
- 执行 commit
- 校验结果和可回滚点

## 11. 状态、审计与回滚

建议最小状态链为：

```text
captured -> pending-routing -> routed -> pending-curation
         -> pending-approval -> approved -> applying
         -> applied -> verified
```

旁路状态至少包括 `rejected`、`needs-revision`、`failed`、`rolled-back` 和 `archived`。

Git 负责文件版本，但不能单独表达全部业务状态，因此还需要提案元数据和审核日志。一次批准应尽量对应一个原子 commit；若执行或校验失败，不发布半成品，并回到可重试状态。

### 11.1 “每个 KB 独立 Git”是什么意思

它指每个知识库根目录都有自己的 `.git/`、提交历史、分支和回滚边界，而不是所有知识库共用项目顶层的一个 Git 仓库：

```text
knowledge-hub/                 # 可选：只保存 KB 注册表和全局 Intake
├── registry.yaml
├── intake/
└── knowledge-bases/
    ├── agent-learning-智能体学习/
    │   ├── .git/             # KB A 的独立历史
    │   └── kb.yaml
    └── job-dui-酒驾案件/
        ├── .git/             # KB B 的独立历史
        └── kb.yaml
```

与此相对，父级统一 Git 只有 `knowledge-hub/.git/`，下面所有 KB 都由同一份历史管理。

| 方案 | 优点 | 成本/限制 |
|---|---|---|
| 每个 KB 独立 Git | 回滚、权限、同步和备份边界清晰；可单独迁移或映射为一个 GBrain source | 仓库数量多；批量管理更复杂；跨 KB 变更不能天然形成一个原子 commit |
| 父级统一 Git | MVP 最简单；一次提交可同时更新多个 KB 和全局注册表 | 权限和历史耦合；单库分享、迁移和恢复的边界较弱 |

“每个 KB 独立 Git”目前只是候选架构，不是已经确认或实现的需求。在 Git 拓扑正式定案前，SOP-000A 不应擅自在现有项目中创建嵌套 `.git/`。

## 12. 文件与目录命名基线

### 12.1 可采用“英文名-中文名”的范围

技术上可以采用 `english-name-中文名`，并建议从新建的人类可读设计文档和 KB 根目录开始，例如：

- `requirements-and-governance-baseline-需求与治理基线.md`
- `sop-000a-provisional-kb-bootstrap-临时知识库骨架初始化.md`
- `agent-learning-智能体学习/`

英文部分应使用稳定的 `kebab-case`，中文部分用于快速识别。KB 的真实身份应由稳定 `kb_id` 表示，不能把目录名当作永久主键。

### 12.2 不应强制改名的机器契约

以下名称属于工具、生态或协议契约，应保留标准英文形式：

- Git/开发生态：`.git/`、`.gitignore`、`.github/`、`README.md`、`LICENSE`、`package.json`、`pyproject.toml` 等。
- KnowledgeFlow 固定契约：`kb.yaml`、`SCHEMA.md`、`index.md`、`log.md`。
- 固定系统目录：`inbox/`、`raw/`、`wiki/`、`schema/`、`proposals/`、`_archive/`。
- 代码模块、导入路径和命令入口：原则上保持稳定英文名。

这些路径可在 UI 和文档中显示中文标签，例如把 `proposals/` 显示为“提案隔离区”，无需修改磁盘契约。

### 12.3 不建议“一次性全部重命名”

现有文件之间存在 Markdown 链接、脚本路径、测试夹具、Git 历史和外部集成约定。批量重命名可行，但应作为独立迁移处理：

1. 先生成旧路径到新路径的完整映射表。
2. 标出机器契约和保留项。
3. 使用 `git mv` 分批迁移。
4. 更新所有链接、脚本、配置、测试和文档引用。
5. 运行全量测试和链接检查。
6. 用单独 commit 保存迁移，便于整体回滚。

当前阶段只对新文档应用双语命名，不批量改动现有路径。

## 13. 当前确认度

### 13.1 已由用户明确的需求

- 项目核心是解决或缓解知识策展悖论。
- 深度材料允许按完整地图、分层地图或检索优先的方向处理，任何语义候选都先审后写；三类 Profile 的工作名称、默认路由、阈值和物理契约仍须通过实验及独立门禁确认。
- 临时灵感等低摩擦内容先无门槛保存到本地 Capture Store；“GBrain 先写后审”在当前设计中解释为保存后可选异步镜像到 GBrain 未审核范围，而不是由 GBrain 先落规范原件。
- 不涉及语义的机械任务可由规则引擎或硬编码自动完成。
- 涉及语义的可信写入必须先提交方案，由人确认。
- 不允许自动黑盒策展写入。
- 需要类似 Obsidian 的低摩擦交互，但必须补充状态、权限和回滚。
- QQ 只是可选验证入口，长期目标是外置第二大脑。
- 可以立即保存原料，但新 KB 应先建立最小骨架，领域和结构可后置确认。
- 先把需求和流程写入 Markdown，再继续实现。

### 13.2 已确认的治理设计

- 使用 Global Intake 逻辑队列呈现尚未分配 KB 的本地 Capture Item，不另建第二份捕获原件。
- 将 `proposals/` 作为语义工件隔离区，并从 `raw/` 分离策展地图。
- 将 SOP-000 拆为 SOP-000A（临时骨架）和 SOP-000B（审核后激活）。
- 使用 `kb.yaml` 记录 KB 的机器身份和生命周期。
- 机器契约名称作为双语命名规则的明确例外。
- 本地 Capture Store 是第一规范原件；Global Intake 是未分配 Capture Item 的逻辑队列。
- GBrain 是可选异步未审核工作层，不承担唯一原件。
- MVP-0 先限制为单机、单用户、文本捕获。
- 当前机器未来生产 `capture-root` 的已选目标是 `E:\KnowledgeFlowData\capture-store`，但生产配置和目录尚未创建；只有用户另行授权初始化后它才成为实际绑定。通用代码读取每机配置，最终解析为绝对路径，内部原件只记录可迁移的相对路径。
- 文本 4 MiB 是内联阈值、64 MiB 是可配置默认安全上限；超限不得截断、摘要或自动拆分 Capture Item。

### 13.3 仍后置到对应功能前的架构选择

- 每个 KB 是否使用独立 Git 仓库，仍作为架构选项而非既定事实。
- 非文本文件大小上限、大文件对象存储、敏感内容加密和保留周期。
- GBrain 远程身份、多设备同步、QQ 和完整编辑器形态。

## 15. 顶层非功能需求

| ID | 非功能需求 | 验证方向 |

| `NFR-QUAL-001` | **机械完整性与语义质量分开证明**：字节、哈希和处理记账可作硬门禁；语义召回只能用人工样本估计 | gold set、引用正确率、遗漏类型和对照实验 |

| `NFR-EXT-001` | **可替换与可演化**：入口、模型、检索引擎和 GBrain 不得成为规范真源；新 schema 必须版本化并有迁移/回退边界 | 适配器契约、重建测试、版本与迁移评审 |
| `NFR-MAINT-001` | **可维护性**：权威、实现状态和测试证据必须可追踪；独立批次需单独复核、提交并通过确定性文档检查 | 冲突登记、提交历史、doc-check 与 CI |

当前没有冻结捕获时延、检索时延、语义召回率或人工审核时长的数值 SLA。先在 MVP dogfood 和方法实验中取得基线，再以独立决策设阈值；不得用未经测量的数字制造“已达标”印象。

| MVP-1 路由与 KB 骨架 | 人工路由、Route Record、纠错流程、SOP-000A 调用边界 | 自动模型路由、KB 自动激活、可信 wiki 写入 |
| 受控知识形成 | 重构 SOP-001，定义 SOP-000B 与新 SOP-002，闭合精确批准、事务、验证和回滚 | 未批准的结构扩展或黑盒批量写入 |
| 可选扩展 | 候选图谱、GBrain 未审核镜像、更完整 UI、QQ、远程/多设备能力 | 改变本地规范真源和人工闸门，除非另有明确迁移决策 |

严格顺序见第 20 节。阶段名称用于范围管理，不表示相应能力已自动获批；每个实施批次仍需单独授权。

## 17. 成功信号与验收口径

| 目标 | 先观察什么 | 不能用什么冒充成功 |
|---|---|---|
| 捕获得住 | 保存后字节/哈希可回读；重复请求不重复；崩溃后提交状态可证明；断网仍可用 | UI 显示“成功”、仅有投影或远端副本 |
| 找得回来 | 用户能按稳定身份读取、列表和续写；Global Intake 不漏掉未分配项 | 只证明文件存在，或只能靠开发者手工找目录 |
| 整理负担可接受 | 记录从捕获到归档/延期的用时、积压、放弃率和纠错次数 | 只统计模型生成了多少摘要或标签 |
| 处理成本可解释 | 比较 token/计算成本、首次可用时间、人工审核时间和不同材料/策略的差异 | 用文本长度单独决定处理方式 |
| 证据与语义质量可审 | 测量引用正确率、人工 gold set 召回估计、遗漏类型、候选批准/修改/拒绝比例 | 用区段覆盖率或条目数量证明“语义无遗漏” |
| 可信写入受控 | 执行内容与批准对象一致；失败不留下半成品；可定位检查点并回滚 | Git 有 commit 就等同于业务批准 |
| 系统可运维 | 恢复、重建、迁移可重复；未知对象保留并失败关闭；干净 Windows 环境通过门禁 | 开发机一次运行成功或仅 Linux 逻辑测试通过 |

MVP-0 的通过条件由 C8 汇总现有契约与测试证据。产品可用性和渐进式处理质量必须在之后的 dogfood/实验中形成基线，数值目标再单独批准，不能由当前 293 项工程测试代替。

## 19. 与当前文档/流程的主要冲突

以下冲突的当前裁决由[设计权威与冲突登记](design-authority-and-conflict-register-设计权威与冲突登记.md)统一记录；“已裁决”不表示旧文件已经全部完成迁移：

1. [已归档的 SOP v2 完整文档](../archive/2026-design-history/sop-v2-full.md)中的 SOP-000 要求先确认领域并立即创建完整 `SCHEMA.md`，与“先建无领域承诺的临时骨架”冲突。**已裁决：冷启动以 SOP-000A 为准。**
2. 现行 SOP-001 声称支持 `SCHEMA.md` 不存在的情况，但 SOP-000 和 SOP-002 又把 SCHEMA 存在作为前置条件，冷启动分支无法完整闭环。
3. 策展地图当前放在 `raw/_curation-maps/`，与 `raw/` 不可修改、原料与提案分层的原则冲突。**已裁决：新流程使用 `proposals/curation-maps/`，待重构 SOP-001。**
4. 现行 SOP-002 允许 Agent 自动扩展领域、注册标签和模块，与“所有语义结构变更先提案后确认”冲突。**已裁决：旧自动写入授权暂停，待重构 SOP-002。**
5. [已归档的 GBrain 集成方案](../archive/2026-design-history/gbrain-integration-plan.md)中曾存在“未审核内容是否会进入检索”的待确认项。**已裁决：GBrain 只作异步未审核工作层，接入前必须完成查询隔离实证。**
6. 项目文档中部分路线把 QQ 入口或 GBrain 能力写得接近产品主线。**已裁决：二者分别降级为可选入口和可替换工作引擎。**
7. 当前项目已经形成 Capture 操作的权限/版本与事务边界，但尚未形成可信知识写入所需的可执行权限矩阵、批准版本绑定、事务提交和回滚协议。**Capture 版本绑定原则已确认；可信写入部分仍是 SOP-000B/002 的阻塞门禁。**

## 20. 生效范围与下一步

本文件现为 `Approved Design`：后续设计不得违反其中的治理红线。第 14、15、18 节明确区分已实现、待 C8 验收、未实现和 Draft；README 和演示不得把整份需求基线描述成已交付功能。

主题级优先级以[设计权威与冲突登记](design-authority-and-conflict-register-设计权威与冲突登记.md)为准。推荐顺序：

1. R1 只收口顶层需求和追踪关系，不改变 Capture v1；后续 C7-0 已另行获批并以本地提交 `dbe8329` 冻结 CLI 文档契约，C7A 又完成私有协议代码与本地验证。当前下一功能门禁是需单独授权的 C7B。
2. [MVP-0 捕获内核实现拆解与测试矩阵](mvp-0-capture-implementation-plan-捕获内核实现拆解与测试矩阵.md)和[编码执行方案](mvp-0-capture-coding-execution-plan-捕获内核编码执行方案.md)已经批准；C3–C6 已逐批闭合并版本化。截至 C6C `ea8f84e` 已同步到 `origin/main`，Windows CI 运行 `35319645501` 首次通过当时 274 项普通/严格全量及工程检查。C7A 新增 19 项后当前 293 项本地全量通过并已独立版本化；下一步经单独授权实施 C7B、C7V，并以 C8 验收机器适配接口、安装态和 MVP-0 全链路。
3. C8 通过后，用户可另行授权创建生产 Capture Store 和只暴露既有 Capture 能力的最小本地捕获/收件箱，先通过真实 `capture_text/get_capture/list_captures/append_capture_version` dogfood 验证产品入口。
4. 同期在隔离临时 Store 中用获准的非敏感材料完成规模/结构基线实验，不新增生产 schema；再据证据冻结 Segment、Ledger、Profile 与 Evidence Bundle 的最小契约。
5. 实现本地检索与 Evidence Bundle POC，比较候选处理路径的引用正确率、成本、审核负担和人工 gold set 召回估计；不把 GBrain 作为前置。
6. 证据形成后再实现人工路由与 SOP-000A 调用边界，并重构 SOP-001，使其绑定精确 Capture 版本、处理范围和证据。
7. 再评估候选图谱和 GBrain 未审核镜像 POC；二者始终属于派生/候选层。
8. 根据实验证据定义 SOP-000B 和新 SOP-002，闭合精确批准、可信写入事务、校验和回滚后，才允许写入可信 wiki。
9. 最后扩展更完整的 Harness/Obsidian 式交互、QQ、多设备和其他入口。
