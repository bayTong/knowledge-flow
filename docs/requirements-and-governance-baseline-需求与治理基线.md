## 2. 项目概述

### 背景与核心问题

个人知识工作通常在两个失败方向之间摇摆：

```text
先全部理解、分类和建模再保存
→ 前置成本过高，灵感和材料容易在整理前流失

让模型自动提取并直接写入知识库
→ 速度快，但来源、选择和语义判断不透明，难以信任、维护和回滚
```

高质量知识策展要求理解材料，而理解又依赖持续阅读、检索、问答、比较、组织和修订。KnowledgeFlow 不承诺用一次模型调用消除这个矛盾，而是把它转化为可持续的知识工作循环。

### 产品定位

> **KnowledgeFlow 是一个通用、适应性、治理优先的个人知识工作与知识管理系统。用户可以从零散想法、现有材料、问题、研究主题、已有知识库或模糊意图开始；系统自动承担大部分可委托的保存、检索、比较、解释、组织和维护准备，让知识先被可靠纳入并快速可用，再在持续使用中逐步治理、选择性晋升为可信知识。**

用户无需预先定义完整领域、Schema、受控词表、Taxonomy、Ontology 或 Wiki 结构。用户始终保有任务目标与范围、知识取舍、可信判断、高影响结构变化、发布和语义回滚的最终决定权。

### 产品目标

KnowledgeFlow 应降低从以下任一起点：

```text
一个想法 / 一份材料 / 一个问题 / 一个研究主题 / 一个已有知识库
```

到以下结果的总成本：

```text
能够找回、查看、理解、问答、组织、编辑和治理，
并能在需要时形成有证据、可维护、可回滚的可信知识。
```

产品必须追求：

- 输入能够低摩擦、可靠且离线保存；
- 保存后的材料在合理成本内变得可搜索、可浏览并显示处理状态；
- 陌生领域允许边研究、边学习、边形成候选结构；
- 熟悉领域能够减少重复阅读、比对、链接和维护劳动；
- 大型或持续增长语料可以先检索和问答，再按真实使用逐步组织；
- 普通变化可以批量审核，高影响变化可以精确控制；
- 回答、摘要、关系和提案能够返回来源、范围和已知缺口；
- 本地规范事实不依赖 GitHub、GBrain 或在线模型才能保存和恢复。

### 成功假设

产品方向成立，需要通过真实使用证明：

1. 用户获得第一份可用结果的时间明显低于完全手工整理；
2. 系统减少机械阅读、比对和维护劳动，而不是把全部审核重新交给用户；
3. 来源、候选和可信知识的边界能被普通用户理解；
4. 大型语料的检索优先路径不会暗示已经完整提取；
5. 可信写入、结构变化和回滚能够被审计和复核；
6. 同一核心生命周期能服务多个代表性领域和起点。

具体数值目标应在 dogfood 和代表性材料实验后冻结；在没有基线前不得编造 SLA 或语义质量承诺。

### 非目标

KnowledgeFlow 不是：

- 固定领域或固定 Ontology 的知识库生成器；
- 要求用户先手工完成完整分类和建页的工具；
- 只有文件保存、没有工作知识和组织能力的归档器；
- 只有问答、没有来源状态和治理边界的 RAG 聊天工具；
- 单一 Wiki 编辑器、知识图谱生成器或 GBrain 外壳；
- 允许模型不经审核直接改写可信知识的黑盒 Agent；
- 以页面数量、图谱节点数或分类层级衡量成功的系统；
- 承诺对任意领域、任意规模实现语义零遗漏、绝对正确或无需用户判断的系统。

QQ、GBrain、Obsidian 式界面和远程 Agent 可以成为入口或可替换组件，但不是产品本体，也不得成为本地规范事实的唯一依赖。

## 3. 用户、角色与核心场景

### 目标用户与当前产品环境

首要用户是希望长期开展个人知识工作，又不愿在每次记录、研究或维护前先完成领域建模和分类整理的单机用户。用户可能：

- 对领域完全陌生；
- 已有部分理解；
- 已经是领域专家；
- 只想先保存零散材料；
- 已有一个需要持续维护的知识库。

当前首个产品范围面向单用户、单设备、Windows、本地文件系统和文本输入。团队协作、多租户、多设备冲突合并、移动端和远程服务不属于首个产品范围；未来增加时必须重新定义身份、权限、同步和冲突处理需求。

### 产品角色

| 角色 | 拥有或决定什么 | 主要行为 | 明确不承担什么 |
|---|---|---|---|
| 用户 | 任务目标、范围、成本、隐私、知识取舍、可信判断、长期组织、高影响变化、发布和语义回滚 | 提问、学习、笔记、编辑、纠正、选择和批准 | 不必逐条手工阅读、分类、建页或执行文件写入 |
| 辅助处理系统 | 不拥有最终目标和可信决定权 | 保存、检索、比较、摘要、聚类、解释、问答、发现关系/冲突/缺口、生成工作知识和准备提案 | 不得宣称用户已经理解，不得自行提升候选 |
| 受限执行器 | 只消费确定性规则或已批准精确对象 | 检查前置条件、事务写入、回读验证、审计、检查点和技术回滚 | 不得扩大范围、重新生成正文、改变语义或把执行成功等同于知识正确 |

“最终决定权属于用户”不等于每个动作都逐项点击。用户可以批准边界清晰、影响可见、能够整体回滚的批次，也可以预先批准确定性政策；历史批准不能被解释成永久授权。

### 核心用户旅程

| 旅程 | 典型起点 | 系统主要承担 | 用户主要承担 | 可接受的第一成果 |
|---|---|---|---|---|
| 低摩擦日常知识管理 | 灵感、计划、对话、随手笔记和零散资料 | 可靠保存、来源卡片、汇总、相似项发现和整理建议 | 表达必要意图；按需接受、修改、延期、归档或忽略 | 可找回、可搜索的原料，以及不过度打扰的整理建议 |
| 陌生领域研究与学习 | 问题、研究主题、模糊目标或尚未读懂的材料 | 收集和比较来源，生成有证据的概览、术语、争议、缺口、学习路径和临时关系 | 追问、纠正目标、形成理解并判断关键争议 | 有引用的答案、学习路径和可继续演化的工作知识 |
| 熟悉领域与已有 KB 维护 | 新材料、已有页面、明确修改目标 | 对齐现有结构，发现新增、重复、冲突、过时、断链和结构漂移，准备精确变更 | 审核关键差异、高影响结构和最终可信写入 | 可批量复核、可验证、可回滚的维护提案 |
| 大型或持续增长语料 | 大量材料、持续流入内容、尚不明确的问题 | 建立来源清单、分段状态、可重建索引、多层概览和查询证据包 | 决定高价值问题和需要稳定化的部分 | 可溯源检索与问答，并明确查询偏置和未处理范围 |

这些旅程不是互斥产品。日常灵感可以转为研究主题，研究可以逐渐形成正式知识库，已有知识库也可以重新进入研究和重构循环。

### 统一业务流程

```text
材料、想法、问题或研究目标
        │
        ▼
来源级纳入
保存原文、来源、版本和用户明确意图
        │
        ▼
工作级纳入
形成状态、来源卡片、索引、摘要、问答和临时组织
        │
        ▼
立即可用
阅读、搜索、学习、笔记、追问和临时组织
        │
        ▼
候选与提案
绑定证据、范围、版本、影响和精确变更
        │
        ├── 保留为来源
        ├── 延期
        ├── 修改
        ├── 拒绝
        └── 批准
                │
                ▼
可信知识
受限执行、验证、审计和检查点
                │
                ▼
持续治理
更新、重组、迁移、废弃和回滚
```

并非每项任务都必须到达可信知识层。只用于临时研究、一次问答或保留来源，也可以是完整、正确的结束状态。

## 4. 产品范围与业务模型

### 核心术语

| 术语 | 产品含义 |
|---|---|
| Capture | 用户保存的原始表达、材料或来源事实及其不可变版本 |
| 工作知识 | 系统基于来源生成、可立即用于阅读、搜索、问答和组织，但尚未取得可信身份的派生结果 |
| 提案 | 绑定来源、版本、影响和精确变更对象，等待接受、修改、拒绝或延期的候选 |
| 可信知识 | 已按治理流程明确接受、可审计、可维护和可回滚的知识或结构 |
| 知识库（KB） | 为持续目标管理来源、工作知识、提案和可信知识的知识空间；不等同于固定 Wiki 模板 |
| 策展地图 | 对材料范围、候选主题、证据、关系、缺口和可能组织方式的可审工作成果；不是可信知识本身 |
| 受限执行器 | 只执行确定性操作或已批准精确变更的组件，不拥有重新作语义决定的权限 |

这些术语描述产品概念，不自动冻结同名机器 schema 或物理目录。

### 三种“入库”含义

| 含义 | 用户获得什么 | 默认治理要求 |
|---|---|---|
| 来源级纳入 | 原文、来源、版本和明确意图得到可靠保存 | 用户提交即可，不需要模型语义审核 |
| 工作级纳入 | 来源可搜索、可浏览并产生摘要、提纲、临时集合、候选标签、问答和学习辅助 | 系统可自动生成，但必须显示来源、状态和边界 |
| 可信知识晋升 | 结论、页面、稳定结构或关系正式进入可信层 | 用户确认精确对象或批次后，由受限执行器执行 |

产品原则是：

> **先把来源可靠纳入并形成可用的工作知识，再把值得长期稳定的部分选择性晋升为可信知识。**

### 四层信任模型

| 层 | 典型内容 | 产品身份与限制 |
|---|---|---|
| T0 来源事实层 | 原始 Payload、不可变版本、Envelope/Event、用户原始笔记 | 是规范来源事实；不证明内容正确、已理解或已分类 |
| T1 工作知识与可重建派生层 | 来源卡片、索引、embedding、摘要、提纲、问答、临时集合、候选图谱 | 可立即使用、应可重算；不等于已批准知识结论 |
| T2 提案隔离层 | 路由、策展、结构、promotion 和精确变更提案 | 必须绑定来源和提案版本；批准前不得视为已执行 |
| T3 可信知识与治理层 | 获批知识产品、稳定结构、可信关系、批准和审计记录 | 必须版本化、可维护、可验证和可回滚；不得被派生系统自动覆盖 |

工作知识空间是面向用户的逻辑视图，可以联合呈现 T0、T1 和相关 T2 内容，但必须清楚显示各自状态。它不是第五个信任层，其物理 Store、Schema 和界面另行设计。

### 组织和访问方式

集合、专题、时间线、自由标签、Wiki、受控词表、Taxonomy、Ontology、知识图谱和 RAG 是可组合工具，不是所有知识库必须依次通过的阶梯。

| 方式 | 主要价值 | 适用信号 |
|---|---|---|
| 集合/专题/时间线 | 快速聚合相关内容 | 项目、事件和低摩擦整理 |
| 自由标签 | 轻量、多维浏览 | 命名和结构尚不稳定 |
| Wiki | 长期阅读、链接和维护 | 需要稳定解释和人工编辑 |
| 受控词表 | 统一重要名称和别名 | 同义词和命名漂移开始造成成本 |
| Taxonomy | 建立稳定层级与导航 | 层级浏览和分类复用有明确价值 |
| Ontology | 明确复杂概念、关系和约束 | 跨内容复用的语义需要稳定治理 |
| 知识图谱 | 表达和探索具体对象关系 | 关系分析、导航和候选发现 |
| RAG | 从大规模来源或可信知识检索证据并回答问题 | 全量策展不经济或需要问题驱动访问 |

结构应从真实材料和使用中形成候选，并支持延期、版本化、迁移、替换和回滚。

### 产品增量边界

| 产品增量 | 交付目标 | 明确不自动包含 |
|---|---|---|
| MVP-0 可靠捕获底座 | 本地文本捕获、读取、列表、追加版本、恢复、重建、迁移和受限机器入口 | 生产知识库、UI、AI 路由、工作知识、可信写入 |
| 本地 dogfood | 经用户确认的生产 Capture Store；只暴露现有能力的最小捕获/收件箱 | 自动策展、未冻结语义格式和大型编辑器 |
| 代表旅程与方法基线 | 测量三类主要旅程和大型语料的成本、首次可用时间与人工负担 | 将单一领域结果直接推广为通用方案 |
| 工作知识与自适应处理 | 来源卡片、处理状态、本地检索、概览、问答/研究和组织候选 | 候选自动晋升、预设全局 Ontology |
| 人工路由与临时知识库 | KB 身份、Route Record、纠错流程和临时 KB 冷启动 | 模型最终路由、自动激活和可信写入 |
| 受控知识形成 | 风险分层审核、精确批准、可信写入、验证、结构迁移和回滚 | 未批准结构扩展和黑盒批量写入 |
| 知识工作产品化 | 将捕获、工作知识、研究、问答、学习、笔记、组织、图谱、编辑和维护组合进低摩擦界面 | 强制所有知识库使用同一组织模型 |
| 可选扩展 | GBrain 未审核镜像、QQ、远程、多设备和更完整交互 | 改变本地规范真源和信任边界 |

这张表定义产品范围和依赖关系，不表示当前实现进度，也不替代每个增量的详细 PRD。

## 5. 详细功能需求

### 阅读方式和成熟度

功能需求 ID 是稳定追踪标签，不表示优先级或实施顺序。

| 需求成熟度 | 含义 |
|---|---|
| `Approved Design / Ready` | 产品义务已经确认，对应 L1/L2 规范足以支持当前范围的实现和验收 |
| `Approved Design / Needs Detail` | 用户价值和治理边界已经确认，详细流程、交互或数据契约尚待设计 |
| `Draft` | 仍需实验或决策，不得直接据此实现正式产品能力 |

任何功能进入实现前，阶段/功能规范至少要补齐：用户角色、前置条件、触发、主流程、异常流程、业务规则、用户可见反馈、数据边界、依赖和验收标准。

### MVP-0 可靠捕获流程

| 操作 | 用户/调用方意图 | 成功结果 | 必须区分的异常 |
|---|---|---|---|
| `capture_text` | 保存一份新的原始文本和明确意图 | 返回稳定 Capture 身份、版本和可验证回执 | 输入无效、配置不可用、冲突、未提交、未知提交状态 |
| `get_capture` | 按身份读取当前或指定版本 | 返回精确元数据和完整正文 | 不存在、查询无效、规范事实损坏 |
| `list_captures` | 在受限条件下稳定浏览 Capture | 返回确定性排序、过滤和游标结果 | 查询无效、投影与规范事实不一致 |
| `append_capture_version` | 在已知当前版本基础上追加新版本 | 返回新的不可变版本和回执 | 幂等命中、幂等冲突、版本冲突、未知提交状态 |

MVP-0 的产品要求是可靠保存和证明事实，不是自动分类、路由、摘要或可信知识写入。机器字段、错误码和事务步骤以对应 L2 契约为准。

### 不可破坏的产品治理规则

下列稳定标签用于跨文档引用，不表示实施顺序。

| ID | 规则 |
|---|---|
| P1 | 立即保存只证明用户提交过什么，不证明内容已被正确理解、分类或策展。 |
| P2 | 语义计算可以自动；改变可信层含义、边界、结构或关系必须形成可复核对象。 |
| P3 | 模型不得静默改变用户目标、KB 边界、可信页面、稳定结构、发布状态或删除范围。 |
| P4 | 批准必须绑定具体条目、版本化批次、内容哈希或精确 diff；批准后不得重新生成不同正文。 |
| P5 | 自动机械操作必须确定、幂等、可检查，失败时不得留下半批准或半写入状态。 |
| P6 | 原始来源、可信知识和可重建派生结果按事实类别使用不同规范真源；派生系统不得反向覆盖。 |

| P9 | RAG 回答、摘要和候选图谱可以帮助理解，不因流畅或可检索而获得可信身份。 |
| P10 | 知识结构按需、渐进且可逆；没有 Schema、Taxonomy 或 Ontology 时仍可开始工作。 |
| P11 | 人工控制按风险和影响分层，系统必须先完成证据、冲突检查和精确变更准备。 |

## 7. 约束、依赖与主要风险

### 当前约束

- 首个产品范围是单用户、单设备、Windows、本地文件系统和文本输入。
- 本地规范事实必须在没有网络、GitHub 账号、模型账号和外部知识服务时仍可保存和恢复。
- 真实私人内容进入正式使用环境前，产品必须提供明确的初始化、备份、恢复和日志隐私方案。
- 当前已冻结的 Capture v1 身份、版本和事务不能被未来 UI、RAG、路由或图谱绕过。
- 模型输出具有不确定性，不能作为机械完整性、用户批准或语义正确性的替代证明。

### 外部依赖

| 依赖 | 必需性 | 失效时的产品行为 |
|---|---|---|
| Windows 本地文件系统 | 首个产品范围必需 | 无法满足当前可靠性声明时必须失败关闭 |
| 在线或本地模型 | 增强能力可选 | 捕获、读取、版本和恢复继续可用；研究与派生处理降级或暂停 |
| GBrain | 可选适配器 | 不影响本地规范事实；镜像和派生能力暂停 |
| Git/GitHub | 开发与可选版本协作工具 | 本地产品核心不得因此不可用 |
| QQ、远程 Agent、其他入口 | 可选适配器 | 对应入口不可用，不改变已有本地事实 |

### 主要产品风险

| 风险 | 可能后果 | 产品应对 |
|---|---|---|
| 人工审核过载 | 用户放弃审核或盲目批准 | 风险分层、批量决策、差异优先、审核预算和延期 |
| 模型生成流畅但错误 | 工作知识被误认为可信知识 | 来源、信任层、不确定性和候选隔离 |
| 大型语料检索遗漏 | 局部答案被误认为完整覆盖 | 查询偏置、检索边界、未处理范围和对照评测 |
| 过早建立复杂结构 | 冷启动困难、维护成本高 | 结构非前置、按需候选、版本化迁移 |
| 动态派生反向污染原件 | 规范事实失真 | 真源隔离、只读基线、可重建派生 |
| 文档与实现漂移 | 团队误判已实现能力 | 分层权威、追踪关系和自动文档检查 |
| 外部服务锁定 | 离线不可用、迁移困难 | 可替换适配器、本地真源和退出边界 |

## 8. 验收标准与发布条件

### 产品级成功信号

| 目标 | 应观察什么 | 不能用什么冒充成功 |
|---|---|---|
| 可靠接住输入 | 保存后字节和哈希可回读，重复请求不重复，崩溃后提交状态可证明，断网仍可用 | UI 显示成功或只有远端副本 |
| 保存后尽快可用 | 来源能够被找到、浏览、显示状态，并按策略形成检索、汇总或组织建议 | 文件存在但只能靠用户手工翻找 |
| 陌生领域可渐进学习 | 无预设 Schema 时形成有证据的概览、术语、争议、学习路径和候选结构 | 流畅回答或单次演示被当作理解正确 |
| 熟悉领域可快速维护 | 发现新增、重复、冲突、过时和结构差异，并形成精确可回滚变更 | 用户仍需逐页手工比对 |
| 大型语料可按需使用 | 检索边界、查询偏置和未处理范围可见，高价值内容逐渐稳定化 | 用局部问答暗示已经完整提取 |
| 人工控制不过载 | 首次可用时间、审核分钟数、批次大小、接受/修改/拒绝比例和纠错成本可测 | 要求逐条审核全部候选或取消可信闸门 |
| 证据与状态可审 | 回答、候选、关系和提案回到精确来源并显示信任层 | 把模型置信度、RAG 或图谱当作批准 |
| 组织方式适应任务 | 简单内容不被迫建立复杂本体，复杂领域可渐进形成稳定结构 | 页面、节点或层级越多就视为越好 |
| 知识可持续治理 | 用户能编辑、查看差异、维护关系、回滚批次和迁移结构 | Git 有提交就等同于业务批准 |
| 跨领域底座成立 | 多个代表领域和起点使用同一核心生命周期，差异由策略和提案承载 | 单个定制领域成功后宣称通用 |

### 功能进入实现前的就绪条件

一项功能只有在以下内容有权威位置后，才能视为需求就绪：

- 用户角色和用户价值；
- 范围内与范围外；
- 前置条件和触发；
- 主流程、异常流程和恢复路径；
- 业务状态和用户可见反馈；
- 数据分类、隐私和权限边界；
- 外部依赖和降级方式；
- 可执行验收标准；
- 仍未冻结的问题及其阻塞级别。

“产品方向已批准”不等于“功能已经需求就绪”。尚缺详细流程、交互或机器契约的长期能力不得直接进入正式实现。

### 阶段发布条件

每个阶段发布前至少必须满足：

1. 范围内需求有对应验收证据，范围外能力没有被暗示为已交付；
2. 正常、异常、边界、恢复和权限场景已覆盖；
3. 所有可能导致数据丢失、完整性破坏、越权或敏感泄露的已知阻塞缺陷已经关闭；
4. 适用平台和环境已真实验证，未验证平台不作支持声明；
5. 用户可理解当前内容属于来源、工作知识、提案还是可信知识；
6. 迁移、备份、恢复和退出边界与该阶段风险相匹配；
7. 尚未解决的问题、已知限制和降级行为已经公开记录。

详细测试步骤和缺陷分级由对应阶段的测试计划冻结，本文只规定产品级完成条件。

## 附录：编号与阅读原则

主 PRD 只直接维护三类稳定标签：

| 形式 | 用途 | 示例 |
|---|---|---|
| `FR-<能力域>-<序号>` | 功能性产品义务 | `FR-WORK-001` |
| `NFR-<质量域>-<序号>` | 可靠性、安全性、通用性等质量要求 | `NFR-LOCAL-001` |
| `P<序号>` | 不可破坏的产品治理规则 | `P12` |

编号不是优先级、实现阶段或阅读顺序。普通读者应先理解项目概述、用户旅程、统一业务流程和产品范围；只有在设计、验收或变更时才需要使用需求 ID。

设计决策、冲突记录、编码批次和测试场景拥有各自编号，但只在相应权威文档中解释，避免把所有命名空间带入主 PRD。
