## 1. 为什么先写这份文档

此前的产品目标、GBrain 集成方案、SOP 和交互设想分散在多份文档中，且部分文字把“设计设想”“已确认需求”和“已经实现”混在了一起。继续开发前，应先建立一份可审阅、可追踪的需求基线。

本文件承担四项职责：

1. 固定系统真正要解决的问题，避免项目退化为普通的知识库工具或 QQ 机器人。
2. 明确哪些写入可以自动执行、哪些必须先形成方案并由人确认。
3. 把深度策展、低摩擦捕获、机械维护放入同一条可解释的状态链。
4. 列出当前方案尚未解决或相互冲突的部分，供后续逐项确认。

## 2. 核心问题：知识策展悖论

本项目提出并试图缓解的“知识策展悖论”是：

> 高质量策展需要先充分理解材料，但充分理解往往又依赖持续整理、关联、使用和修订；如果入库门槛过高，灵感和原料会因为摩擦而流失，如果门槛过低或交给模型自动完成，知识库又会被不透明、不可控的语义判断污染。

系统不试图用一次模型调用“消灭”这个矛盾，而是通过分层、状态、人工闸门和可回滚版本，把矛盾变成可管理的流程：

- 捕获可以立即发生，不要求当场完成策展。
- 理解、分类、提炼和关系建立可以由模型辅助，但先产出可审方案。
- 可信知识的语义写入必须由人确认。
- 机器可自动完成无语义或可证明等价的机械操作。
- 所有变化都有来源、方案、批准对象、执行结果和 Git 历史可追溯。

## 3. 产品北极星与非目标

### 3.1 北极星

长期目标是形成一个可外置、可审计、可持续演化的“第二大脑”：

- 知识易捕获，不因当下无法分类而丢失。
- 深度材料能以高精度、先审后写的方式进入可信知识层。
- 临时灵感、对话和想法能低摩擦保存，再在合适时间审核和提升。
- 用户始终知道系统准备改什么、为什么改、批准后实际改了什么。
- 误操作和不满意的策展结果能够回滚。
- 检索、图谱、联想和自动分析服务于知识管理，但不能绕过治理边界。

### 3.2 非目标

- QQ 不是产品本体，只是验证低摩擦捕获和问答效果的一种可选入口。
- GBrain 不是可信知识的唯一真源，也不直接取得黑盒策展权限。
- Obsidian 不是必须复刻的宿主；目标是借鉴其本地 Markdown 交互体验，同时补足状态、权限、审核和回滚。
- 项目不追求“全自动整理一切”。自动化程度必须服从可解释、可批准和可恢复。

## 4. 不可破坏的治理原则

以下原则视为当前已经对齐的产品约束；若未来调整，必须形成显式决策记录。

### P1：立即保存不等于可信入库

用户原始表达、链接、文件或对话可以立即保存。立即保存只证明“原料已被捕获”，不证明它已经被正确理解、分类或策展。

### P2：语义计算可以自动，语义落库必须受控

模型可以自动做摘要、分类建议、关系发现、策展地图和变更方案，但这些结果只能进入派生层或提案隔离区。凡会改变可信知识的含义、边界、结构、关系或检索身份的写入，必须先提交方案，由人确认后执行。

### P3：禁止自动黑盒策展写入

系统不得让模型在后台自行决定并直接完成以下行为：

- 将原料提升为可信 wiki 页面。
- 改写已有可信页面的语义内容。
- 自动扩展知识库领域。
- 新建或合并知识库。
- 新增页面类型、关系类型、标签体系或模块。
- 将一个知识条目自动路由到某个知识库并视为最终归属。

### P4：批准必须绑定精确对象

人工批准的对象应是可复核的方案、具体条目或精确 diff，而不是一句宽泛的“方向同意”。批准后不得再让模型根据该方向重新生成另一版正文并直接写入。

### P5：机械操作可以自动，但必须确定、幂等、可重建

哈希、时间戳、格式校验、索引重建、引用扫描、确定性文件移动等不涉及语义判断的操作，可由规则引擎或硬编码执行。自动操作应满足：

- 同一输入重复执行不会产生额外副作用。
- 规则和结果可检查。
- 派生产物可以从真源重新生成。
- 失败时不会留下“半批准、半写入”的状态。

### P6：Markdown + Git 是可信内容与治理记录的规范真源

可信 wiki、原料档案、审核工件、结构规范和审计记录以本地文件为规范载体，并由 Git 提供版本、diff 和回滚能力。GBrain 负责捕获、索引、搜索、图谱和派生分析，但其可重建数据不得反向覆盖规范真源。

### P7：权限按状态授予，而不是一次性给 Agent 整库写权限

Agent 的权限至少区分捕获、提案、执行已批准变更、机械维护四类。处于临时状态的知识库不得获得正式发布、联邦检索或自动传播权限。

## 5. 四类内容与对应流程

| 情况 | 典型输入 | 初始落点 | 语义处理 | 可信入库方式 |
|---|---|---|---|---|
| 深度策展 | 长文、论文、研究资料、重要访谈 | 指定 KB 的 `inbox/`，再机械归档至 `raw/` | SOP-001 生成策展地图 | 人审核地图和精确变更后，由 SOP-002 执行 |
| 低摩擦捕获 | 临时灵感、随手想法、短对话、语音转写 | GBrain 的未审核捕获区；必要时同步原始副本到全局 Intake | 可自动生成摘要、候选标签和路由提案，但保持未审核 | 人选择忽略、保留为原料、提升到已有 KB 或创建新 KB |
| 外部资料收集 | URL、PDF、附件、剪藏 | 全局 Intake 或已明确 KB 的 `inbox/` | 抓取、转码、哈希可自动；分类和提炼只形成提案 | 路由确认后进入相应 KB，再走 SOP-001/002 |
| 机械维护 | 校验、断链扫描、索引、哈希、备份 | 派生区或审计日志 | 规则引擎执行 | 不改变语义时可自动；发现语义问题只报告或提案 |

“用户自己刚写下的原文”属于来源事实，可以立即保存；模型对原文作出的概括、归类和改写属于机器语义判断，不因保存入口低摩擦而自动获得可信身份。

## 6. 最小捕获与路由链路

### 6.1 先捕获，后决定归属

捕获时有三种情况：

1. **用户明确指定已有 KB**：先提交本地 Capture Store 原件并记录用户意图；本地保存成功后，确定性路由步骤才把它呈现在该 KB 的 `inbox/` 逻辑队列并按批准方式归档。
2. **归属未知或存在多个候选 KB**：先提交同一个本地 Capture Store；它通过 Global Intake 逻辑查询呈现，不创建第二份 Intake 原件，模型只能提交路由建议。
3. **用户明确要求新建 KB**：仍先提交本地 Capture Store；确认创建意图和名称后执行 SOP-000A，建立无领域承诺的临时骨架，再路由捕获项。

系统不得因为模型认为“像某个领域”就自动新建知识库，也不得把未知归属原料直接塞入某个可信 KB。

### 6.2 不是所有捕获都先走 SOP-000

- 捕获到全局 Intake：不需要先执行 SOP-000。
- 捕获到已有 KB：不需要再次执行 SOP-000。
- 只有“创建一个新的 KB 容器”才执行 SOP-000A。
- SOP-000A 只创建最小临时骨架，不提前虚构领域、标签或页面类型。
- 第一份有代表性的原料进入临时 KB 后，执行 SOP-001；其策展地图同时提出领域与 SCHEMA 建议。
- 人工确认领域和结构方案后，再执行后续待定义的 SOP-000B，将 KB 从 `provisional` 激活为 `active`。

### 6.3 最小状态机

```text
捕获
  ├─ 已明确已有 KB ──> KB inbox ──> raw ──> 策展提案
  ├─ 归属未知 ───────> Global Intake ──> 路由提案 ──> 人确认
  └─ 明确新建 KB ───> SOP-000A ──> provisional KB
                                           │
第一份代表性原料 ──> SOP-001 策展地图 + 领域/SCHEMA 建议
                                           │
                                      人工确认
                                           │
                                  SOP-000B（待定义）
                                           │
                                        active KB
```

## 7. 隔离区的用途

隔离区不是“另一个正式知识库”，也不只保存一份笼统方案。它保存所有**已经生成、尚未获准改变可信知识**的语义工件，例如：

- `routing/`：建议进入哪个已有 KB，或是否建议新建 KB。
- `curation-maps/`：对长文、论文等原料的策展地图。
- `promotions/`：把灵感、捕获页或原料提升为可信知识的候选内容。
- `changes/`：对现有 wiki、SCHEMA、关系或标签的精确变更方案/diff。
- `maintenance/`：模型发现重复、冲突、过时内容后提出的处理方案。

隔离区具有以下性质：

- 内容可以由模型自动写入，但默认状态必须是 `pending`。
- 隔离区内容不能被检索层当作已确认知识返回，必须在查询结果中明确标识。
- 拒绝的方案可归档或删除，但审核记录应保留。
- 批准的是具体版本；方案变化后原批准自动失效。
- 执行结果和批准版本不一致时，事务应失败，而不是静默接受漂移。

旧版 `raw/_curation-maps/` 把“不可变原料”和“可编辑提案”混在一起，职责冲突。新流程已经确定使用 `proposals/curation-maps/`；已有知识库的旧目录只在实际迁移前保留兼容读取，不再作为新产物路径。

## 8. 系统组件的职责边界

| 组件 | 主要职责 | 不应拥有的权限 |
|---|---|---|
| KnowledgeFlow | 治理规则、状态机、审核、精确执行、审计与回滚 | 不把模型判断伪装成确定性规则 |
| LLM Wiki / SOP | 深度原料的穷举提取、策展地图、受控写入和质量检查 | 未经批准直接策展入库 |
| GBrain | 低摩擦捕获、混合检索、图谱、派生分析、审核队列承载 | 将未审核内容自动提升为可信知识；覆盖 Markdown 真源 |
| DeepSeek Harness | 对话交互、工具编排、模型调用和执行会话 | 持有无边界整库写权限；批准后重新自由发挥 |
| Git | 版本、diff、审计、恢复和发布检查点 | 替代业务状态机或人工批准 |
| QQ 等入口 | 快速捕获、通知、简单查询和验证使用习惯 | 成为唯一入口或决定核心架构 |

## 9. 写入权限矩阵

| 操作 | 可否自动 | 说明 |
|---|---|---|
| 保存用户原始文本或附件 | 可以 | 写入未审核捕获层，保留原始内容和来源 |
| 抓取网页、转码、计算 SHA256 | 可以 | 规则确定且保留来源；抓取失败需显式报告 |
| 生成摘要、标签、关系、路由建议 | 可以生成 | 只能写入派生层或提案隔离区 |
| 将原料归到某个 KB | 条件允许 | 用户在捕获时明确指定可直接归入；模型推断必须待确认 |
| 新建 KB | 不可由模型自行决定 | 用户确认后由 SOP-000A 机械执行 |
| 修改 SCHEMA、领域、标签或关系类型 | 不可以直接执行 | 先给出精确变更方案，再由人确认 |
| 新建或改写可信 wiki 页面 | 不可以直接执行 | 先审策展地图，再审精确写入对象或 diff |
| 重建索引、embedding、图谱缓存 | 可以 | 只能作用于派生层，且应可从真源重建 |
| 自动修复格式、排序、规范化 | 视规则而定 | 只有能证明不改变语义的规则才可直接执行 |
| 回滚已批准批次 | 用户触发或策略触发 | 回滚对象必须是明确批次/commit，保留审计记录 |

## 10. 审核对象与执行约束

深度策展至少需要两个不同层级的确认：

1. **策展地图审核**：确认有没有遗漏、误读，哪些条目应入库，领域和 SCHEMA 建议是否合理。
2. **精确变更审核**：确认将创建、修改、移动或删除哪些文件，以及每个文件的具体内容或 diff。

执行器只消费“已批准且版本未变化”的变更集。建议每个批准批次至少记录：

- `proposal_id`
- 原料哈希和当前 KB 基线 commit
- 方案版本或内容哈希
- 审核人、审核时间和审核范围
- 允许的文件路径及操作类型
- 执行 commit
- 校验结果和可回滚点

## 11. 状态、审计与回滚

建议最小状态链为：

```text
captured -> pending-routing -> routed -> pending-curation
         -> pending-approval -> approved -> applying
         -> applied -> verified
```

旁路状态至少包括 `rejected`、`needs-revision`、`failed`、`rolled-back` 和 `archived`。

Git 负责文件版本，但不能单独表达全部业务状态，因此还需要提案元数据和审核日志。一次批准应尽量对应一个原子 commit；若执行或校验失败，不发布半成品，并回到可重试状态。

### 11.1 “每个 KB 独立 Git”是什么意思

它指每个知识库根目录都有自己的 `.git/`、提交历史、分支和回滚边界，而不是所有知识库共用项目顶层的一个 Git 仓库：

```text
knowledge-hub/                 # 可选：只保存 KB 注册表和全局 Intake
├── registry.yaml
├── intake/
└── knowledge-bases/
    ├── agent-learning-智能体学习/
    │   ├── .git/             # KB A 的独立历史
    │   └── kb.yaml
    └── job-dui-酒驾案件/
        ├── .git/             # KB B 的独立历史
        └── kb.yaml
```

与此相对，父级统一 Git 只有 `knowledge-hub/.git/`，下面所有 KB 都由同一份历史管理。

| 方案 | 优点 | 成本/限制 |
|---|---|---|
| 每个 KB 独立 Git | 回滚、权限、同步和备份边界清晰；可单独迁移或映射为一个 GBrain source | 仓库数量多；批量管理更复杂；跨 KB 变更不能天然形成一个原子 commit |
| 父级统一 Git | MVP 最简单；一次提交可同时更新多个 KB 和全局注册表 | 权限和历史耦合；单库分享、迁移和恢复的边界较弱 |

“每个 KB 独立 Git”目前只是候选架构，不是已经确认或实现的需求。在 Git 拓扑正式定案前，SOP-000A 不应擅自在现有项目中创建嵌套 `.git/`。

## 12. 文件与目录命名基线

### 12.1 可采用“英文名-中文名”的范围

技术上可以采用 `english-name-中文名`，并建议从新建的人类可读设计文档和 KB 根目录开始，例如：

- `requirements-and-governance-baseline-需求与治理基线.md`
- `sop-000a-provisional-kb-bootstrap-临时知识库骨架初始化.md`
- `agent-learning-智能体学习/`

英文部分应使用稳定的 `kebab-case`，中文部分用于快速识别。KB 的真实身份应由稳定 `kb_id` 表示，不能把目录名当作永久主键。

### 12.2 不应强制改名的机器契约

以下名称属于工具、生态或协议契约，应保留标准英文形式：

- Git/开发生态：`.git/`、`.gitignore`、`.github/`、`README.md`、`LICENSE`、`package.json`、`pyproject.toml` 等。
- KnowledgeFlow 固定契约：`kb.yaml`、`SCHEMA.md`、`index.md`、`log.md`。
- 固定系统目录：`inbox/`、`raw/`、`wiki/`、`schema/`、`proposals/`、`_archive/`。
- 代码模块、导入路径和命令入口：原则上保持稳定英文名。

这些路径可在 UI 和文档中显示中文标签，例如把 `proposals/` 显示为“提案隔离区”，无需修改磁盘契约。

### 12.3 不建议“一次性全部重命名”

现有文件之间存在 Markdown 链接、脚本路径、测试夹具、Git 历史和外部集成约定。批量重命名可行，但应作为独立迁移处理：

1. 先生成旧路径到新路径的完整映射表。
2. 标出机器契约和保留项。
3. 使用 `git mv` 分批迁移。
4. 更新所有链接、脚本、配置、测试和文档引用。
5. 运行全量测试和链接检查。
6. 用单独 commit 保存迁移，便于整体回滚。

当前阶段只对新文档应用双语命名，不批量改动现有路径。

## 13. 当前确认度

### 13.1 已由用户明确的需求

- 项目核心是解决或缓解知识策展悖论。
- 深度长文走策展地图和先审后写。
- 临时灵感等低摩擦内容先无门槛保存到本地 Capture Store；“GBrain 先写后审”在当前设计中解释为保存后可选异步镜像到 GBrain 未审核范围，而不是由 GBrain 先落规范原件。
- 不涉及语义的机械任务可由规则引擎或硬编码自动完成。
- 涉及语义的可信写入必须先提交方案，由人确认。
- 不允许自动黑盒策展写入。
- 需要类似 Obsidian 的低摩擦交互，但必须补充状态、权限和回滚。
- QQ 只是可选验证入口，长期目标是外置第二大脑。
- 可以立即保存原料，但新 KB 应先建立最小骨架，领域和结构可后置确认。
- 先把需求和流程写入 Markdown，再继续实现。

### 13.2 已确认的治理设计

- 使用 Global Intake 逻辑队列呈现尚未分配 KB 的本地 Capture Item，不另建第二份捕获原件。
- 将 `proposals/` 作为语义工件隔离区，并从 `raw/` 分离策展地图。
- 将 SOP-000 拆为 SOP-000A（临时骨架）和 SOP-000B（审核后激活）。
- 使用 `kb.yaml` 记录 KB 的机器身份和生命周期。
- 机器契约名称作为双语命名规则的明确例外。
- 本地 Capture Store 是第一规范原件；Global Intake 是未分配 Capture Item 的逻辑队列。
- GBrain 是可选异步未审核工作层，不承担唯一原件。
- MVP-0 先限制为单机、单用户、文本捕获。
- 当前机器 `capture-root` 确认为 `E:\KnowledgeFlowData\capture-store`；通用代码读取每机配置，最终解析为绝对路径，内部原件只记录可迁移的相对路径。
- 文本 4 MiB 是内联阈值、64 MiB 是可配置默认安全上限；超限不得截断、摘要或自动拆分 Capture Item。

### 13.3 仍后置到对应功能前的架构选择

- 每个 KB 是否使用独立 Git 仓库，仍作为架构选项而非既定事实。
- 非文本文件大小上限、大文件对象存储、敏感内容加密和保留周期。
- GBrain 远程身份、多设备同步、QQ 和完整编辑器形态。

## 14. 与当前文档/流程的主要冲突

以下冲突的当前裁决由[设计权威与冲突登记](design-authority-and-conflict-register-设计权威与冲突登记.md)统一记录；“已裁决”不表示旧文件已经全部完成迁移：

1. 现行 [SOP v2 完整文档](sop-v2-full.md) 的 SOP-000 要求先确认领域并立即创建完整 `SCHEMA.md`，与“先建无领域承诺的临时骨架”冲突。**已裁决：冷启动以 SOP-000A 为准。**
2. 现行 SOP-001 声称支持 `SCHEMA.md` 不存在的情况，但 SOP-000 和 SOP-002 又把 SCHEMA 存在作为前置条件，冷启动分支无法完整闭环。
3. 策展地图当前放在 `raw/_curation-maps/`，与 `raw/` 不可修改、原料与提案分层的原则冲突。**已裁决：新流程使用 `proposals/curation-maps/`，待重构 SOP-001。**
4. 现行 SOP-002 允许 Agent 自动扩展领域、注册标签和模块，与“所有语义结构变更先提案后确认”冲突。**已裁决：旧自动写入授权暂停，待重构 SOP-002。**
5. 当前 [GBrain 集成方案](gbrain-integration-plan.md) 中仍存在“未审核内容是否会进入检索”的待确认项。**已裁决：GBrain 只作异步未审核工作层，接入前必须完成查询隔离实证。**
6. 项目文档中部分路线把 QQ 入口或 GBrain 能力写得接近产品主线。**已裁决：二者分别降级为可选入口和可替换工作引擎。**
7. 当前项目尚未形成可执行的权限矩阵、批准版本绑定、事务提交和回滚协议。**版本绑定原则已由 Capture Envelope 确认，其余仍是可信写入门禁。**
