## 1. 结论

P0 不是“把测试路径换成 E 盘然后开始使用”，而是把已经验收的捕获内核安全地变成第一个可真实使用、可备份、可恢复、可理解的本地产品增量。

P0 只验证“低摩擦本地文本捕获与收件箱”这一条首要旅程：用户不接触机器协议或 Store 文件，也能保存、找回、阅读和续写文本，并理解当前状态、警告和失败。P0 不验证搜索、研究、RAG、图谱、路由或可信知识形成，也不得把捕获底座的可靠性冒充为整个 KnowledgeFlow 的产品价值已经成立。

当前内核已经能够初始化 Store、执行四个文本操作、重建派生状态和迁移 Store，但仍缺少三类生产闭环：

1. 面向操作者的初始化、校验、备份和恢复路径；
2. 只暴露现有 Capture 能力的最小收件箱；
3. 真实内容使用、重启、备份恢复和人工体验证据。

因此采用以下顺序：

```text
P0A 方案与只读预检（已完成）
  → P0B 最小生产管理能力与临时 Store 演练
  → P0C 最小收件箱在临时 Store 上实现和验收
  → P0D 明确授权后初始化生产 Store 并建立首份可验证备份
  → P0V 真实 dogfood、问题登记和限定状态复核
```

在 P0B 和 P0C 均通过之前，不初始化真实生产 Store。这样不会让真实私人内容先进入一个尚无可靠备份路径或可用界面的环境。

P0B 只建设首次 dogfood 所需的最小冷备份闭环，不建设通用备份平台；P0C 只建设一个薄的用户垂直切片，不继续扩展捕获内核。两批都必须以尽快取得真实使用证据为约束。

## 4. 术语与边界

| 术语 | P0 中的精确定义 |
|---|---|
| 生产配置 | 当前 Windows 用户实际使用的唯一配置文件；不是仓库样例或测试配置 |
| 生产 Store | 承载用户真实 Capture 规范事实的本地 Store；“生产”只表示含真实数据，不表示产品已经生产就绪；测试临时目录不属于生产 |
| 最小收件箱 | 只提供捕获、列表、读取和追加版本的本地交互层，不做语义处理或可信写入 |
| P0 待处理视图 | 对仍为 `unassigned` / `unreviewed-capture` 的 Capture 作出的界面分组；不是新的持久状态，也不等于内部 outbox 的 `pending` |
| dogfood | 用户用真实但自行选择的内容持续使用最小收件箱，并记录故障、理解成本和操作负担 |
| 备份 | 在明确一致性边界下形成可独立验证、可恢复的第二份副本；迁移和派生重建都不是备份 |
| 恢复演练 | 不覆盖生产源，在新的空目标上重建可打开的 Store 并证明关键事实等价 |
| 回退 | 停止新入口、保留规范原件和证据；不把“删除生产 Store”当作默认回退 |

## 5. P0 硬边界

### 5.1 必须保持

1. 单机、单用户、Windows-first、文本捕获、本地优先、离线可用。
2. 捕获正文和所有规范事实继续以 Capture Store 为真源。
3. 最小收件箱只能经过已有四操作的公共边界或其一对一受限适配层，不能直接写 Store 文件、导入私有事务函数或复制事务逻辑；究竟采用进程内公共 API 还是机器 CLI，由 P0C 的最小技术比较决定。
4. 管理能力与日常四操作分离；初始化、备份、恢复、重建和迁移不能伪装成普通捕获请求。
5. 所有生产写入必须使用受信安装上下文构造的 `PathPolicy.production`，不能从 UI、JSON 或环境变量打开测试能力。
6. 日志、stderr、崩溃报告和遥测不得包含正文、preview、幂等键、完整本机路径或配置字节。
7. 已提交版本不可覆盖；未知对象、外来目录、reparse point 和无法证明归属的数据不得自动删除。
8. P0 运行不依赖 GitHub 登录、网络、模型账号、GBrain 或任何云服务。
9. P0 不提供应用层静态加密；P0D 前必须明确实际依赖的 Windows 账户、NTFS ACL、卷加密和备份介质保护，并据此限定允许进入 dogfood 的内容敏感度。
10. P0 没有产品级删除或安全擦除能力；第一次真实捕获前必须明确提示追加保存、备份复制和退出边界，不能让用户误以为界面关闭或停止 dogfood 等于删除数据。

### 5.2 本阶段不做

- 不实现自动摘要、标签、embedding、RAG、图谱或语义路由。
- 不创建或激活知识库，不运行 SOP-000A/SOP-001/SOP-002。
- 不接入 GBrain、QQ、浏览器扩展、移动端或多设备同步。
- 不提供删除 Capture、原地修改历史版本或批量清理生产数据。
- 不把收件箱做成完整 Obsidian 式编辑器。
- 不为“看起来方便”把初始化或测试路径开关加入现有四操作 CLI。
- 不建设定时调度、增量/去重备份、保留策略、备份管理 UI、云同步或跨平台备份框架。
- 不把同卷复制称为磁盘故障备份，也不把一次 CI 成功称为生产长期运行证据。

## 6. 候选生产配置

以下是 P0A 推荐值，不因本文形成而自动生效：

```yaml
schema: knowledgeflow.local-config
version: 1
capture:
  root: 'E:\KnowledgeFlowData\capture-store'
  inline_text_threshold_bytes: 4194304
  max_text_version_bytes: 67108864
```

候选配置路径为：

```text
%LOCALAPPDATA%\KnowledgeFlow\config.yaml
```

两个阈值沿用已经实现和验收的 4 MiB / 64 MiB 默认值。P0 不以真实内容为理由临时改变阈值；确需变更时必须单独说明兼容性、资源和既有版本影响。

P0D 前仍需用户逐项确认：

- 精确配置路径；
- 精确 Store 路径；
- 备份目标及其物理介质；
- 是否允许创建尚不存在的两个父目录；
- 用于首次真实捕获的内容由用户选择，而不是自动写入“测试数据”。

## 7. 备份、恢复和退出策略

### 7.1 最小冷备份语义

P0B 必须先冻结并验证以下语义：

1. 备份在没有活动写入的受控窗口中执行，并以 Store 写锁或等价的已证明排他边界保证一致性。
2. 备份先完整验证规范事实，再复制；不能复制到一半就宣称成功。
3. 复制使用有界 I/O，目标只能是新建空目录或可证明为同一备份作业的兼容续传目标，绝不覆盖陌生非空目录。
4. 成功结果至少绑定源 `store_id`、源配置阈值、备份时间、文件集合、字节数和内容哈希。
5. `.staging`、锁文件、派生状态和逻辑不可见尾部是否进入备份，必须由 P0B 契约显式规定，不能靠人工挑文件。
6. 备份目标与生产 Store 具有相同隐私级别；日志不得输出正文和完整路径。
7. 如果备份位于同一物理磁盘，必须标记为“操作副本”，不能声称防磁盘损坏；真正的磁盘故障保护需要另一物理介质。

P0B 的完成条件止于“显式初始化、只读完整校验、一致性冷备份、恢复到新目标”四类能力及其临时 Store 证据。自动计划、历史保留、增量同步、压缩、加密封装、远端上传和日常管理界面均不属于 P0B。

### 7.1A P0B-min 管理入口契约

P0B-min 使用独立安装入口 `knowledgeflow-capture-admin`，不向日常 `knowledgeflow-capture` 增加第五个操作，也不改变四操作的帧协议。入口只接受以下四种精确形式：

```text
knowledgeflow-capture-admin init --config <绝对本地路径> --store <绝对本地路径> [--inline-threshold <正整数>] [--max-version <正整数>]
knowledgeflow-capture-admin verify --config <绝对本地路径>
knowledgeflow-capture-admin backup --config <绝对本地路径> --target <绝对本地路径>
knowledgeflow-capture-admin restore --backup <绝对本地路径> --target <绝对本地路径>
```

固定边界如下：

1. 选项顺序可变，但不得重复、不得出现未知选项，也没有隐式默认配置路径；`init` 的两个阈值默认仍为 4 MiB / 64 MiB。
2. 安装入口只在可信代码中构造 `PathPolicy.production`；命令行、环境变量和 JSON 都不能打开测试目录能力。测试只能通过不安装的私有 runner 注入 `PathPolicy.test_owned`。
3. stdout 在公共成功或公共失败时只输出一行规范 JSON，schema 固定为 `knowledgeflow.capture-management-response` v1；回执不含正文、preview、幂等键、配置字节或完整路径。
4. exit `0` 表示完整成功 JSON，exit `2` 表示完整公共失败 JSON；内部异常、回执路径泄露或输出失败固定 exit `1` 且 stderr 只允许固定 `knowledgeflow-capture-admin: internal failure`。exit `1` 时 stdout 不可信，调用方必须整体丢弃。
5. `init` 只显式初始化或幂等重开所选 Store；`verify` 在 Store 写锁内完整验证不可变事实、当前派生状态和稳定树摘要，不修复、不重建、不切换配置。
6. `backup` 和 `restore` 都是显式一次性管理动作，没有调度器、自动发现、自动清理、断点续传、保留策略或配置切换。

### 7.1B Backup Bundle v1 与失败语义

一个成功备份目录只允许两个直接子项：

```text
<backup-root>/
├── backup.json
└── capture-store/
```

`backup.json` 使用严格、规范、重复键拒绝的 `knowledgeflow.capture-backup` v1 JSON。它绑定 `backup_id`、创建时间、源 `store_id`、Store schema/layout 版本、4/64 MiB 等实际阈值、规范相对目录集合、每个文件的字节数与 SHA-256、总目录/文件/字节数以及整个快照元数据摘要。Manifest 最后写入；缺少 Manifest 的目录永远不是成功备份。

内容选择固定为：

- 不可变 Capture/Version/Envelope/Event/Payload 和当前派生状态进入备份；
- `.staging/` 目录骨架保留，但其全部内容排除；
- `journal/capture-write.lock` 排除；
- 逻辑不可见、但仍属于 Store 现场的唯一未提交版本尾部进入备份，恢复后继续由四操作按既有规则隐藏或处理；
- 任何 reparse point、未知类型、完整性损坏、需重建的派生状态或不受支持 schema 都使操作失败关闭。

P0B-min 采用比“兼容续传”更窄的规则：备份与恢复目标的父目录必须已经存在且是普通目录，目标叶目录在开始时必须不存在，哪怕已经存在但为空也拒绝；中断、空间不足或竞争留下的部分目标保留为证据，不自动删除、不自动续传，重试必须选择新的不存在目标。备份在源 Store 写锁内先验证、再以不超过 1 MiB 的块复制、再验证目标并最后写 Manifest。恢复先验证整个 Bundle，再在锁边界内复制到新目标并完整回读，且永不切换任何配置。

`protection_scope` 固定为 `operational-copy`：它证明的是可验证恢复副本，不声称同盘副本能抵御整盘损坏。真实备份介质、ACL、卷加密和内容敏感度仍必须到 P0D 精确确认。

### 7.2 恢复演练

恢复不得覆盖当前生产源。固定方向是：

```text
已验证备份
  → 新的空恢复目标
  → 完整字节与机器契约校验
  → 四操作只读/写入组合验收
  → 形成恢复报告
  → 默认不切换生产配置
```

只有用户另行明确批准，才允许把配置切换到已验证恢复目标。失败时保留生产源和失败证据，不自动删除无法证明归属的目标。

### 7.3 回退原则

- 管理入口失败：不启动收件箱，不自动改配置。
- 初始化失败：按既有初始化事务重试；不得手工删除未知残片。
- 收件箱失败：停止界面进程，Store 仍可由既有四操作读取；不回滚已提交 Capture。
- 备份失败：生产配置和 Store 不变，失败目标隔离等待人工判断。
- dogfood 停止：保留生产配置、Store、备份和问题记录；删除真实数据必须另有专门设计与明确授权。

### 7.4 隐私、保留和退出告知

P0B/P0C 只使用测试持有的临时 Store，不接收真实私人内容。P0D 前必须形成一份面向用户的短告知并获得确认，至少说明：

1. 当前正文以本地明文文件保存，应用本身不提供静态加密；实际保护依赖已确认的 Windows 账户、ACL、卷加密和物理设备边界。
2. 备份与源 Store 具有相同敏感等级；未确认保护能力的介质不得接收真实备份。
3. 当前没有产品级单条删除、安全擦除或自动保留期；历史版本、备份和审计副本不会因界面关闭而消失。
4. 停止 dogfood 的默认动作是停止入口并保留原件；若用户要求导出、迁移或删除，必须另行设计可复核步骤并精确授权。
5. 用户应只选择其接受在上述边界下保留的内容作为首批 dogfood 数据。

更完整的导出、保留、删除和加密能力属于后续产品数据生命周期设计；P0 的公开限制不能被解释为这些需求永久不重要。

## 8. 最小收件箱产品契约

### 8.1 角色与主流程

P0 只有一个本机用户角色，不建立账号、组织或权限后台。最小主流程是：

```text
启动并检查配置
  → 浏览 Capture 收件箱（当前均为未分配、未审核）
  → 新建文本 Capture
  → 打开并完整读取某一 Capture
  → 基于当前版本追加一个新版本
  → 查看成功回执、警告或可行动错误
```

配置缺失时，界面只能显示“尚未初始化”和下一步说明，不能自行创建目录或静默初始化。

### 8.2 必须具备的界面能力

| 能力 | 最小行为 | 明确不包含 |
|---|---|---|
| 捕获 | 输入非空 UTF-8 文本，调用 `capture_text`，显示 Capture ID、版本和提交状态 | 自动摘要、分类、模型调用 |
| 收件箱 | 使用稳定分页列出 preview、时间、版本、`unassigned` 和 `unreviewed-capture`；可用“未分配”“待处理”作用户文案 | 新增 `processing_status`、复用 outbox `pending` 或本地自造第二套状态 |
| 阅读 | 调用 `get_capture` 展示完整正文、版本、哈希和 warning | 绕过核心读取直接打开 Store 文件 |
| 续写 | 显示当前版本，以该版本调用 `append_capture_version` | 覆盖旧版本、无 CAS 的静默保存 |
| 错误 | 区分输入错误、冲突、未提交、未知提交状态和完整性失败 | 向用户展示 traceback、底层路径或正文日志 |
| 警告 | 明确展示投影需重建、未完成尾部被忽略等警告，并给出停止/管理建议 | 把 warning 隐藏成成功无事发生 |

P0 没有独立的用户处理状态机。“未分配”精确对应 `routing_status=unassigned`；“待处理”只是对尚处于 `trust_status=unreviewed-capture` 的 Capture 的界面分组和通俗提示。它不写入新字段，不表示后台任务已经排队，也不得映射为 Store 内部预留的 `outbox/pending` 目录。

### 8.3 幂等和客户端崩溃边界

- 每次写操作必须在调用核心前生成稳定幂等键；同一次重试必须复用该键。
- P0C 首版只在界面进程存活期间保留正文、请求参数和稳定幂等键；明确重试必须复用同一组内容与 key。
- 返回 `unknown` 时，界面必须保留本次编辑状态并引导用户使用同一请求重试或先刷新核对；不得自动换新 key 重发。
- P0C 首版不建立持久客户端正文副本、草稿库或请求 outbox。界面进程异常终止后不得自动重发上一请求；用户必须先刷新收件箱并人工核对，再决定是否重新提交。
- “跨重启不能自动恢复草稿或证明上一请求身份”必须在首次使用说明和 dogfood 限制中公开。P0V 根据真实摩擦再决定是否值得引入受治理的持久草稿/请求日志。

### 8.4 技术选择停点

P0A 只冻结交互和安全边界，不提前锁定 Tk、WebView、localhost Web 或其他界面框架。P0C 编码前必须用一个很小的技术比较回答：

1. 是否引入新的运行时依赖或常驻服务；
2. 如何在 Windows 上安装、启动和退出；
3. 在进程内公共四操作与既有机器 CLI 之间选择哪种一对一适配方式，且不导入私有实现、不直接读写 Store、不复制协议或事务；
4. 如何测试正文不进入参数、日志或临时泄漏路径；
5. 如何保持完全离线，且不要求 GitHub 账号。

选择结果进入 P0C 小批次，不回写主 PRD 成为永久技术约束。

#### P0C 最小技术比较与本批选择（2026-10-01）

| 候选 | 运行与安装代价 | 正文/故障边界 | 本批结论 |
|---|---|---|---|
| Tk 桌面窗体 + 进程内公共 API | Python Windows 安装通常自带 Tk；不增加依赖、端口或常驻服务，console entry 启动、关闭窗口退出 | 正文只在 Tk/Python 进程内；直接使用四个公共结果模型，不需要重新实现机器帧或磁盘 spool | **选用**；最窄、完全离线，适合先取得 dogfood 证据 |
| Tk/WebView + 四操作机器 CLI | 仍需桌面壳，并为每次调用启动子进程 | 已有协议安全，但 UI 还需实现帧、exit 70、输入/输出 spool 和进程生命周期，重复一层适配复杂度 | 本批不选；保留给未来跨进程隔离确有价值时再评估 |
| localhost Web | 浏览器交互灵活 | 需要 HTTP 服务、端口/来源/CSRF/进程退出等新增安全面，即使只绑定 loopback 也扩大 P0 | 本批不选 |
| WebView/第三方 GUI 框架 | 可提供更完整视觉与前端生态 | 引入新运行时或依赖、打包和升级链，当前价值证据不足 | 本批不选 |

本批因此注册安装入口 `knowledgeflow-inbox`，只接受默认配置、显式绝对 `--config` 和 `--help`。受信入口构造生产 `PathPolicy`；测试经未安装的对象注入使用临时 Store。界面适配层只调用 `capture_text`、`list_captures`、`get_capture`、`append_capture_version`，不导入私有事务函数、不解析或直接写 Store、不复制 CLI 帧协议。

正文不会进入命令行参数、stdout/stderr、日志或磁盘临时文件：新建/追加正文由进程内 `str` 传入公共操作，读取正文由进程内 `BytesIO` 接收后展示。公共错误和 warning 转为固定、不含路径与正文的用户文案；未捕获的写入适配异常保守转为 `unknown` 并保留当前进程内请求。由于本批不经过机器 CLI，exit 70 不再是 UI 传输态；其等价风险是“调用未返回可验证结果”，同样按 `unknown` 处理。

每次写入在调用核心前生成稳定 key。同一进程中的显式重试复用完整正文、目标版本和 key；`unknown` 时编辑区锁定，先刷新/回读核对后才允许明确放弃。关闭或崩溃会丢失这份客户端状态，启动后绝不自动重发。Tk 视图保持为可替换薄壳；这一选择不是主 PRD 的永久技术约束。当前 I/O 在界面线程同步执行，较大正文操作可能短暂冻结窗体，留给 P0V 以真实摩擦决定是否增加受控后台执行。

#### 可移植性分层

P0D 要求在执行时确定精确路径，是把通用能力绑定到当前机器，而不是把盘符写进业务内核。必须保持以下四层分离：

| 层级 | 本层负责 | P0D 边界 |
|---|---|---|
| 可移植核心契约 | 新目标、零覆盖、有界复制、Manifest 最后提交、完整回读、失败关闭 | 不感知 `E:`、NTFS、BitLocker 或具体用户名 |
| 平台 Profile | 把核心能力映射到当前操作系统的路径、链接、权限、卷和耐久性事实 | P0 只验收 Windows Profile；NTFS、ACL、reparse、BitLocker 是当前平台检查，不是永久跨平台要求 |
| 本机部署绑定 | 为 `RUNTIME`、`CONFIG`、`STORE`、`BACKUP-1` 选择本机实际绝对路径和允许创建的目录 | 精确值仅用于本地预检、用户授权和执行；不硬编码进源码、公共 schema 或共享项目文档 |
| 脱敏证据 | 记录角色、代码/包版本、结果、保护范围和已知限制 | Git 中只写角色别名与结论，不写私人绝对路径、正文或凭据 |

未来 Linux/macOS Profile 可以把相同核心契约映射到挂载点、POSIX 权限、符号链接和相应卷加密能力，而不改变 Capture 或 Backup Bundle 的身份与验证语义。P0D 不负责实现这些未来 Profile，也不得把“架构可迁移”写成“当前实现已经跨平台”。

备份物理关系是保护能力的声明，不是盘符规则：

- `operational-copy` 允许目标与 Store 同一物理磁盘，或物理关系经过尽力探测后仍未知；它只能声称防文件级损坏、部分误操作和可恢复性问题，不能声称防整盘故障。
- `device-failure-protected` 只有在另一物理介质得到确认且其权限、加密和可用性满足要求时才允许声明。
- 物理关系未知本身不阻塞最低 dogfood；如果用户接受 `operational-copy`、相应明文风险和内容敏感度限制，可以继续。只有用户要求防整盘故障却无法证明独立物理介质时，才严格阻塞 P0D。

| 输入 | 约束 | 未确认时的结果 |
|---|---|---|

#### 固定执行检查点

P0D 只能按以下检查点串行执行；每个检查点输出脱敏结论并停下来判断是否继续，后一步不得用来补救前一步的失败：

1. **P0D-P1 只读预检**：确认 Git 与运行时代码基线、工作树状态、Python/依赖、非 editable 安装方案、候选路径现状，以及当前 Windows Profile 可取得的卷类型/空间/健康、ACL、reparse、加密、备份物理介质和竞争进程。此步仍然零生产写入；无法可靠取得的保护事实必须标记为未知，不得猜测。
2. **P0D-P2 精确授权**：向用户提交 P1 结果和本节授权模板。只有所有占位符被精确值替换并得到明确确认后，才允许任何生产写入；“继续”“下一步”或批准 P0D-0 均不能替代。

#### 失败关闭与保留原则

出现以下任一情况必须停止在当前检查点：代码/包来源不一致，工作树或安装来源无法说明，候选目标出现陌生对象，路径含 reparse point，当前 Windows Profile 的卷/空间/权限事实与授权不符，要求 `device-failure-protected` 却只能证明同盘或物理关系未知，发现竞争进程，管理入口返回 exit 1/2，初始化或备份结果不明，或用户没有明确接受已知/未知保护事实对应的内容与保留限制。

停止时保留既有生产源和可归属失败证据，不自动重试、不换目标伪装成功、不删除未知或失败残片、不切换配置。任何清理、恢复目标创建或授权值变更均另行复核。
