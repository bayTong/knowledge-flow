## 2. 四条合法路径

### 2.1 写入已有知识库

```text
精确 Capture
  → 目标确认与 raw/ 归档
  → SOP-20 材料深度理解与策展地图
  → 地图处结束，或进入 SOP-30
  → 准备精确方案 → 人工批准 → 受限写入
```

这条路径跳过 SOP-10，也不运行新知识库首次启用门禁。已有 active KB 的实际写入仍在首个实现切片之后。

### 2.2 新建知识库并写入

```text
精确 Capture
  → 用户确认新建位置
  → SOP-10 新建知识库骨架
  → raw/ 归档
  → SOP-20 材料深度理解与策展地图
  → SOP-30 准备精确方案 → 人工批准
  → SOP-30 内部首次启用门禁 + 首批可信写入
```

这是当前首个完整垂直切片采用的路径。

### 2.3 暂不选择知识库，只生成地图

```text
精确 Capture
  → 明确深度处理授权
  → SOP-20 材料深度理解与策展地图
  → 保存地图并结束
```

这条路径不创建 Route Record、知识库或 `raw/` 副本。以后选择目标时再单独取得目标归属权限。

### 2.4 没有原料，提前建立空知识库

```text
用户确认父目录
  → SOP-10 新建知识库骨架
  → 保持 provisional 并结束
```

不得为了填满空库而自动生成领域、SCHEMA、地图或可信页面。

## 3. 两级保存与三项权限

两级保存不能混为一件事：

1. Capture Store 保存精确来源版本，是所有路径共同的第一持久化位置。
2. 目标知识库 `raw/` 只在用户确认目标后保存同字节来源副本和旁车映射。

三项权限也必须分别记录：

| 权限 | 允许什么 | 不允许什么 |
|---|---|---|
| 目标归属与 `raw/` 归档 | 选择已有库或调用 SOP-10 新建库，并机械归档来源 | 深度分析、生成可信页面 |
| 深度处理 | 允许 SOP-20 在精确范围和预算内生成地图 | 自动选库、可信写入 |
| 可信写入 | 允许 SOP-30 应用已展示并批准的精确变更集 | 批准后改写正文、扩大路径或授权以后类似任务 |

同一句用户指令可以同时给出前两项权限，但第三项只有完整变更方案已经存在并展示后才能产生。

## 4. 新知识库首次启用门禁

历史 SOP-000B 不再是平级流程。它作为 SOP-30 的新库分支内部规则，只回答：

> 一个由 SOP-10 建立的 `provisional` 知识库，是否已经具备随首批可信内容一起转为 `active` 的条件？

它不调用模型、不单独写文件，也不增加一次用户确认。SOP-30 必须先写入获批 SCHEMA、导航、日志和首批页面，最后才发布 `active` manifest；但 manifest 不是单独的提交点。只有事务回执、结果本地 Git commit、最终文件和 manifest 全部匹配且不存在未解决事务时，产品可信读取才可打开。

本地 Git 是目标知识库受管工件和首版 T3 可信 Wiki 的内部版本引擎，不是 GitHub 集成：Capture 保存和无目标地图终点不要求 Git；SOP-10 为新 KB 建立无 remote 的 `managed-local` 仓库；路由、SOP-20 有目标地图/决定及 SOP-30 分别创建离线本地检查点，绝不自动 fetch、pull、push 或请求账号。Git 负责长期差异和版本历史，事务日志负责写入中断恢复，备份负责介质或整机恢复，三者不能互相替代。

### 4.1 目标知识库本地检查点的共同约束

SOP-10 初始化、路由/`raw/` 归档、SOP-20 有目标地图与决定、SOP-30 可信写入必须复用同一个受控版本适配器，而不是各自直接调用任意宿主 Git：

- 首个切片固定管理 `refs/heads/knowledgeflow`，并要求工作树 `HEAD` 符号指向该 ref；detached HEAD 或切换到其他分支时停止并提示恢复受管工作树。每次提交绑定精确基础 commit，并以比较后更新方式推进该 ref。外部进程抢先改变 ref 时失败关闭，不覆盖并发提交。
- 版本政策固定仓库 object format、受管树条目模式、规范 UTF-8/LF 提交消息、技术提交身份及事务中冻结的 UTC 时间；它不读取用户 Git 姓名/邮箱，也不代表业务批准。首个切片只接受普通非可执行文件（Git mode `100644`），拒绝符号链接、reparse、大小写折叠或 Unicode 规范化后冲突的受管路径。内容完整性仍使用业务 SHA-256，不能把 Git object ID 冒充 Payload/工件哈希。精确重试不得因为宿主平台、配置或重新取时而生成第二个等价 commit。
- 适配器忽略可能改变字节、启动外部程序、弹出交互或访问网络的系统/全局 Git 定制；不运行 hooks、filter、签名、凭据助手、外部 diff、pager/editor 或文件监视助手。commit 中每个 blob 必须与获批/已验证工作树字节完全一致。
- 使用隔离索引或等价路径限定机制；目标路径上出现未绑定的 staged/unstaged/工作树变化时停止，目标外的用户改动保持原样。受管 ref 比较后更新成功后，只把本批路径在默认索引中的条目对齐到结果树，使这些路径保持 clean；目标外 index 条目的 staged/unstaged 语义不得改变。ref 已更新但默认索引尚未对齐属于可恢复的未完成事务，不能报告成功。完成后同时验证父提交、结果树差异、blob 哈希、默认索引和实际工作树。
- 写入前先建立本流程事务，受版本控制的非自引用记录保存业务/事务身份，被忽略的本机回执保存结果 commit。Git 已提交但回执未闭合时仍是未完成事务；只有证据链唯一时才可重建回执。

`managed-local` 也不等于备份。当前首个切片只使用可删除、可重建的隔离实验 KB；在允许不可替代或正式知识进入真实 KB 前，必须另行批准并演练 KB 备份/恢复契约，覆盖工作树、本地 Git 历史和必要的本机恢复证据。GitHub 或 remote 将来即使启用，也不能自动替代该备份责任。

## 5. 当前首个实现边界

当前获准的 `CUR-MVP-1` 只覆盖：一个 UTF-8 文本 Capture、一个带 `managed-local` 离线版本库的全新隔离 `provisional` KB（或明确无目标）、目标分支中的同字节 `raw/` 映射，以及一份可核验、可修改、可独立结束的地图。精确方案、一次批准、首批可信写入和首次启用属于后续 `CUR-MVP-2`，尚未授权。

以下内容后置：已有 active KB 更新、多 KB、删除/归档、物理目录改名、PDF/Office/OCR 适配器、GBrain、自动批准和生产知识库。
