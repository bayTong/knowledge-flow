## 1. 本计划解决什么问题

现有文档已经回答“产品为什么需要深入策展”“三个权限怎样分开”“地图和可信知识有什么区别”，但还没有把这些候选契约压缩成一组可以逐批编码、测试、复核和停止的工作单元。

本计划只解决这一缺口。它不再扩写长期架构，也不把分段、范围和 Evidence locator 单独包装成新的产品阶段。它把必要机械能力放回同一条用户可见纵向链：

```text
选择本地 UTF-8 文件
  → 形成精确 Capture 版本
  → 展示目标建议，用户确认新库或明确暂不选库
  → 选择新库时建立一个隔离 provisional KB，并校验 raw/ 原料副本
  → 显示全文结构、实际处理范围、延期范围和缺口
  → 生成带精确证据的策展地图
  → 用户查看证据、修改结果，并选择“保存地图后结束”
```

只有最后一项能够由用户实际完成，`CUR-MVP-1` 才算完成。前面的机械批次可以独立提交和复核，但都不能单独升级为“产品里程碑已完成”。

## 2. 完成定义

`CUR-MVP-1` 必须同时证明以下结果：

1. **来源精确**：活动文件经严格 UTF-8 校验后，通过现有公共 Capture 操作成为实验 Store 中的精确版本；原文件身份、Capture ID/版本、Payload 哈希和字节数能够互证，不修改 Capture v1 schema。
2. **权限分开**：系统分别记录目标归属授权和深度处理授权；本切片不请求、也不产生可信知识写入批准。
3. **目标可选**：主旅程使用一个全新隔离 provisional KB；受控分支证明用户暂不选库时不会创建 KB、不会写 `raw/`、不会伪造 Route Record。
4. **原料可核验**：选择新库后，目标 `raw/text/` 中的文件与 Capture Payload 同字节，来源映射、Route Record 和本地版本检查点一致。
5. **范围可见**：完整来源的字节范围都被记为已处理、延期、失败或缺口之一；机械结构覆盖全文，语义处理不能通过只截取开头冒充全文。
6. **证据可回读**：每个具体主张、争议、限制或关系能够打开精确 Capture 版本中的 UTF-8 字节范围；错版本、越界、切断多字节字符或哈希不符时明确失败。
7. **地图可使用**：用户能阅读概览、结构、概念、主张、争议、限制和缺口，能区分原文内容、处理器归纳、用户修改和未核实项。
8. **地图可修改**：接受、拒绝、延期只形成决定记录；改变候选含义时形成新地图版本，不覆盖旧版，也不静默复用旧候选身份。
9. **地图可独立结束**：用户保存地图并结束后不产生 `wiki/` 正文、不改变 KB 的可信可见性，也不自动进入 SOP-30。
10. **实验结论受限**：记录首次有用结果时间、人工复核负担、证据问题、范围缺口、处理器调用和成本；一次成功不外推为任意领域或任意规模已有效。


## 4. 最小实现形态

### 4.1 包和入口边界

保持 `knowledgeflow_capture` 的已实现四操作、Store schema 和 Tk 收件箱不变。新增同级、受限的 `knowledgeflow_curation` 包承接实验能力，避免把地图状态塞进 Capture 内核。预计职责如下，精确文件拆分可以在不改变职责的前提下微调：

| 组件 | 最小职责 |
|---|---|
| `contracts` | 运行、来源映射、Segment、范围账、locator、目标决定、地图和回执的受限值对象与安全 YAML/JSON 校验 |
| `source` | 从明确白名单文件读取严格 UTF-8 bytes，调用公共 Capture API，并记录外部文件与 Capture 版本的实验映射 |
| `segmentation` | 按冻结实验 Profile 生成覆盖全文的确定性区段；不承担语义判断 |
| `evidence` | 校验 Capture/版本/Payload/范围/片段哈希并回读证据 |
| `kb` | 仅创建一个 `managed-local` provisional KB；不接管已有仓库 |
| `routing` | 在确认目标后执行复制—校验—记录到 `raw/text/`；无目标时不运行 |
| `processor` | 定义可替换的语义处理边界；核心不绑定供应商、账号或网络 |
| `maps` | 校验候选、生成同事实的 `map.yaml + map.md`、发布新版本与决定记录 |
| `cli` | 提供首轮受限操作入口和机器可读回执，不扩成通用搜索或完整工作台 |

`pyproject.toml` 只需把新包和一个受限 `knowledgeflow-curation` 入口纳入构建。首轮不引入数据库、向量库、图数据库、后台服务、Web 前端或模型厂商 SDK。

### 4.2 实验分段 Profile

首个实现只提供组合身份 `profile_id=experiment-markdown-blocks + revision=1`（下文简称 `experiment-markdown-blocks-v1`），明确标记为可废弃的实验选择，不冻结为永久产品策略：

1. 严格按原始 UTF-8 bytes 工作，不规范化换行、不重写 Unicode。
2. 原始 Segment 层无重叠，所有 bytes 恰好归属一个有序 Segment；空行、标题分隔、表格、代码块和消息标记不能被静默丢弃。
3. 优先在 Markdown 标题前、空行后、完整行末建立边界；超长行只在合法 UTF-8 字符边界切分。
4. 实验初值采用 16 KiB 目标大小、32 KiB 硬上限；这是兼顾精确 locator、自然块边界、局部失败恢复和工件数量的证据层工程初值，不是模型语义最佳尺寸，也不是 token 上限。Profile ID、数值和算法修订进入运行记录；真实运行后可以废弃或调整，不能据此宣称适用于所有材料。
5. `segment_id` 绑定精确 Capture/版本、Payload 哈希、半开字节区间、片段哈希和 Profile 修订；显示行号只作导航。
6. 后续语义批次可以组合多个 Segment 或形成有重叠的处理窗口，但范围账必须单独记录重复 bytes，不能把重叠算成额外覆盖。

### 4.3 全文结构与语义预算分层

`E0-C` 的 1.18 MB 原文不要求一次调用或一次上下文全部送给模型。首轮地图分成两层：

- **零模型机械层**：覆盖全文的标题/消息/区段结构、字节范围、状态和缺口，必须完整；
- **获准语义层**：只处理运行前批准的 Segment/窗口，形成概览、主题、主张、争议和限制；未处理范围继续在地图中可见。

原始 `Segment` 是供应商无关的证据与范围记账单元，不等于一次模型调用。`Processing Window` 是一次语义工作单元：由同一标题树下连续的一个或多个主要 Segment、必要的前后文 Segment、标题路径、任务与输出约束组成。每个 Segment 在粗粒度覆盖中只作为一个窗口的主要范围，允许在相邻窗口中作为辅助上下文重复出现；重复输入必须进入 token/费用记录，但不能重复计算语义覆盖。窗口必须优先尊重标题/章节边界，大章节超限后再拆，小章节只有在同一上级主题且未超限时才合并；边界歧义另建受限联合核查窗口，而不是依赖模型记忆。

首轮采用两级输入限制，二者均针对**完整请求输入**，包括 system/task 指令、最小元数据、主要正文、辅助上下文和必要的已验证前序候选，而不只是原文字段：

- 正常装载目标为 `24,576` tokens；窗口规划达到目标后应在最近的材料结构边界停止，不为减少调用次数继续堆满上下文；
- 请求规划硬上限为 `32,768` tokens；超限时必须减少辅助上下文或按结构拆窗，不得截断、静默丢段或依赖 provider 的 1M 上下文上限兜底；
- 规划使用参考 provider 对应的离线 tokenizer/profile 并记录其身份；API 返回的 `usage.prompt_tokens` 是计费与累计预算真值。若实际 usage 超过规划硬上限，已完成响应只进入偏差/费用记录，不继续后续调用，须先重新规划；
- 输出 token、思考 token、阶段总量和整个运行总量使用独立上限，不能占用未声明的“剩余上下文”。

截至 2026-10-21，DeepSeek 官方说明 `deepseek-flash` 的上下文长度为 1M、最大输出为 384K；这些是动态服务能力而非产品默认值，真实运行前仍须重查[模型与计价](https://api-docs.deepseek.com/quick_start/pricing/)。选择约 24K/32K 是为了让一个窗口能够容纳多个现有 Segment，同时控制注意力稀释、单次失败重做、证据复核和输出压缩风险；它不表示 1M 上下文不可用，也不冻结未来模型的永久窗口大小。

`CUR1D-CODE-R1` 的 tokenizer 裁决是：真实 `deepseek-flash` 运行优先使用 DeepSeek 官方发布且与该请求模型匹配的离线 tokenizer 资产，固定资产来源、版本/Profile 与文件摘要；官方目前提供[离线 token 估算说明](https://api-docs.deepseek.com/quick_start/token_usage/)和 `deepseek-recipe` 中的 V4.1 tokenizer 资料，但官方同样明确离线结果只是估算，实际 API `usage` 仍是真值。`Utf8ByteUpperBoundTokenCounter` 只用于确定性测试和具名保守后备，不能在真实远端 CLI 中静默冒充模型 tokenizer。若运行环境无法取得或验证官方资产，只有在运行记录明确标为 conservative、按该估算器重新规划窗口和预算且不降低硬上限时才可使用后备；否则在发送首个正文请求前失败关闭。

如果获准预算不足以支持全文语义处理，必须在运行前缩小语义范围或采用分层批次，并在地图中明确显示延期范围。不得静默截取开头、把机械覆盖率冒充语义覆盖率，或凭输入字节数虚构 token/费用。

### 4.4 首个语义处理器边界

核心先实现一个供应商无关的文件交换端口和一个确定性测试处理器：

1. KnowledgeFlow 生成绑定运行 ID、来源哈希、获准范围、任务、输出约束和预算的处理请求包。
2. 外部或本地处理器返回受限候选包；候选只能引用请求包允许的 Segment/locator。
3. KnowledgeFlow 重新校验所有范围、证据、来源属性、不确定性和输出上限，再决定是否发布地图。
4. 测试处理器只用于契约、失败和复现测试，不能证明真实语义价值。
5. `E0-C` 的 provider/协议/请求模型/密钥引用、完整正文分批外传范围、Processing Window、思考模式和深化边界已经在后续预检中确认；总调用/token/费用、超时、重试、真实处理器实现和一次实际联网运行仍须在语义批次前闭合或单独授权。

这种边界使 Capture、范围、证据、地图保存和本地版本历史在断网时仍可工作，同时允许以后替换成本地模型或不同服务，不把首轮实验绑定到单一账号。

### 4.5 最小用户入口

首轮使用“受限命令入口 + 可直接阅读的 `map.md` + 精确证据打开命令”，不扩建完整 Tk/Obsidian 式工作台。至少支持以下用户任务：

- 准备一个精确来源并查看身份；
- 查看目标建议，确认一个新 KB 或选择暂不选库；
- 查看全文范围与当前缺口；
- 生成并打开地图；
- 按候选打开证据；
- 接受、拒绝、延期或用替代文本修改候选；
- 保存新地图/决定版本；
- 保存地图并结束。

命令任务名在 `CUR1A` 固定；每个命令的首个可执行批次再固定其最小参数，避免为尚未实现的后续能力预设伪接口。无论采用交互式提示还是显式参数，都必须提供结构化回执和单一可执行的修正提示。只有生成机械诊断文件而没有上述查看、修改和结束入口，不算完成。

`CUR1A` 冻结以下用户任务名称和未来 CLI 拼写，但不暴露“尚未实现却返回成功”的空壳命令。对应子命令只在表中所列批次实现后进入可执行入口：

| 用户任务 | 操作身份 / CLI 拼写 | 首次实现批次 |
|---|---|---|
| 准备精确来源 | `source.prepare` / `knowledgeflow-curation source prepare` | `CUR1B` |
| 查看来源、区段与范围 | `source.inspect` / `knowledgeflow-curation source inspect` | `CUR1B` |
| 打开精确证据 | `evidence.show` / `knowledgeflow-curation evidence show` | `CUR1B` |
| 确认新库或暂不选库 | `target.decide` / `knowledgeflow-curation target decide` | `CUR1C` |
| 生成地图 | `map.build` / `knowledgeflow-curation map build` | `CUR1D` |
| 接受、拒绝、延期或修改候选 | `map.decide` / `knowledgeflow-curation map decide` | `CUR1D` |
| 保存地图并结束 | `map.close` / `knowledgeflow-curation map close` | `CUR1D` |

全部命令最终只输出一个 UTF-8 JSON 回执；失败沿用 `knowledgeflow_curation` 的稳定错误码和 `not-committed / unknown` 提交状态。`unknown` 不得伪报 `saved: false`，成功状态也不能仅凭文件存在推断。首个可执行子命令进入 `CUR1B` 时再把 `knowledgeflow-curation` 注册到 `pyproject.toml`，CUR1A 不安装误导性的占位 CLI。

`CUR1B` 固定的首组显式参数如下；所有路径由用户在本机运行时给出，产品代码不保存原件绝对路径，也不提供默认生产 Store：

```text
knowledgeflow-curation --experiment-root <绝对路径> source prepare
  --source <绝对 UTF-8 文件路径>
  --source-reference <安全来源代号>
  --expected-sha256 <sha256:...>
  --expected-bytes <正整数>
  --request-id <幂等请求代号>
  --authorized-by <授权者代号>
  --task-id <任务代号> [--task-id <任务代号> ...]
```

#### 从产品需求反推首轮处理逻辑

处理器选择不得从 `prompts/` 的现成模式开始。首轮逻辑先由主 PRD 的 `FR-WORK-001`、`FR-ASSIST-001`、`FR-PROC-001`、`FR-EVID-001`、`FR-AUTO-001`、`FR-PROP-001`，治理规则 P2/P7/P8/P9，以及 `NFR-HUMAN-001`、`NFR-QUAL-001`、`NFR-EXT-001` 共同约束，再由 SOP-20 细化。由此得到以下需求链：

1. **用户成果先行**：目标是让用户更快形成对材料范围、主要结构、重要主张、争议、限制和缺口的初始整体理解，并能决定下一步，而不是最大化实体数量、固定十节齐全或证明模型“读完了一切”。
2. **机械范围与语义理解分层**：全文先由已实现的确定性 Segment、范围账和 Evidence locator 完整覆盖；语义处理只能作用于获准范围，每个 Segment 必须处于已处理、延期、失败或用户排除之一。机械记账完整不等于语义完整。
3. **只有一类地图工件，范围、深度和呈现分开**：`declared_scope` 说明本次覆盖整份来源还是明确子范围；实际处理说明各范围是粗粒度还是选择性深入；用户默认看到薄总览并按需展开证据。子范围结果仍是策展地图，不另造“局部地图”；整份来源地图也不等于整个知识库的永久全文地图。
4. **长文采用分层候选而非单次全文指令**：对当前约 1.18 MB、76 个机械 Segment 的 `E0-C`，首轮合理候选是“区段级粗粒度理解 → 带 Evidence 的分层汇总 → 跨区段主题/演进/冲突比较 → 重要或高风险区段深化 → 地图组装与证据校验”。如果声明范围是整份来源，各主要范围必须至少得到粗粒度说明，或明确显示为延期/失败/用户排除；预算不足时不得以少量局部深挖冒充整份来源理解。
5. **薄地图优先**：默认呈现材料概览、主要部分及范围、少量跨部分重复/演进/冲突、可见缺口和建议下一步；详细主张、概念、关系、运行事实和 Evidence 按需展开。完整机械范围账留在底层，不把 76 个 Segment 直接铺成用户目录。
6. **减少人工负担而不是转嫁选段劳动**：系统先提出可解释的处理范围、层次和预算建议，用户批准一个边界清晰的批次；不要求用户预先逐段阅读或手工挑完 76 个 Segment。用户主要审核关键概览、争议、低置信度、高影响候选和修改结果。
7. **处理器只生成候选**：处理器请求只携带运行身份、获准 Segment/locator、任务、输出限制和预算；返回候选必须引用获准证据，区分来源表达、外部引用、可核实事实和处理器推断。处理器不能选择或激活 KB，也不能写入 `wiki/`。
8. **本地核心验证后再发布**：KnowledgeFlow 必须机械拒绝越界 locator、无证据主张、截断/超限输出、范围账不平、身份不符和预算状态不明；只有通过验证的候选才能生成同事实的 `map.yaml + map.md`。
9. **地图是合法终点且不是全库导航**：用户可以修改、接受、拒绝、延期或只保存地图；继续进入 SOP-30 必须另有精确方案和批准。新材料、冲突或结构变化以后可以触发新地图或新版本，但旧地图不承担 README、Wiki 导航、来源总目录、Ontology 或知识图谱职责。模型流畅度、固定章节数、条目数或覆盖报告都不能替代用户价值与证据正确性。

因此，预检的决定顺序固定为：**用户任务与成功证据 → 处理范围和分层策略 → 处理器输入/输出契约 → 处理器实现与模型 → 调用、token、费用和停止上限 → Prompt 细节**。模型版本和数值预算确实必须在真实运行前确认，但它们是需求和策略的下游决定，不得反向支配产品流程。

#### 首轮 API 处理器方向（2026-10-20）

项目所有者决定暂不检查或接入本机模型，首轮真实语义处理使用用户自行配置的外部 API key、受支持 provider profile 和 `model_id`；本地部署模型作为后续适配器，不阻塞本轮。这个决定只影响可关闭的语义增强能力：没有 key、网络或可用模型时，Capture、读取、版本、恢复、既有机械 Evidence 和已保存工件继续可用，真实语义任务在发送任何正文前明确暂停或失败，不得静默换模型。

“用户可配置模型”不等于首版承诺兼容任意厂商、任意协议或任意模型。`CUR1D` 只实现供应商无关处理端口、确定性测试处理器和一个获批的参考 API 适配器；用户可在该适配器明确支持且通过能力预检的模型中配置精确 `model_id`。新增 provider 协议、本地模型或 OpenAI-compatible 端点均作为后续适配器单独验证，不能靠修改 URL 就冒充兼容。

API key 只能通过运行时密钥来源引用，例如环境变量名或后续凭据存储句柄；明文 key 不得写入仓库、普通配置、命令行回显、日志、错误、回执、地图或测试夹具。处理器只接收获准 Segment、运行/任务身份、输出契约和预算，不接收整个仓库、C-K/盲抽答案、判分记录或无关来源。每次运行必须记录 provider profile、请求的 `model_id`、服务实际返回的模型身份（若有）、Prompt/Profile 版本、发送字段类别、调用次数、token/usage、超时、重试、停止原因和费用口径，但不记录密钥。

#### 本地运行编排，不依赖 Agent 长会话

76 个原始证据 Segment 不等于 76 次模型请求，也不要求建立服务商侧的长对话或通用 Agent 会话管理器。它们按标题结构和 token 上限组合成数量更少的 Processing Window；DeepSeek Chat Completions 按无状态调用使用，每个请求都由本地根据已冻结 Profile、一个或一组获准 Segment、明确任务和输出约束重新构造。后续汇总只显式携带已经通过本地验证的前序候选及不透明 Segment 引用，不依赖模型“记得之前聊过什么”。

KnowledgeFlow 仍需要一个**本地、有界、可恢复的策展运行编排**：记录工作单元属于哪个精确来源版本、使用了哪些 Segment、请求摘要、尝试次数、用量、结果/错误和依赖关系；中断后只恢复未闭合单元，不重发已经确认成功的调用。它是 `CurationRunManifest` 的 CUR1D 运行细化，不是面向任意任务的自主 Agent 平台，也不引入服务端 conversation ID、隐藏记忆或无限历史。具体请求/回执字段仍在 CUR1D 契约能力批次内测试后冻结，不能由本段提前扩成通用持久化 schema。

#### 思考模式、粗粒度覆盖与重点深化（2026-10-21）

项目所有者确认首轮按任务复杂度分配思考模式，而不是对所有正文统一开启：

| 工作阶段 | 首轮模式 | 边界 |
|---|---|---|
| 本地来源校验、Segment、locator、范围账 | 不调用模型 | 全部由确定性代码完成 |
| 目标未明确时的最小梗概与目标建议 | non-thinking | 用户已经明确目标时跳过；结果只是建议 |
| 整份来源的 Processing Window 粗粒度覆盖 | non-thinking | 主要部分必须得到说明或显式延期/失败/排除；不要求语义穷举 |
| 章节/部分综合与整份薄地图 | thinking，`reasoning_effort=low` | 只使用已验证候选和必要获准原文；不得继承隐藏会话记忆 |
| 重点歧义、冲突或跨部分关系深化 | thinking，默认 `low` | 只有低置信度、高影响且 `low` 明显不足的单个工作单元，才可在同一总预算内升级为 `high`；不得默认全局使用 `high` |
| Schema、locator、范围、预算与发布验证 | 不调用模型 | 模型不得审核或批准自己的输出 |
| 用户接受、拒绝、替换文本或关闭地图 | 默认不调用模型 | 用户明确要求局部重生成时另建受限工作单元并计入预算 |

DeepSeek 官方当前默认启用 thinking 且默认 effort 为 `high`，因此参考适配器不能通过省略参数表达上表；每次模型请求都必须显式发送 thinking 开关，并在启用时显式发送 `reasoning_effort`，响应与运行记录须保存实际请求值。动态参数语义在真实运行前按官方 [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/) 重新核对。

首轮不是“少量重点详写、其余静默跳过”。整份声明范围先完成 L1 粗粒度覆盖，再建议 `3` 个、最多 `5` 个 L2 重点；不足 3 个时不得为凑数创建重点。选择理由只能来自用户关注、跨部分反复出现、对全文结论影响大、明显冲突/歧义或低置信度等可见信号，不能读取 C-K 或非 C-K evaluator-only 答案。每个重点至少说明核心问题、原文定义/主张、论据或前提、跨部分关系、来源表达与处理器推断、不确定项、精确 Evidence 和建议下一步；达到“用户能理解是什么、为什么、依据和限制，并能决定是否继续”后停止。外部搜索核验、完整 Wiki、本体、知识图谱和可信写入均不属于本轮重点深化。

#### 一本书或更长材料的分层处理

对于单个 UTF-8 文本来源，Capture 继续保存一个完整、不可变的版本；4 MiB 只是内联/流式实现阈值，当前默认单版本安全上限是可本地配置的 64 MiB。不得为了绕过上限而静默截断，或自动把一份逻辑原料伪装成多个无关联 Capture。PDF、EPUB、扫描件、超过本地上限的单文件或多卷集合需要以后单独批准文件提取/多来源契约，不属于 `CUR-MVP-1`。

获准的长文本先形成无遗漏的原始 Segment 层，再按材料自身结构把 Segment 组合为章节/部分等处理窗口；语义结果采用“Segment 候选 → 章节/部分地图 → 全书薄地图 → 重点范围深化”的显式层次。全书声明范围下，所有原始 Segment 必须最终处于已处理、延期、失败或用户排除之一；模型无需在一次请求中同时看到整本书，但所有声称已处理的正文都必须实际进入获准请求。跨章节汇总主要使用已验证的章节候选，并在需要时回取少量原始 Segment 核对，最终 Evidence 仍由本地映射到精确原文 bytes。

材料越长，处理时间与费用近似随实际发送正文和分层汇总增长；预算不足时按章节停在可恢复检查点，把余下章节显示为延期，而不是降级为“只读开头、宣称全书完成”。首轮只验证当前单来源 `E0-C`，不能据此宣称已经支持任意书籍、文件格式或多卷语料。

截至 2026-10-21，DeepSeek 官方对 `deepseek-flash` 的峰时 cache-miss 输入价为每百万 tokens `USD 0.30`，输出价为每百万 tokens `USD 1.20`；首轮预算不依赖低谷价或缓存折扣。按上述 token 硬上限计算的当前峰值理论费用约为 `USD 1.194`，再保留价格、计量和未知尝试余量后，provider 费用硬上限冻结为 **USD 2.00**，不做易漂移的汇率换算。每个请求发送前都必须按当前官方峰时 cache-miss 价格和该请求最坏用量预留费用；若动态价格、计费口径或模型别名发生实质变化，或下一请求会使预留总额超过 `USD 2.00`，则在发送前停止并重新授权。费用不能记录为 `0` 或仅凭本地估算认定。

首轮固定串行调用，并发数为 `1`。连接超时为 `15` 秒，首个非空响应数据等待上限为 `300` 秒，单请求墙钟总上限为 `900` 秒；provider keep-alive 空行只证明连接仍在，不能伪装成有效响应。只有明确的连接前失败，或 HTTP `408/429/500/503` 才可在同一冻结请求字节下自动重试；单个工作单元最多 `2` 次瞬时重试，退避为约 `2` 秒、`8` 秒并优先遵守不超过 `60` 秒的 `Retry-After`。HTTP `400/401/402/403/404/413/422`、内容过滤、输出截断、Schema/locator 无效、请求已发送后的读取超时或提交状态不明均不得自动重试；它们必须保存失败/未知事实并暂停该单元，避免重复计费和语义漂移。

离线规划 input 不得超过 `32,768`；API 实际 `prompt_tokens` 高于规划值但未越过硬上限时，先按实际用量记账，再确认剩余预算足以完成下一单元。实际输入越过硬上限、任何输出以 `length`/`content_filter`/资源中止结束、usage 缺失且无法按最坏值预留、累计尝试/token/费用达到任一上限时，不发布该候选，不再发起新请求；保留已验证结果和运行记录，其余范围明确标为 `deferred`、`failed` 或 `unknown`。预算耗尽不得触发自动换模型、降低证据要求或把机械覆盖冒充语义覆盖。

数据边界维持不变：不使用文件上传、工具调用、联网搜索、服务端对话延续或无关仓库内容；不发送本机绝对路径、Capture/KB/Git 身份、gold 或判分答案。DeepSeek 当前隐私政策覆盖 API 输入并说明输入/输出可能用于训练或服务优化；本轮还须把账号是否关闭“数据用于优化体验”作为最终授权包的显式选择。因此只能在项目所有者另行批准 `CUR1D-RUN` 后发送已经确认的低敏感度 `E0-C`。政策、服务条款或用户的数据使用选择发生实质变化时，在下一次正文发送前暂停。

### `CUR1V`：本地总验收与价值判断

按下列两条旅程验收：

1. `E0-F`：验证精确身份、全文机械范围、locator、回读、双跑、派生物重建和“暂不选库”零副作用；不把结果计为语义价值。
2. `E0-C`：在一个全新隔离 provisional KB 中完成来源 Capture、目标建议/确认、`raw/` 映射、整份来源声明范围下的分层薄地图、证据打开、至少一次用户修改和地图处结束；主要范围须有粗粒度说明或可见延期/失败，重点范围可选择性深入。

验收同时运行届时全部现行单元/集成/故障与回归测试、严格 `ResourceWarning`、源码编译、依赖检查、文档一致性与差异检查；不在长期计划中复制一个会持续漂移的旧测试总数。Windows CI 只作远端复核，不是本地使用、GitHub 账号或联网运行的产品前置。

结果报告必须分别给出：机械全通过/失败项、语义处理范围和深度、默认薄地图及展开内容、可见缺口、证据支持问题、首次有用结果时间、限时初始理解对照与系统路径用时、用户修改、调用/token/费用、失败样例和清理结果。没有可比较的限时对照时只报告系统路径的绝对可用性，不宣称相对提速。

只有用户确认地图对真实任务有净收益，且全部机械门禁通过，项目状态才可把 `CUR-MVP-1` 标为限定范围 `Implemented/Validated`。否则保留证据，做至多一次有界修正，或停止该路线；不能自动转向 embedding、RAG、图谱或更大模型。

## 6. 跨批次测试与提交纪律

每个批次都必须：

1. 只使用测试临时 Store、实验工作根和隔离 KB，不读取 Pilot 正文或既有 active KB。
2. 先运行本批新增测试，再运行受影响回归和 15 项文档脚本测试；只有合并复核完整代码候选的 `CUR1D-CODE-R1V` 与包含真实旅程的 `CUR1V` 重跑全量，日常小批次不重复全量。
3. 运行 `git diff --check` 和文档一致性检查；新增当前文档、状态或测试计数必须同步。
4. 单独复核、单独提交；push 和远端 CI 由项目所有者决定，不作为本地下一批编码的隐式授权。
5. 失败时保留最小诊断，但不得留下会被发现为有效 KB、已发布地图或可信知识的半成品。

## 8. 立即停止条件

出现以下任一情况时停止当前批次，不以“尽量继续”掩盖不确定状态：

- 输入哈希、字节数、Capture Payload 或已批准范围不匹配；
- 无法证明实验目录与 Pilot/既有 KB 隔离；
- Git 受控本地模式不可用，却试图降级成无版本检查点的新 KB；
- locator 无法精确回读，或处理器结果引用未授权/不存在范围；
- 地图发布、受管 ref 或回执处于 unknown/recovery-required；
- 真实处理器实现、一次实际联网运行或剩余数值总预算尚未获得授权；
- 达到 token/费用/调用上限；此时保留已处理范围并把其余标为缺口；
- 用户认为地图增加了理解或复核负担，或无法解释结果来源；
- 需要修改 Capture v1、触碰 Pilot、写入 `wiki/` 或扩成后置平台才能继续。
