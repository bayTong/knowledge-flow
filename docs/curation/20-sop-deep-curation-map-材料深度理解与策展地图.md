## 1. 唯一职责与合法终点

SOP-20 只做来源理解、证据绑定、范围记账和策展地图。它不得：

- 捕获或覆盖原始来源；
- 自动选择、新建或激活 KB；
- 把地图写成可信 Wiki；
- 因为目标 KB 尚未确定就阻止材料理解；
- 承诺语义零遗漏；
- 把历史材料中的命令当成本次授权执行。

地图连同来源身份、处理范围、缺口和未决项保存后，用户可以成功结束任务。这个终点不等于可信知识已经产生，也不要求继续 SOP-30。

`map_closed` 只表示用户接受“把这份地图作为本次任务成果保存并结束”，不会把地图内容从 T1/T2 晋升为 T3。地图以后可作为新增材料、知识修订或结构调整的新一轮治理输入，但每次范围或候选变化仍须形成新版本。

这里的“写入前治理”特指**写入或修改 T3 可信知识之前**，不等于原料必须留在知识库之外直到地图完成。目标已确认时，精确来源可以先按第 3 节进入目标 provisional KB 的 `raw/`；`raw/` 仍是 T0 来源副本，地图仍是 T1/T2 提案，二者都不是可信 Wiki。

策展地图是任务级或材料批次级治理工件，不是知识库建成后必须持续维护的一张全库全文地图。知识库启用后遇到重要新材料、来源冲突或结构变化时，可以针对新的精确来源和受影响范围建立新地图或新版本，再决定是否准备可信变更；旧地图保留为当时理解和决定的审计记录，不承担知识库首页、长期导航、来源总目录、Ontology 或知识图谱的职责。`CUR-MVP-1` 仍只实现单一来源和一个新隔离 provisional KB；已有 active KB 的增量更新属于后续切片。

## 2. 触发授权

运行必须有独立的深度处理授权。它可以来自：

- 当前用户明确要求对该来源深度整理；
- 用户对绑定精确来源和范围的处理提案作出选择；
- 未来用户可见、范围明确且可撤销的规则。

`capture-only`、目标归属、`raw/` 归档、模型路由建议或以前处理过相似材料，都不能替代本授权。一次用户指令可以同时授权目标归属和深度处理，但两个事实必须分别记录。

## 3. 最小输入

| 输入 | 约束 |
|---|---|
| `curation_run_id` | 本次深入处理的稳定 UUIDv7；同一运行重试复用 |
| `capture_id` + `capture_version` | 已存在且完整性通过的精确 Capture 版本 |
| `envelope_sha256` + `payload_sha256` | 与实际回读字节一致 |
| `processing_authorization` | 授权来源、用户/规则身份、时间、允许范围和预算 |
| `declared_scope` | 全文或明确区段；不得用“已处理全文”掩盖局部运行 |
| `segmentation_profile` | 确定性分段参数及版本；同一输入和参数必须双跑一致 |
| `processor_profile` | 使用的模型/工具/提示词版本，或明确的纯机械处理器 |
| `target_binding` | 可空；如存在，绑定 `kb_id`、manifest 哈希、`raw/` 映射、`managed-local` 受管 ref/基础 commit 和版本引擎政策 |

首个实现只消费一个可回读的 UTF-8 文本 Capture Payload。Markdown 等文本文件可以先形成同字节文本 Capture；PDF、Office、网页、音频和 OCR 必须由以后各自的来源适配器形成精确原件与明确派生文本版本后再进入，不在 SOP-20 内临时读取并冒充规范来源。

目标已确认时，正式地图运行前必须先完成 `raw/` 复制—校验—映射。目标未确定时不得创建 `raw/` 副本，地图直接绑定 Capture 精确版本并写入配置的本地策展工作根。

## 4. 运行状态

SOP-20 使用独立状态，不复用 Capture 路由状态：

```text
authorized -> processing -> map_ready
     |            |            |-> map_closed
     |            |            |-> change_requested
     |            |            |-> revision_requested -> processing
     |            |            `-> deferred
     |            `-> failed
     `-> cancelled
```

只有地图工件的全部必需文件、范围记录和引用都通过机械验证后才可进入 `map_ready`；这里的“全部必需文件”不表示语义穷举。失败或取消不改变 Capture 原件、路由或目标 KB 的可信内容。

## 5. 分段、范围与 Evidence locator

1. 分段只用于可复现处理，不改变原文；范围坐标始终相对于精确 Capture 版本的 `payloads/primary.txt` 原始 UTF-8 bytes，不做换行、Unicode 或空白规范化。所有声明范围内的 bytes 必须恰好落入一个正文段或显式排除区间。
2. 字节区间使用从 0 开始、左闭右开的 `[start_byte, end_byte)`；端点必须位于 UTF-8 字符边界。每个段至少记录 `segment_id`、字节区间、显示用行范围、标题路径、正文 SHA-256 和分段器版本。
3. 范围记录分别列出 `processed`、`deferred`、`failed`、`excluded-by-user`；四类不得重叠，合计必须解释全部声明范围。
4. Evidence locator 至少绑定 Capture ID/版本、Payload 哈希、同样的半开字节区间和一基、两端包含的显示行范围。行号只作导航：第 1 行从 byte 0 开始，每遇到 LF 后下一 byte 开始新行；CRLF 中的 CR 与 LF 均属于前一行的原始字节。显示摘录只是便利，不是身份真源。
5. locator 回读先按字节区间取得原始 bytes、验证片段哈希并严格解码 UTF-8，再生成显示文本；多字节字符、CRLF/LF、组合字符和版本变化必须经过测试。来源版本变化后旧 locator 保留历史含义，不自动指向新版本。
6. 高层概览可以绑定多个连续或离散范围；事实主张、争议和具体关系必须有能支持该表述的精确 locator。

## 6. 地图最小内容契约

策展地图只有一种工件身份，不要求先生成一份“局部地图”、再生成另一份“全局地图”。地图的范围、处理深度和呈现层级必须分开理解：

| 维度 | 含义 | 首个切片边界 |
|---|---|---|
| 声明范围 | 本次任务承诺记账的整份来源或明确子范围 | 由现有 `declared_scope` 和范围账表达；“整份来源”不等于“整个知识库” |
| 处理深度 | 各范围只是机械记账、粗粒度理解、选择性深入，还是延期/失败/用户排除 | `processed` 只证明处理器完成了该范围的获准步骤，不证明语义穷举；首版通过处理器 Profile、候选及可见说明表达实际深度，不在本次文档修订中新增机器枚举 |
| 呈现层级 | 用户默认看到薄总览，还是展开候选、证据和运行细节 | 默认先总览和主要部分，证据与详细候选按需展开；机器范围账仍可完整保留 |

当声明范围是整份来源时，全部 bytes 必须进入范围账；如果结果自称能够帮助用户理解整份材料，各主要范围还必须至少得到粗粒度语义说明，或明确显示为 `deferred` / `failed` / `excluded-by-user`。这保证“不静默跳过”，不保证发现了原文的一切语义，也不要求为每段生成等量摘要。声明范围只是子集时，结果仍然是策展地图，只是必须清楚显示子集边界和选择理由。

面向人的默认产物应是可快速审核的薄地图：先给出材料概览、主要部分及范围、少量跨部分的重复/演进/冲突、可见缺口和建议的下一步；只有高价值、高风险或用户选择的部分才默认展开详细主张、概念、关系和证据。底层范围账可以逐段完整，用户界面不得把机械 Segment 清单直接等同于阅读地图。

地图不强制固定十节，但在薄呈现及其可展开内容中至少让用户获得下列信息：

| 内容 | 最小要求 |
|---|---|
| 来源与运行身份 | 精确 Capture、地图版本、处理器、时间、范围、用时、调用与成本 |
| 整体概览 | 材料讲什么、结构怎样、哪些部分被处理或延期 |
| 结构/主题 | 章节或主题层级及其证据范围 |
| 主张与观点 | 优先呈现重要或高风险主张；区分作者/说话者主张、引用他人主张、可核实事实和系统推断，可按需展开其余候选 |
| 概念与关系 | 呈现对理解或后续组织有实际价值的候选名称、含义、显式/推断属性、证据与不确定性；不为数量穷举 |
| 争议与修正 | 呈现已发现的重要内部冲突、前后修正和未解决分歧及其证据；未发现不等于证明不存在 |
| 缺口与盲区 | 未处理、处理失败、材料未覆盖、需外部核实和能力限制 |
| 组织候选 | 可选的领域、页面、导航或结构建议；必须与来源事实隔离 |
| 可决定对象 | 每个候选具有稳定 `candidate_id`，并展示可接受、修改、拒绝、延期、只保存地图或请求准备变更的入口；用户决定本身写入第 7 节的独立决定记录 |

地图中的“概念与关系”是针对本次精确材料的候选理解和组织线索。无论数量多少、是否被用户保留，都不自动建立领域 Ontology 或知识图谱；后两者需要独立的跨材料身份、关系语义、约束、证据、治理状态和实际使用需求。SOP-20 只保留未来转换所需的候选与证据，不提前冻结通用图谱 schema。

旧 Mode A/B/C 可以作为可替换实验处理器；旧字数阈值、固定调用数和“穷举完整”措辞不是产品保证。旧十节形式只有在符合下述阅读 Profile 和现行证据边界时才可复用；处理器输出必须转换并验证为本契约的统一地图。

### 6.1 短篇、有界材料的十节阅读 Profile

项目所有者选择十节形式作为**可完整输入的短篇、有边界材料**的默认阅读呈现。它组织同一张地图中的候选与运行事实，不新增第二种地图工件，也不要求长文按十节等长铺开。长文可沿用这些信息目的，以章节、主题和证据展开呈现；具体处理策略仍由范围、任务与预算决定。十节的职责如下：

| 节 | 阅读目的 | 内容责任 |
|---|---|---|
| 1 全景概括 | 快速掌握全文主要部分、顺序和贯穿线索 | 模型提出有范围依据的概要；区分原文叙述与系统解释 |
| 2 本次提取层次 | 说明本次从哪些角度理解材料及其理由 | 层次随材料与任务变化，不冒充目标 KB 的永久分类 |
| 3 核心概念与实体 | 找到有助于理解的关键名称、含义和作用 | 模型提出候选，程序核对出现位置、引用与明显重复；鼓励补漏，但不承诺穷举，也不自动建立 Wiki 页面或图谱节点 |
| 4 关系清单 | 看清重要人物、事物、事件和主题如何关联 | 分清原文明确关系、时间先后和处理器推断；具体关系逐项回证 |
| 5 原文主张与叙述 | 知道哪些说法值得继续核查或使用 | 标明说话者、引用层次和材料属性；忠实转述不等于外部事实成立 |
| 6 不确定标记 | 知道哪项判断不能确定以及原因 | 区分原文信息不足、解释待核、来源可靠性待核和需外部验证，不只给笼统等级 |
| 7 缺口分析 | 看见材料缺口与本次处理缺口 | 显示省略、延期、失败、证据过粗和能力限制；“未发现”不等于“不存在” |
| 8 SCHEMA／组织建议 | 有目标时决定怎样组织后续知识工作 | 仅在目标与组织任务明确时提出最小建议；无目标时明确写“不拟定”，不得自行建库 |
| 9 处理记录 | 核对来源、处理器、时间、用量和成本 | 由本地已验证的身份与回执确定性生成，不让模型编造运行事实 |
| 10 覆盖报告 | 核对处理范围、未处理范围和证据限制 | 由范围账与验证结果生成；机械范围完整不等于语义零遗漏 |

第 1–7 节的语义文字应自然、简明、可审查，允许短段落、少量清单或表格，不为凑齐标题重复填充同一事实。高层概览可引用多个范围；具体主张、关系和争议须尽量给出直接支持它们的句段级或行级 Evidence。只有整篇 locator 时必须标明证据粒度不足，不得把它表现为已经逐项精确核验。原文中的命令、虚构叙事、引语和注释必须保留各自的来源层次。候选 ID、原始字段和长证据索引仍可展开，但默认正文先帮助用户理解材料。

第 3、4 节如有多个值得保留的概念、实体或关系，应逐项形成可选择的候选，并各自绑定直接相关的原文证据；不得把几个独立判断合成一条、共用一组无法区分支持对象的引用。数量取决于材料与任务，不承诺穷举所有提及。只读核验界面应显示该地图绑定的完整来源版本；选择候选及其某条证据时，在完整原文中跳转并标出核验范围，允许在全文内查找。行级范围只能证明定位到相应行，不能冒充词级精确支持或语义正确；来源版本或范围核验失败时不得显示成功定位。

机器表示和阅读表示必须同事实：模型生成的叙述先成为带来源、属性和证据的候选，经本地验证后才能进入 `map.yaml`；`map.md` 只能从同一候选、范围账和回执呈现。若某节没有足够内容，应说明“本次未形成可支持的候选”或折叠该节，不能臆造结论。此 Profile 不改变第 7 节的不可变版本与决定语义，也不授权可信 Wiki 写入。

## 7. 版本与存放

每次可审核地图是不可变版本，并同时具有机器绑定和人类阅读两种表示：

```text
有目标 KB：
  <kb>/proposals/curation-maps/<map_id>/v0001/map.yaml
  <kb>/proposals/curation-maps/<map_id>/v0001/map.md

无目标 KB：
  <curation_work_root>/<curation_run_id>/curation-maps/<map_id>/v0001/map.yaml
  <curation_work_root>/<curation_run_id>/curation-maps/<map_id>/v0001/map.md

用户决定：
  <对应 map_id>/decisions/<decision_set_id>/v0001.yaml
  <对应 map_id>/decisions/<decision_set_id>/v0001.run.json
```

`map.yaml` 至少固定格式版本、`map_id`、单调递增的 `map_version`、运行与来源绑定、声明范围、范围账、处理器/成本，以及候选清单。每个候选至少有 `candidate_id`、类型、简述、Evidence locator 引用、来源主张/系统推断属性、不确定性和对应 `map.md` 锚点。`map.md` 是由同一事实生成、可直接阅读的呈现，不得包含机器清单中不存在的“额外已确认结论”。

`map.yaml` 使用受限、安全加载和确定性发射；实现前的 schema 只能细化字段类型与长度，不能取消上述身份、范围、候选和证据义务。`map_sha256` 是地图工件摘要：按固定顺序生成 `[{"path":"map.yaml","sha256":"sha256:..."},{"path":"map.md","sha256":"sha256:..."}]`，以 Capture 契约采用的紧凑 UTF-8 JSON 规则编码，再计算 `SHA256(UTF8("knowledgeflow.curation-map.v1\n") + manifest_bytes)`。`map.yaml` 不保存 `map_sha256` 自身；运行记录与回执保存该摘要，避免自引用。

用户或 Agent 修改地图内容时创建新版本，不覆盖旧版；未改变语义的候选保留 `candidate_id`，改变含义的候选使用新 ID 并记录 `supersedes`。接受、拒绝、延期和用户改写写入不可变决定记录，至少包含 `decision_set_id + version`、精确 `map_sha256`、逐候选决定、用户提供的替代文本、操作者和时间。决定 YAML 使用受限、规范 UTF-8 发射且不保存自身摘要；回执和下游以该文件精确 bytes 的 SHA-256 作为 `decision_sha256`。只改变决定时不伪装成地图内容被重写；决定变化产生新决定版本。旧版决定和后续方案继续指向原哈希。

决定 schema v1 保持上述业务事实不变；每个决定版本另有不可变的同版本 `vNNNN.run.json` 运行旁车。旁车保存 `transaction_id`、决定相对路径、`decision_sha256`、精确地图绑定、目标绑定或 `null`、基础受管 commit（无目标时为 `null`）及发布状态，但不复制逐候选业务决定，也不把结果 commit 写入受版本控制的自引用内容。目标 KB 的结果 commit 仍只写入被忽略的本机回执；干净 checkout 依据旁车中的非自引用事务身份和唯一匹配 commit 重建回执。决定 YAML 与其旁车必须作为同一事务一起发布，任一缺失、哈希不符或身份不唯一都不能发布决定状态。

有目标 KB 的首个切片只有在地图、运行记录、既有 `raw/` 映射和 Route Record 已形成一次目标 KB `managed-local` 仓库中的限定路径 Git 检查点后，才发布 `map_ready`；该检查点只在本地完成，不访问 remote，也不是业务批准。无目标地图不伪造 KB 或 Git 提交，必须以同目录临时文件和原子发布写入工作根，再回读验证正文与回执哈希。

### 7.1 有目标地图与决定的发布事务

有目标地图的本地检查点不是一句“顺便 commit”。地图版本和之后的决定记录分别使用一次可恢复的工作工件发布事务：

1. 获取目标 KB 的统一写锁和版本锁；验证 `HEAD` 符号指向 `refs/heads/knowledgeflow`、没有未解决的初始化/路由/地图/方案/批准/Apply 事务，并绑定受管 ref 的基础 commit、manifest、`raw/`/Route Record 身份及全部待发布路径不存在证明。目标路径已有未知对象或出现未绑定的 staged/unstaged/工作树变化时停止。
2. 在 `.knowledgeflow/transactions/` 的流程自有 staging 中生成完整 `map.yaml + map.md + 运行记录`，或同一决定版本的 `vNNNN.yaml + vNNNN.run.json`，保存稳定 `transaction_id`，验证范围账、引用、路径、哈希和不可变版本号后再发布；不得覆盖旧地图或决定。
3. 回读最终字节后，使用总览第 4.1 节的受控版本适配器，以隔离索引和基础 commit 比较后更新受管 ref，再只对齐本批路径在默认索引中的条目。commit 只包含本次地图/运行记录或决定记录；blob 必须等于回读字节，目标外用户 index 与工作树改动不得被提交、清空、改写或改变 staged/unstaged 含义。
4. 结果 commit 写入被忽略的本机回执；受版本控制的运行/决定记录只保存非自引用事务身份。Git 已提交但回执尚未闭合时保持未完成，后续地图决定、Prepare 和 Apply 均被阻塞。
5. 只有事务、原始或重建回执、结果 commit、文件和来源绑定全部匹配时才发布 `map_ready`、`map_closed` 或 `change_requested`。中断后只能依据本事务证据继续、精确恢复前态或进入 `recovery_required`，不能仅因文件存在就推断成功。

干净 checkout、换机或本机回执缺失时，只能从地图运行记录或决定运行旁车中的事务身份、唯一带相同身份的可达 commit、地图/决定摘要、来源/`raw/` 绑定和当前字节确定性重建回执；链条不唯一、受管 ref 漂移或目标路径被未知后续 commit 修改时失败关闭。

无目标地图和决定使用同样的稳定身份、不可变目录、流程自有事务与原子发布规则，但不创建 Git 仓库。它们的本机回执绑定工作根中的最终路径与哈希；以后复制到目标 KB 时再按有目标发布事务建立独立检查点，不把原工作根回执冒充 KB 提交。

以后选定目标 KB 时，可以把无目标工作区中该地图版本的完整目录和决定记录作为同字节副本登记到目标 `proposals/`，并记录原路径和相同工件摘要；不能借迁移改写地图后仍沿用旧决定或批准。

`curation_work_root` 必须由部署配置给出，不能硬编码为某台机器的盘符，也不能放入 Capture Store 内部。已发布地图、用户修改与决定属于用户工作成果，不得按临时缓存规则清理；它们的备份与保留策略由部署层另行配置。

## 8. 从地图到决定

用户至少可以：

- 查看原文证据；
- 修改、接受、拒绝或延期地图中的候选；
- 要求扩大/缩小处理范围或生成新地图版本；
- 保存地图并结束；
- 选择或更换一个目标 KB；
- 请求 SOP-30 根据当前地图版本准备精确变更集。

上述选择必须先形成绑定精确地图的不可变决定记录。“请求准备变更”只授权 SOP-30 使用该决定记录生成 T2 方案，不授权写入。地图审核和变更方案可以连续呈现，但最终执行必须另有绑定完整变更集的批准。

## 9. 幂等与失败

- 相同 `curation_run_id`、精确来源、范围和处理器配置重试，不重复发布相同地图版本；同一 `decision_set_id/version` 也不得被覆盖。
- 同一运行身份但来源、范围、目标或处理器配置不同，返回冲突或显式创建新运行/版本。
- 处理器中断、输出无效、引用无法回读或范围账不平时，不发布 `map_ready`；保留可证明属于本次运行的诊断与成本事实。
- 临时模型输出可重建并可清理；用户修改、决定、已发布地图和成本记录不可当作缓存静默删除。
- 预算不足时停止并把未处理范围记为 `deferred`，不得用看似完整的叙述掩盖。

## 10. 输出回执

成功回执至少包含：`curation_run_id`、`map_id`、`map_version`、`map_sha256`、`map.yaml`/`map.md` 路径及各自哈希、来源身份、目标绑定或 `null`、处理/延期/失败范围摘要、处理器身份、调用/时间/成本、状态 `map_ready | map_closed | change_requested`。进入 `map_closed/change_requested` 时还须包含相应 `decision_set_id + version + decision_sha256`。

## 11. 首个实现验收

至少覆盖：

- 目标已知和目标未知两条入口；未知目标不会创建 KB 或 `raw/`。
- 只有路由授权而没有深度授权时拒绝运行；有深度授权但无目标时允许生成地图。
- 相同来源与参数双跑得到相同机械区段和 locator；多字节、CRLF/LF、表格、代码块和长段可回读。
- 字节区间严格按零基半开规则工作，端点不切断 UTF-8 字符；一基行号在 LF、CRLF、无尾随换行和组合字符场景下都能回读同一原文。
- 处理、延期、失败范围完整且不重叠；预算停止不会伪装成完整处理。
- 历史对话中的命令、链接和工具示例保持数据身份，不被执行。
- 来源主张、系统推断和外部核实状态明确分离。
- 地图修改形成新版本并使绑定旧地图的后续批准失效。
- 候选 ID、地图工件摘要和决定记录可以被 SOP-30 机械绑定；只改变用户决定不会覆盖地图，改变候选含义不会悄悄复用原 ID。
- 有目标地图/决定在文件发布、受管 ref 比较后更新、commit、回执任一故障点都不会提前发布状态；干净 checkout 只在证据唯一时重建回执。
- 目标 KB 存在不相关的 staged/unstaged 改动时保持原样；批准路径重叠改动或受管 ref 并发漂移时安全停止。宿主 Git 配置不得改变 blob 字节、技术提交身份或触发外部/网络副作用。
- 地图处成功结束时不产生 T3 内容；请求继续时只生成未执行的变更准备请求。

本文通过评审和版本化之前，`prompts/` 中沿用历史编号 SOP-001 的文件仍只是实验处理器资产，不是现行执行契约。
