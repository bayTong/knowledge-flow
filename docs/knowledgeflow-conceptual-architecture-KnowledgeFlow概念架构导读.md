# KnowledgeFlow 概念架构导读

> 状态：`Explanatory Guide`（非规范性）<br>
> 最近修订：2026-09-24<br>
> 作用：用一条主线解释 KnowledgeFlow 的核心概念、信任层和典型使用方式。<br>
> 非作用：本文不建立第二份产品需求，不冻结机器 schema、处理策略或实施顺序，也不记录当前开发进度。

## 怎样阅读本文

本文适合希望快速理解以下问题的读者：

- KnowledgeFlow 与普通文件归档、RAG 聊天和自动 Wiki 有什么区别；
- 来源、工作知识、提案和可信知识怎样连接；
- Ontology、Schema、SOP、知识图谱、RAG 和 GBrain 分别负责什么；
- 为什么用户无需先建好知识库或领域模型；
- 系统可以自动做到哪里，哪些决定仍然属于用户。

产品目标和需求以[主产品需求文档](requirements-and-governance-baseline-需求与治理基线.md)为准；主题权威和冲突裁决以[设计权威与冲突登记](design-authority-and-conflict-register-设计权威与冲突登记.md)为准。本文与权威规范冲突时，应修改本文，而不是反向覆盖规范。

## 两分钟理解 KnowledgeFlow

KnowledgeFlow 解决的不是单纯的“把文件保存起来”，也不是“让模型自动生成一个看起来完整的知识库”。它把知识工作分成三个可以逐步发生的结果：

```text
来源可靠保存
    ↓
形成可搜索、可浏览、可问答但尚未获可信身份的工作知识
    ↓
将值得长期稳定的部分，经证据和批准晋升为可信知识
```

用户可以从想法、材料、问题、研究主题、已有知识库或模糊意图开始。系统负责大量可委托劳动，例如保存、检索、比较、摘要、解释、聚类、发现关系和准备变更；用户负责目标、取舍、可信判断和高影响变化。

由此得到五条核心认识：

1. 保存原文不等于理解原文。
2. 可以立即使用的回答、摘要和图谱不等于可信知识。
3. 用户无需在开始前定义完整 Schema、Taxonomy 或 Ontology。
4. 不是每项知识工作都必须形成正式知识库。
5. 需要改变可信内容时，批准对象必须精确，执行结果必须可验证和可回滚。

## 一张图理解目标架构

```text
                         │ 临时集合、候选图谱       │
                         └───────────┬────────────┘
                                     ▼
                         ┌────────────────────────┐
                         │ T2 候选与提案           │
                         │ 证据、范围、影响、diff   │

                                             │

                                             │

```

路由不是所有工作的前置条件。Capture 可以保持未分配，研究任务也可以先产生有来源的工作结果；只有准备归入某个知识空间或改变其可信内容时，才必须明确目标身份和相应政策。

工作知识空间是面向用户的逻辑视图，可以联合显示 T0 来源、T1 派生结果和相关 T2 提案，但必须标明各自状态。它不是第五个信任层，其物理 Store 和界面尚需独立设计。

## 四层信任模型

| 层 | 典型内容 | 可以怎样使用 | 不能被误解为什么 |
|---|---|---|---|
| T0 来源事实 | 原始文本、版本、哈希、来源和用户明确意图 | 回读、引用、恢复和重新处理 | 内容已经正确、已理解或已分类 |
| T1 工作知识 | 来源卡片、索引、摘要、提纲、问答、临时集合和候选图谱 | 搜索、浏览、学习、追问和临时组织 | 用户已经批准的知识结论 |
| T2 候选与提案 | Evidence Bundle、策展地图、路由/结构/变更提案 | 比较、修改、接受、拒绝或延期 | 已经执行的可信变化 |
| T3 可信知识与治理 | 获批知识产品、稳定结构、可信关系、批准和检查点 | 长期阅读、编辑、维护、发布和回滚 | 可以被 RAG、模型或镜像自动覆盖的缓存 |

T0 是规范来源事实，但不是“可信知识结论”；T1/T2 可以很有用，但“可用”与“已批准”必须保持区别。

## 核心概念边界

| 概念 | 主要回答的问题 | 在 KnowledgeFlow 中的位置 |
|---|---|---|
| 当前知识任务 | 用户现在想保存、研究、理解、组织还是维护什么 | 所有处理的直接起点 |
| KB 长期目标 | 一个持续知识空间为什么存在、长期服务什么 | 可选上下文，不是开始工作的前提 |
| 策展策略 | 什么值得成为候选或长期稳定，以什么粒度保留 | 连接当前任务、长期目标和审核预算 |
| Schema | 一类记录、提案或页面怎样表示才合法 | 表示规则；不同对象可以有不同 Schema |
| SOP | 谁在什么条件下按什么步骤执行，在哪里暂停、验证和回滚 | 执行流程和控制边界 |
| 受控词表 | 重要名称和别名怎样统一 | 轻量、可选的语义治理工具 |
| Taxonomy | 内容怎样形成稳定的上下级分类和导航 | 有层级需求时使用，不是统一前置 |
| Ontology | 有哪些概念、关系和约束，它们分别意味着什么 | 复杂语义需要跨内容稳定复用时按需建立 |
| 知识图谱 | 具体对象和关系怎样被表达、浏览和查询 | 可以使用正式 Ontology，也可以先使用较轻的类型与关系规则；候选和可信图必须分开 |
| 策展地图 | 一批材料有哪些主题、证据、关系、缺口和组织候选 | T2 审查工件，不是最终知识库 |
| RAG | 怎样从大规模材料中检索证据并回答当前问题 | T1 访问与证据组织能力，不是可信写入器 |
| GBrain | 可选的镜像、检索、派生或候选图谱后端 | 可替换适配器，不是本地真源 |
| Karpathy LLM Wiki | LLM 持续维护 `raw / wiki / schema` 的文件式知识组织模式 | 可选参考模式；KnowledgeFlow 另外增加来源版本、候选隔离、精确批准和回滚 |

[Karpathy 的原始 LLM Wiki 说明](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)把它描述为一种可由使用者和 Agent 共同具体化的抽象模式，不是所有知识系统必须遵循的固定产品规范。

### Ontology 与知识图谱不是必经层

```text
只需保存和全文查找
→ 原始材料 + 搜索

需要临时聚合
→ 集合、专题或自由标签

同义词和重复命名反复造成成本
→ 受控词表候选

需要稳定层级导航
→ Taxonomy 候选

需要复杂类型、关系和一致性约束
→ Ontology 候选

需要保存和探索大量具体对象关系
→ 候选或可信知识图谱
```

这不是强制升级路线。知识图谱可以在轻量 Schema 下开始，Ontology 也可以只服务语义约束而不要求图形界面。只有真实检索、学习、推理或维护价值出现时，才值得把相应结构稳定下来。

## 任务、意图和处理策略怎样汇聚

“用户目标”不是一个固定字段，也不等于必须先建立完整 KB Profile。系统可能同时获得以下上下文：

| 上下文 | 作用 | 是否可以缺席 |
|---|---|---:|
| 全局产品需求与治理 | 约束所有流程的信任和权限边界 | 否 |
| 用户当前任务 | 定义这一次要保存、研究、理解、组织或维护什么 | 通常需要；纯捕获可只表达最小意图 |
| Capture `user_intent` | 记录捕获时用户明确给出的目标和处理意图 | 可以 |
| KB 长期目标和政策 | 提供持续知识空间的范围、受众和结构上下文 | 可以 |
| 已有可信知识和结构 | 作为只读比较和维护基线 | 可以 |
| 材料规模、风险、成本和审核预算 | 帮助选择处理深度 | 可以部分未知 |
| 历史使用反馈 | 帮助改进建议 | 可以 |

这些上下文汇聚成本次可解释的处理建议，而不是形成“先建 KB → 先定 Ontology → 才能处理”的单向前置链。模型推断和历史习惯不得伪装成用户原始意图。

### `processing_mode` 与 `processing_profile`

| 概念 | 回答的问题 | 性质 |
|---|---|---|
| `processing_mode` | 用户捕获时希望只保存、作为原料，还是允许较深处理 | 写入 Capture 的明确用户意图；当前值为 `capture-only`、`raw-source`、`deep-curation` |
| `processing_profile` | 对这批材料实际采用高覆盖、分层还是检索优先 | 可解释、可覆盖、可重算的派生策略；当前仍是 Draft |

当前三个候选 Profile 是：

| Profile | 适合条件 | 第一成果 |
|---|---|---|
| `full-map` | 有界、高价值、预计能够完整审核的材料 | 较高覆盖的策展地图、证据和盲区 |
| `hierarchical-map` | 中等规模、章节清楚、需要快速全局理解 | 文档总览、章节地图、风险和热点 |
| `retrieval-first` | 大型、持续增长或问题尚不明确的语料 | 分段索引、处理台账、查询 Evidence Bundle |

这些名称只描述当前方法假设，不是完整产品的三种固定使用方式。任何策略都必须显示处理范围、未处理或延期内容、证据位置和已知偏差。

## 自动化和人工决定的边界

| 操作级别 | 默认处理 |
|---|---|
| 低风险、确定性、可重建的机械操作 | 自动执行并留记录，例如哈希、格式校验和索引重建 |
| 可逆的工作知识生成 | 在任务范围内自动生成或重算，例如摘要、检索、问答、聚类和临时结构 |
| 普通可信语义变化 | 系统先准备证据和精确批次，用户可以批量批准、修改或退回 |
| 高影响结构、范围、删除或发布变化 | 展示具体影响、依赖和回滚点后精确批准 |
| 技术失败恢复 | 受限执行器按已冻结协议自动恢复安全状态，不产生新的语义决定 |

系统尤其不得自行：

- 静默改变用户问题、目标、范围、成本或隐私约束；
- 宣称用户已经理解或接受某个模型输出；
- 把回答、摘要、临时地图或候选图谱直接提升为可信知识；
- 新建或激活正式 KB，扩大领域，或改变稳定 Schema、Taxonomy、Ontology；
- 合并重要概念、删除或发布可信知识；
- 把一次批准或过去习惯解释成无限期授权；
- 在批准后重新生成不同正文并以原批准名义写入。

用户决定“可信层应该改变什么”；受限执行器负责“按获批对象准确执行、验证并留下审计记录”。

## 四类代表场景

### 低摩擦日常捕获

用户说：“先帮我保存这些想法，有空再整理。”

```text
原文进入 T0
→ 形成来源卡片和明确状态
→ 在成本和隐私允许时生成摘要、相似项或临时主题（T1）
→ 用户以后可以保留、延期、归入专题或选择性晋升
```

这里不需要先创建知识库、Taxonomy 或 Ontology。第一成果是可靠保存，以及能够找回和理解处理状态的最低工作知识。

### 陌生领域研究与学习

用户说：“我不懂量子计算，先帮我研究并建立学习路径。”

```text
问题或研究主题
→ 收集和比较可追溯来源
→ 生成 Evidence Bundle、概览、术语和临时概念关系
→ 用户通过追问、换角度和纠错逐步形成理解
→ 系统根据真实使用提出组织方式
→ 用户可以只保留研究成果，也可以选择建立长期知识空间
```

结构在使用中逐步形成，而不是用户开始研究前必须提交的分类树。

### 已有知识库维护

用户说：“把新资料和我的 Agent 学习库对齐，只让我看关键差异。”

```text
已有 T3 可信知识作为只读基线
        +
新材料的 T0 来源事实
→ 匹配、去重、冲突分析和证据绑定
→ 普通更新形成边界清晰的批次
→ 高影响结构变化单独展示影响
→ 用户批准后由受限执行器执行、验证并保留回滚点
```

系统承担逐页比对和变更准备，用户把注意力放在高价值差异和语义取舍上。

### 大型持续语料

```text
来源事实
→ 确定性分段、处理台账和可重建索引
→ 查询触发证据检索和有引用回答
→ 反复出现或价值较高的局部候选逐渐稳定
→ 需要时才形成词表、Taxonomy、Ontology、图谱或可信页面提案
```

未被查询触发的内容不能被暗示为已经完成语义提取。第一成果是可溯源访问和局部理解，而不是代价失控的“完整知识地图”。

## 常见误解

- **Capture Store 就是完整产品。** 它只解决来源可靠保存，是后续知识工作的底座。
- **生成摘要就等于入库。** 摘要属于工作知识，除非经过相应治理，不是可信结论。
- **所有材料最终都要变成 Wiki。** 一次问答、研究工件或只保留来源都可能是正确终态。
- **Ontology 越早越完整越好。** 没有真实复用价值的结构会增加冷启动和维护成本。
- **RAG 可以代替知识治理。** RAG 解决检索和证据组织，不决定哪些内容应获得可信身份。
- **人工负责最终决定，所以人工必须做全部工作。** 系统应先完成机械劳动、证据和变更准备，再让用户聚焦高影响判断。
- **Git commit 就等于业务批准。** 技术版本记录不能替代用户对精确语义对象的批准。
