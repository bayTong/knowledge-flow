## 1. 使用规则

1. **按主题确定权威。** 不按文件长度、更新时间或编号大小判断优先级。
2. **产品义务与实现事实分开。** `Approved Design` 不等于已经实现；实现范围和证据只由项目状态、代码、测试和验收材料证明。
3. **现行契约优先于历史理由。** `archive/`、`docs/research/`、`prompts/` 和 `examples/` 只用于追溯或实验，不能形成当前授权。
4. **冲突只登记实质分歧。** 只有会改变用户结果、权限、规范数据、长期契约、显著成本或不可逆副作用的分歧，才需要在本文件裁决；普通可逆实现细节采用最小合理方案。
5. **动态状态不在这里更新。** 本文件只在主题权威、稳定裁决或长期依赖变化时修改。

## 2. 文档状态词

| 状态 | 含义 |
|---|---|
| `Draft` | 方法或设计仍待实验、评审或裁决，不能作为最终实现义务 |
| `Review Candidate` | 已形成可复核候选，但尚未获准成为最终执行契约，也不构成编码、模型调用或真实写入授权 |
| `Approved Design` | 产品或设计规则已经确认，可供后续契约和实现细化，但不证明已有实现 |
| `Approved Implementation Contract` | 指定范围可用于实现和验收；仍不等于对应代码已经完成 |
| `Implemented` | 指定范围的版本化实现已按批准契约通过要求的本地与远端门禁；不自动表示生产就绪或产品有效 |
| `Effective` | 已实现、验收且当前运行系统必须遵守 |
| `Superseded` | 对应主题已由新规范取代，仅供迁移与追溯 |
| `Historical` | 历史、研究或形成过程，不参与当前设计决策 |

## 4. 已确认的跨主题决策

### 4.1 捕获与来源事实

| ID | 稳定裁决 |
|---|---|
| `D-001` | 本地 Capture Store 是捕获事实真源；外部镜像和索引均为可重建派生物 |
| `D-002` | 捕获时不要求先选择或创建知识库 |
| `D-003` | Global Intake 是未分配 Capture Item 的逻辑队列，不是第二个知识库或第二份原件 |
| `D-004` | 捕获成功只依赖本地原子保存；模型、网络、GitHub、GBrain 和知识库写入不得进入成功前置条件 |
| `D-005` | 模型产生的路由、摘要、关系和结构只能先成为提案 |
| `D-006` | SOP-10 只在用户明确授权新建知识库时运行 |
| `D-007` | GBrain 是可关闭的异步工作层，不是本地捕获和回读前置 |
| `D-008` | MVP-0 的已实现承诺限定为单机、单用户、文本捕获范围 |

### 4.2 处理质量与知识工作

| ID | 稳定裁决 |
|---|---|
| `D-009` | 不承诺语义零遗漏；承诺来源、处理范围、缺口和证据可见 |
| `D-010` | 深度处理允许分层和按需，不要求所有材料都生成统一完整地图 |
| `D-011` | RAG、动态图谱、摘要和问答结果属于派生或候选层，不能自动成为可信知识 |
| `D-012` | 处理记账覆盖、证据绑定覆盖和语义召回必须分别衡量 |
| `D-013` | 用户可以从材料、问题、研究主题、已有 KB 或模糊意图开始，不以前置完整结构开始 |
| `D-014` | Schema、词表、分类、Ontology 和知识图谱是可选、渐进、可提案的成果 |
| `D-015` | 人工闸门按风险和影响分层，不能把全部阅读、分类和策展劳动转嫁给用户 |
| `D-016` | 知识应先可靠纳入并可用，再按证据与价值选择性晋升 |

### 4.3 深入策展

| ID | 稳定裁决 |
|---|---|
| `D-017` | 先形成或复用精确 Capture 来源版本；只有目标确认后才把原料映射到目标 KB 的 `raw/` |
| `D-018` | 目标已知、目标未知、无目标地图和无原料预建是不同合法入口，不得强迫统一先建库 |
| `D-019` | 策展地图可以是一次任务的成功终点，但仍是工作/提案工件，不自动成为可信 Wiki |
| `D-020` | “放入某库”“允许深度处理”“批准写入可信知识”是三项独立权限 |
| `D-021` | 未指定名称的新 KB 使用日期序号分配初始名称；稳定身份与以后可修改的显示名分离 |
| `D-022` | 首个深入策展纵向切片只使用一个全新隔离 KB；已有活动库、多目标和多 KB 后置 |
| `D-023` | 核心格式与治理语义不得硬编码盘符、Windows 用户名、NTFS、ACL、BitLocker 或固定磁盘布局；Windows 只是首个已验收平台 Profile |
| `D-024` | Capture 与无目标地图不依赖 Git；首版中，地图一旦绑定受管目标 KB，其受管地图、决定和后续 T3 可信 Wiki 必须进入该 KB 无 remote 的本地 Git 版本历史，但 GitHub、远端、账号和网络都不是运行前置 |

## 5. 尚未闭合的设计门禁

| 主题 | 已确认边界 | 仍需在何时裁决 |
|---|---|---|
| P0C 历史浏览与错误提示 | 交互契约已批准，但当前界面尚未实现；不新增公共 Capture 操作 | 只有其阻塞代表旅程或进入独立 UX 批次时 |
| SOP-30 可信写入 | 必须分离 Prepare、批准和确定性 Apply；旧 SOP-002 不得执行 | `CUR-MVP-1` 通过后，进入 `CUR-MVP-2` 前 |
| 低摩擦批量整理 | 先用真实零散样本证明净用户收益，不把一次授权扩成永久后台授权 | 深入策展首条纵向链通过后 |
| 多来源检索与 RAG | 先比较普通文件查找、精确/关键词检索，再按失败证据决定 embedding、重排序或 RAG | 独立检索实验门禁 |
| Task、Ledger、Profile、Evidence、Candidate 的长期持久化 | 只冻结被真实线路共同需要的最小身份和状态；其余保持派生可重建 | 至少两条价值线路给出证据后 |
| URL、文件、音频、OCR | 先定义原始输入、大小、快照、失败降级、派生和敏感数据边界 | 开放对应入口前 |
| GBrain、图谱、QQ、远程和多设备 | 必须证明相对本地基线的增益，并保持可关闭 | 核心本地旅程证明价值后 |
| 正式私人/高敏内容和发布 | 当前低敏感度实验不能外推为高敏保护或生产就绪 | 相应内容或发布声明进入范围前 |

具体当前阻塞、已完成实现和下一授权不在本表维护，统一见[项目状态](project-status-项目状态与当前门禁.md)。

## 6. 编号空间

| 形式 | 含义 |
|---|---|
| `FR-*` / `NFR-*` | 主 PRD 中的产品义务 |
| `P1`–`P12` | 主 PRD 中的长期治理原则 |
| `D-*` | 本文件中的稳定跨主题裁决 |
| `C-*` | 历史冲突编号；完整内容只在历史快照中查询 |
| `C0`–`C8`、`CUR1A` 等 | 实施批次；不是冲突编号或产品版本 |
| `CT-*`、`CLI-*` 等 | 对应测试矩阵中的验收场景 |
| `T0`–`T3` | 信任层；不是磁盘格式或实施顺序 |
| `SOP-*` | 标准操作流程；编号表达流程内阅读顺序，不表达权威等级或完成状态 |

## 12. 批准的方向与阶段顺序

> 为兼容既有文档锚点，本节保留原编号 `12`。它只冻结依赖顺序，不维护当前执行位置，也不预先授权下一阶段。

| 顺序 | 产品里程碑 | 完成含义 |
|---:|---|---|
| 1 | 可靠 Capture 与最小本地使用 | 原料可保存、读取、追加、恢复，并有最低可用本地入口；已测范围不外推为完整产品有效 |
| 2 | `CUR-MVP-1` 首个可用策展地图 | 精确来源、目标确认或跳过、可选新隔离 KB/`raw/`、范围/证据与可查看、可修改、可在地图处结束的结果形成一条真实纵向链 |
| 3 | `CUR-MVP-2` 单一新 KB 可信写入 | 从已复核地图形成精确方案，经人工批准后确定性写入、激活、回读、检查点和恢复 |
| 4 | `CUR-MVP-V` 双终点验收 | 分别验收地图终点和可信写入终点，记录理解收益、人工负担、失败与成本 |
| 5 | 深入策展扩展与低摩擦线路 | 先按证据扩展已有 KB/冲突处理，再独立验证零散笔记整理；不建设未经证明的后台平台 |
| 6 | 多来源检索与共享工作知识 | 先验证本地基线，再决定 RAG；只冻结多条线路共同证明需要的长期契约 |
| 7 | 可选集成、发布和高敏硬化 | GBrain、图谱、URL/文件、完整界面、远程、多设备和安全硬化按真实触发条件进入 |

优先级固定为：**数据安全或越权阻塞缺陷 → 当前门禁的用户任务阻塞 → 最短价值闭环 → 方法质量实验 → 发布与高敏硬化 → 可选集成和远期架构**。

## 13. 维护规则

1. 新冲突必须写清当前请求、冲突基线、用户影响、推荐方案和需要裁决的精确问题；普通实现细节不进入本文件。
2. 裁决形成后，应修改真正负责该主题的需求或契约；本文件只保留跨主题摘要和路由，不复制全部机器细节。
3. 已实现冲突的逐项形成记录移入历史快照，不在现行入口持续追加提交号、CI 运行号和测试数量。
4. 当前状态只更新项目状态文档；历史变化写入 `CHANGELOG.md`、验收报告或归档。
5. 每次整理必须保留旧裁决可追溯入口，不以“减少文件”为理由删除有效需求、契约或证据。
