## 1. 方向判断与完成范围

赞成按用户提出的顺序推进。已有 SOP 的业务骨架足以作为起点，当前需要做的是修订其中与新捕获系统、来源证据和批准执行机制不一致的部分，然后沿一条完整业务链实现与验收。

本轮“完整”同时区分**用户任务的合法终点**和**项目能力的阶段验收**。有原料时，外部文件先形成或复用精确 Capture 来源版本；随后根据用户是否已经明确目标 KB 进入不同判断分支。用户可以只形成并保留可核验、可修改的策展地图，也可以继续准备精确变更并在批准后完成写入、回读验证、检查点与报告。无原料时，可以只完成指定位置的 provisional KB 初始化并报告待用状态。地图处结束是成功的用户任务；但深入策展阶段要宣称具备完整产品链，仍须实际验收至少一条可信写入路径。

第一版采用本地、单用户、文本来源和一种明确的 Markdown KB 组织方式。该实现范围不把固定 Wiki 模板升级为全项目唯一组织模型。URL/PDF/OCR、多 KB 自动路由、图数据库、后台调度和低摩擦自动处理留到各自需要时设计。

与此前三线价值实验排期相比，本建议将深入策展的知识写入闭环提前到低摩擦与独立多来源检索实验之前。这个调整需要由活动方案承接；主 PRD 的通用产品目标和可信批准底线仍适用。此前实验协议中的来源版本、证据回读、范围与成本记录方法可以复用，不要求先完成其全部三条线路。

### 1.1 入口分支、两级保存与合法终点

“保存精确来源”和“把原料放进目标 KB”是两个不同动作，不能合并成一句“存入知识库”：

1. **精确来源保存**发生在 Agent 分析之前。新外部材料先进入 Capture Store，形成不可变 Capture Version、Payload 哈希和 Envelope；已经存在的来源复用指定版本，不重复捕获。
2. **目标 KB `raw/` 归档**只在用户确认目标 KB 后发生。它是可核验的机械复制与来源映射，不改变 Capture Store 的规范原件身份，也不等于批准深度处理或可信知识写入。

| 场景 | 入口需要完成什么 | 后续流程 |
|---|---|---|
| 有原料，用户已明确已有库或要求新建库 | 从精确来源做有界适配检查；目标明显不合适时给出建议和理由，由用户确认最终选择。已有库检查身份、状态与写入能力；新库补齐父目录并按 SOP-10 初始化 | 目标确认 → 机械归档到该 KB `raw/` 并校验来源映射 → 生成地图 → 在地图处结束，或继续精确方案、批准与写入 |
| 有原料，用户不了解材料或未确定目标 | 基于精确来源生成只为路由服务的有限“原料梗概”，展示现有 KB 与适配理由；让用户选择已有库、新建库、暂不选库只生成地图，或暂不深度处理 | 选择 KB 时先检查/初始化并归档 `raw/`；不选库时直接从 Capture 版本在任务工作区或未审核提案区生成地图；暂不处理时只保留来源版本 |
| 无原料，预先建库 | 明确父目录；有明确名称则使用，未命名则分配日期序号；检查目标后创建基本目录、稳定身份、临时状态和模板说明 | 初始化验收与待用报告后结束；不生成地图、Schema 或可信知识，后续有原料时复用该 KB 身份 |

“原料梗概”只服务目标判断，不等于正式策展地图，也不能声称已经理解全文。选择了目标 KB 时，正式地图在目标确认、必要结构准备和 `raw/` 归档之后生成；暂不选库时，正式地图可以直接绑定 Capture 精确版本生成，不得为了地图强迫建立或选择 KB。模型不能自行把建议变成最终归属。

用户已给出明确、可执行且检查通过的已有库命令时，该命令可作为目标授权；检查结果可展示，不反复询问相同问题。存在有依据的适配偏差时按用户要求建议并确认，低置信度建议不自动否定用户选择。路径冲突、库不可写等客观执行问题须说明并修正后继续。

至少存在三个彼此独立的权限边界：

1. **放进某个库**：只授权目标归属、必要建库和 `raw/` 机械归档；
2. **允许深度处理**：授权在明确来源和范围上生成 T1/T2 策展地图；
3. **批准写入可信知识**：绑定地图/方案版本、目标前置状态和精确 diff，才允许改变 T3。

前一项不自动包含后一项。明确的新建命令加确定父目录可以构成临时初始化授权；它不自动批准深度处理、知识正文、领域、结构或可信写入。地图与精确变更可以在同一审核入口连续呈现，但执行前仍须能证明用户批准了完整待执行对象。

长期需求允许用户确认多个目标库，但不把它放进首个实现。首个垂直切片只支持一份来源和一个目标 KB；既有 active KB 支持在首条新 KB 链通过后增加，多 KB 的独立方案、独立批准、逐库恢复和汇总报告再作为后续扩展设计，不能提前制造跨库事务。

### 1.2 新 KB 的初始命名与策展后显示名

用户明确给出名称时沿用该名称；用户只要求新建而没有给出名称时，首版使用 `YYYY-MM-DD-NN`，例如 `2026-10-13-01`。日期取配置时区，序号在同一父目录和同一天内递增，并在分配时用锁与目标冲突检查避免并发重名。该名称只承担稳定占位和显示职责，不声称已经知道领域；`kb_id` 是独立、不可变的身份。

首批策展入库成功后，Agent 根据获批内容、实际边界、排除范围和与其他 KB 的区分，给出一至三个显示名称及理由。用户可以接受、修改、保留日期序号或延期决定。首版只修改 `kb.yaml` 的 `display_name` 与 README 中的显示名，`kb_id` 和物理目录保持不变；物理目录改名若未来确有必要，必须作为检查链接、配置与并发编辑的独立迁移操作。

## 3. 历史 SOP-001：逐步审查（现由 SOP-20 承接）

旧版正文位置为 `archive/2026-design-history/sop-v2-full.md` L440–L691。以下建议同时检查了现行 A/A-fast/B/C 模板与提取接口；修改旧语句时必须同步各模板，不能只在文件顶部追加免责横幅。

| 原步骤 / 规则 | 判断 | 具体修改与理由 |
|---|---|---|
| 入口“所有新原料无条件粗读” | 修改 | 深入研究入口由本次明确任务或范围清楚的规则触发；已有来源直接选择版本。普通捕获继续可靠保存，不因保存就启动模型处理 |
| 0.1 捕获 URL、PDF、对话并直接写 `raw/` | 拆出 | 捕获交给现有 Capture 与后续各来源适配器；SOP-001 只读精确版本。需要 KB 原料副本时由机械归档步骤处理并保存来源映射 |
| 0.2 按固定字数选择流程 | 修改 | 字数保留为成本信号；实际考虑结构、声明范围和处理器预算。长材料分段处理并记录未处理部分；不得把多个 Pass 当作超长全文的一次性处理保障 |
| 0.3 多原料关系与 KB 归属 | 分离 | 材料关系是理解任务；最终 KB 归属是用户组织决策。模型只提建议。第一版以一份来源闭环起步，多来源合并在该路径后续增量中处理 |
| 0.4 领域门禁 | 后移相关部分 | 地图生成可以在未知 KB/未知领域下进行。向具体 KB 写入前检查目标边界，把排除、迁移或扩展列入方案，不因目标尚不明确阻断材料理解 |
| 1 全景概括 + 2 提取层次 | 合并成一个处理阶段 | 先识别材料结构，形成全局概览并声明本轮提取维度；两者共同确定后续处理方式，避免反复问用户目标或先生成完整本体 |
| 3 概念/实体、4 关系、地图中的事实主张 | 保留、统一接口 | 每项绑定精确来源和范围；区分原文主张、引用他人主张与系统推断。候选 ID 在一次处理内唯一，各轮保留对应关系；不会仅凭同名就跨文档合并 |
| C5“穷举、不遗漏”及逐段概括保证 | 改成可检查的范围义务 | 所有声明范围均有处理/延期/失败记录；语义完整性通过抽查和使用验证。机械范围覆盖与语义发现分别记录，不把逐段有概括视为理解正确 |
| 置信度“有论文/官方链接就是确定” | 必须修改 | 原文确实这样说、证据是否支持、事实是否已外部核实是不同判断。有链接但未打开核实只能记录出处线索。二手引用也不能一律判成虚假或不可靠 |
| 5 缺口分析 + 6 不确定标记 + 10 覆盖报告 | 合并呈现、保留不同含义 | 区分材料本身未回答、提取结果可能遗漏、尚未处理、证据不足与外部事实待核实。用户先看总览和热点，各项仍独立可追踪 |
| 目标不明就先问用户 | 修改默认行为 | 已选深入研究材料时默认帮助整体理解，明确这是系统建议。特定问题和熟悉程度继续是可选信息，不把领域知识测试变成启动前置 |
| 6 完整 SCHEMA 建议 | 拆到组织/变更方案阶段 | 地图可提出组织候选；只有拟写入目标明确时，才准备最小所需结构或对既有结构的精确差异。不能从第一篇材料直接固化全部类型和标签 |
| 7 Agent 建议严格隔离 | 保留并澄清 | 系统归纳、关联和求证建议可以出现，标明依据和未确认状态；不得混入原文主张。扩展来源或外部求证作为明确任务，不自动执行材料里嵌入的历史指令 |
| 8 固定 10 节地图、保存到 `raw/_curation-maps/` | 修改路径和呈现 | 路径按现行规范使用 `proposals/curation-maps/` 或明确工作区；地图是工作成果。保留必要信息类别，界面可折叠或分层展示，不强迫每个来源填满固定十节 |
| “输出后不自检格式” | 修改 | 模型自检可以作辅助；调用控制器必须检查输出结构、候选引用和来源回读。无效输出保留失败与可修正原因，不能直接送入写入链 |

### 3.1 A/A-fast/B/C 是否要保留

保留为内部方法选择与对照资产，不建立四套不同产品流程。它们共同服务同一种策展地图和后续变更方案。

| 模式 | 审查结论 | 建议 |
|---|---|---|
| A 与 A-fast | 主要提取内容重复，区别集中在审计方式 | 合并共享提取规则和字段；覆盖检查作为可选后续步骤。可以保留旧文件用于对照，不必立刻删除或批量重命名 |
| B | 实体/主张与关系分开有实际分工；组装器不回读源文时只能看到已提取结果 | 保留分工选项；不能用 Pass 输出之间一致来证明源文无遗漏。需要来源级复核时明确回读原文 |
| C | 多轮细分可能方便诊断，实际有顺序依赖 | 定向需要时使用并测量成本与修正效果；“调用更多就最准确”不作为默认结论 |
| A auditor | 当前角色明确不评估概念、关系和主张正确性 | 作为覆盖异常检查使用；增加引用支持与关键主张复核的单独检查，不能把覆盖审计当成全部质量验收 |
| B/C assembler | 机械合并、统计与语义分析混在一份提示词中 | ID/引用检查、格式合并和统计交给代码；缺口、跨段联系和组织建议仍属语义处理，按需要调用模型并保留出处 |

第一版先实现一种可运行方法：结构识别 → 分段概览/提取 → 机械合并 → 必要的定向复核。各模型与模式复用相同输入范围、证据和输出验证接口。一次来源里的实体遗漏不会因另一轮只查看已有实体表而自然消失。

## 4. 历史 SOP-002：核心拆分与逐步审查（现由 SOP-30 承接）

旧版正文为 L693–L1110。最重要的修改是拆成两个阶段，暂可在同一 SOP 中用 A/B 小节表达，无需为了命名新增多个独立 SOP：

- **方案准备**：阅读目标 KB，查重、判断新增/更新/冲突，生成目标页面正文、结构变化、导航和链接变更，以及精确 diff；此时可以使用模型。
- **批准后执行**：校验已批准对象与目标前置状态，写入已有方案的精确内容，验证、提交检查点与报告；此时不重新作语义决定。

地图帮助用户理解和选择知识，变更方案说明实际怎样改 KB。二者可以同屏、同批次审核；用户的勾选和修改是形成方案的输入。只需在待执行内容和影响已经完整展示后做一次最终写入批准。执行前没有新增变化就不重复确认；方案正文、目标或范围变化则形成新版本。

| 原步骤 / 规则 | 判断 | 具体修改与理由 |
|---|---|---|
| 1 验证原料与审核地图 | 保留并补充 | 绑定 Capture ID/版本、Envelope/正文身份、地图/方案版本和批准对象；执行阶段还要核对目标 KB 与拟修改文件的前置状态 |
| 同 URL + 同 SHA256 就终止摄入 | 拆分去重语义 | 相同来源可用于新任务、不同处理范围或更新后的 KB，允许重新策展而不重复捕获。同一已提交写入批次重复执行则应返回同一结果，不能再次追加 |
| 2 阅读 SCHEMA/index、全文查重 | 移到方案准备阶段 | 复用“先理解已有库”的规则；检索只读明确目标。index 不是唯一知识正文，查重需要看相关页面，搜索失败或范围不足时保留不确定性，不保证关键词查找能识别所有语义重复 |
| 2.5 领域外内容与领域扩展 | 移到方案中审核 | 明确哪些候选不写入、延期或需要扩展；不能在执行时临时自动截取或扩展领域。材料地图保留完整来源与排除说明 |
| 3 新建/追加/冲突/过时判断 | 保留决策树，移到批准前 | 这是语义规划。展示新旧观点、来源与拟写法，由用户决定保留/修改/延期；实际执行器只处理获批变更集 |
| 新模块、页面类型与归属 | 纳入方案 | 目标路径、模块与类型的变化都可审核；模型不会在已批准内容之外另建模块或 KB |
| 4 自动注册标签、修改 SCHEMA | 必须修改 | 结构变化进入提案并包含在最终批准的 diff 内。沿用现行 C-007 裁决，不恢复旧版自动结构扩展 |
| 5 按模板撰写页面 | 内容生成移到批准前 | 复用模板和真实引用，先形成候选最终正文。批准后应用该正文；不在写入时另让模型重写。由本批所选 KB 格式决定模板，不强制全产品四种页面类型 |
| 至少两个链接、entity 必须有 concept 引用 | 修改为所选 KB 的质量政策 | 关系必须有实际依据；缺少关联时可以待组织或提示，不为满足数量编造链接。若调整既有 KB 的硬规则，该修改也要进入批准方案 |
| 6 更新 index/log 与必要回链 | 保留、纳入同批变更 | 索引、日志及链接目标不能成为未审核附带修改。能从已批准页面机械生成的部分可由代码完成，其生成规则和影响范围明确 |
| 7 八项自检 + SOP-003/004 | 合并公共检查实现 | 内容格式、引用目标、标签、索引和结构一致性复用一个验证器；写入前验证候选结果，写入后回读验证已写字节与审计状态。检查失败不无限调用模型自修 |
| 8 完成报告 | 保留并补充执行事实 | 报告新增/更新/跳过/待决、来源与范围、批准和批次身份、成本、检查与失败恢复结果；由已验证的执行记录生成，模型不凭计划宣称成功 |
| 事务、重试、恢复和撤销 | 必须补齐 | 定义 prepare/apply/verify/commit/rollback、单写入者与前置状态检查、幂等、崩溃恢复及安全停止。Git 检查点是版本证据，不能单独证明多个文件的事务一致性 |

人工批准记录、修改选择和已提交写入事实需要可靠保存；它们不能从原文重新推导，也不能像可重建摘要一样随清理一起删除。只冻结当前路径必要的记录与状态，不先建通用任务平台。

### 5.1 SOP-10（历史 SOP-000A）的执行细节补充审查

SOP-10 本身已有清晰职责和步骤，需要细化其机器执行契约，并修正部分重试/回滚表述。它不承担知识库推荐与材料语义判断；这些属于入口/路由，最终目标仍由用户决定。

| 原条款 / 执行点 | 判断与需细化的规则 |
|---|---|
| 第 2–3 节：何时建库 | 保留明确新建授权。用户指定或确认新建后才运行；未确定归属仍可只生成地图，不因“缺基本结构”自动建库。无原料预建是合法入口 |
| 第 4 节：名称、位置和本地版本模式 | 新库父目录必须明确；用户名称优先，未命名时按 `YYYY-MM-DD-NN` 分配并检查同日序号冲突。操作者、时间和稳定 ID 由系统记录。首个切片固定在新 KB 根内建立无 remote 的 `managed-local` 版本库，不要求父目录已有仓库，也不接管或嵌套用户已有仓库；其他模式明确返回当前不支持 |
| 第 5–7 节：临时状态、目录与 kb.yaml | 保留最小容器、`provisional`、`domain: pending`、`schema: absent`、空可信 wiki；实现前定版 manifest 与可解析校验。基本模板不填造领域、标签和页面体系。可提供模板说明，正式 SCHEMA 随材料和批准方案形成 |
| 第 8 节步骤 0：目标与权限检查 | 明确绝对位置及允许根、重名/类型冲突和路径身份校验；非空非 KB 目录不得被直接覆盖或当成空新库；已有 KB 需核对身份与状态，不靠目录名冒认 |
| 第 8 节步骤 1：稳定 ID、日期序号与显示名 | ID 只在首次成功创建时建立并复用；重试不能换 ID。日期序号的分配必须加锁并与目标冲突检查处于一致边界；slug/物理目录、`kb_id` 与显示名职责分开，首版策展后改名只改显示字段和 README，不偷偷改变存储身份 |
| 第 8 节步骤 2–3：目录和文件创建 | 用可识别的本次事务准备基本文件，验证后公布有效 manifest/登记；中断产生的半骨架不能出现在可用库清单中。任何已有用户文件均不自动覆盖 |
| 第 8 节步骤 4–6：版本检查点、隔离和报告 | 登记位置/ID/临时状态/版本纳管情况和验收结果；空库可被看见并继续添加材料，可信查询可见性在激活时另行开启。Git 或登记失败不能伪报全部步骤成功 |
| 第 11.1 节：同一目标幂等重开 | 保留同一库身份，分别判断已完成、可证明属于本次的未完成初始化和未知目录；仅补充仍符合原请求的缺失机械内容。名称/请求不一致不能无条件合并 |
| 第 11.2–11.3 节：失败与回滚 | 收紧“回到初始化 commit 之前”：恢复仅限本批已证明拥有的 KB 变更，不重置整个本地版本库或抹去后来修改。清理前核对身份、范围和文件是否变化；已含用户原料时保留并报告，另行决定迁移/撤销 |
| 第 12 节：接到 SOP-20/30 | 有原料且用户确认新建时，先完成临时结构和 `raw/` 归档，再由 SOP-20 生成地图和方案；不选库时 SOP-20 可直接绑定 Capture 工作。SOP-30 中的首次启用门禁与首批写入须有一致恢复边界。无原料时在初始化完成处停下，后续再次选库时能识别临时身份并接续 |

至少需要覆盖空目录首次创建、已有库重开、同请求重试、非空目录冲突、日期序号并发分配、创建中断与恢复、用户后续放入文件、显示名修改不改变稳定身份，以及本地版本库初始化/检查点失败。多 KB 逐库状态不属于首个实现。该补充仍是审查建议，不把未定版 `kb.yaml` 草案视作已实现契约。

## 6. 建议的完整业务链

```text
外部文件先形成精确 Capture 来源版本，或选择已有 Capture 精确版本
  → 用户已明确目标？
      ├─ 是：Agent 做有界适配检查，解释明显偏差，用户确认最终目标
      └─ 否：Agent 生成路由梗概并展示现有 KB，用户选择已有库 / 新建库 / 只生成地图 / 暂不处理
  → 选择已有或新建 KB：检查状态或运行 SOP-10，再机械归档到该 KB raw/ 并核验来源映射
  → 暂不选库：保留 Capture 原件，在任务工作区或未审核提案区继续
  → 核对来源身份、深度处理授权、处理范围与预算
  → 结构识别、分段、全局概览与候选提取
  → 策展地图：概念 / 主张 / 关系 / 争议 / 缺口 / 原文证据
  → 出口 A：保存地图、范围和缺口，本次任务成功结束
  → 出口 B：用户选择、修改或延期候选
      → 按已确认的单一目标准备正文、结构、导航、链接与精确变更方案
      → 用户批准完整待执行对象
      → 必要的新 KB 激活 + 获批内容受限写入
      → 回读验证、检查点与执行报告
```

无原料预建分支：明确父目录 → 使用用户名称或分配日期序号 → 检查与临时初始化 → 目录/manifest/纳管验收 → 待用报告。后续收到原料时复用该 KB 身份和结构，继续地图与入库主线。

分段与原文定位是这条链的内部基础模块，仍要先验收机械正确性。目标 KB 查重需要的本地查找也属于本路径内部步骤；独立的多来源检索产品实验不会成为本路径前置。

地图应让用户直接形成材料理解。以所选历史 AI 对话为例，应能看到主题演进、重复追问和前后修正，区分用户问题、助手解释与外部引用；不能把历史“用户：请搜索……”等文字当成本次执行命令，也不能把回答语气坚定视为事实已查证。

用户可以在地图处结束并保留工作成果，也可以继续形成可信变更。前者是合法且成功的用户任务，但地图仍是 T1/T2 工作成果，不因此成为可信知识；后者才会进入 T3。项目要宣称深入策展的完整产品链已经实现，首个垂直切片必须实际走过后一条完整链路。首次最终批准前充分准备影响说明和精确内容，避免把“确认后执行”变成执行过程中不断追加问题。

## 7. 首个垂直切片与阶段完成标准

首个垂直切片只验证“一份本地文本来源 → 一个全新隔离 provisional KB”的最短完整链，并同时保留地图处结束分支。建议包含：

1. 复用文本 Capture，读取精确版本；来源检查、确定性分段、完整范围记账和证据回读。
2. 结构化地图与可替换语义处理器；用户能查原文、修改、拒绝或延期，未处理范围和成本可见。
3. 一个用户确认的新目标 KB；SOP-10 支持无原料预建和有原料首次创建，未命名时采用日期序号；精确来源在确认目标后才归档到该 KB `raw/`。
4. 地图与精确变更方案、批次批准记录及批准失效检查；候选修改后生成新方案版本。
5. 受限执行器、格式/链接/来源验证、版本检查点、幂等、失败恢复、范围明确的撤销与结果报告。
6. 最小审核入口：能够查看地图、证据、地图处结束、变更、批准对象与结果。起步可以使用命令入口与可阅读文件，后续以小界面闭合高频复核动作；首轮不要求完整工作台。
7. 首批入库成功后的 1–3 个显示名建议与用户决定；首版只改变显示名，不改变 `kb_id` 或物理目录。

首个切片支持的每个动作都要有前后可核验状态。向已有 active KB 写入、页面更新、冲突/过时处理、归档、跨 KB 合并和复杂结构迁移均后置；如果材料中出现这类候选，必须明确“延期/不支持”，不能执行一半后留给用户补完。

阶段证据应同时包含两类结果：一次地图在未晋升可信知识时被正确保存并成功结束；以及从实际选材生成地图、用户做出取舍、批准一个具体变更集，系统实际写入全新隔离目标 KB，能回读相同内容，验证与报告准确。重新执行同一批次没有重复副作用；故障注入后能够恢复或明确安全停止；撤销不会抹除原始 Capture 和审计历史。

## 8. 开发与验证顺序

以下是实施建议，批次名称只作说明，不新增项目门禁编号。

| 批次 | 做到哪里 | 本批验收产物 |
|---|---|---|
| SOP 契约重构 | 联合修订入口/路由、深入策展 `00` 总览、SOP-10、SOP-20 和 SOP-30，明确两级保存、三类权限、地图终点、单目标首切片与失败行为；历史 SOP-000B 并入 SOP-30 内部门禁 | 可直接编码的规则及状态流测试场景；解决旧 SOP 与现行规范的冲突。修订本身不执行真实 KB 写入 |
| `CUR-MVP-1` 首个可用地图纵向切片 | 在同一产品里程碑内依次闭合 Capture 读取、分段、范围、精确回读，用户已明确/未明确目标分支，一个新隔离 KB 的 SOP-10/日期序号/登记、确认后的 `raw/` 归档，以及长文分层处理、地图复核和地图处结束 | 机械能力可以拆成独立代码提交与测试，但只有用户能看到有证据地图、打开原文、理解范围/缺口、修改或拒绝并在地图处结束时才算本切片完成；不得把前半段另立为“底座阶段” |
| `CUR-MVP-2` 方案、批准与可信写入 | 按 `CUR-MVP-1` 的单一新 KB 准备精确页面/结构变化，实现批准记录、前置检查、首次启用、实际写入、验证、检查点、幂等、恢复/撤销和报告 | 获批对象可核对，修改后旧批准失效；正常与故障场景通过；激活与可信写入不留下半完成的成功状态；Apply 不重新作语义决定 |

每批实现前只确定该批所需最小输入、状态、格式和验收边界；实现后立即验证，再扩展下一批。`CUR-MVP-1` 内的来源机械检查不要求先人工读完整篇长文，也允许先形成独立提交，但它只是纵向切片的内部停点，不能在地图尚不可用时宣称本阶段完成。结构化地图与批准/事务记录在各自批次中定版，不等待低摩擦路径或所有未来方法实验结束。

| 场景 | 应观察到的行为 |
|---|---|
| 有原料未指定库、已指定库及无原料预建 | 分别走路由梗概与选择、命令检查、临时初始化分支；无原料预建完成处有明确待用报告 |

| 地图/方案被修改，或目标文件在批准后变化 | 旧批准不可继续应用；保留用户修改并说明需要重新准备的部分 |
| 新 KB 激活、页面、索引或日志写入中途失败 | 没有“摄入成功”的虚假报告；按有证据事务恢复或安全停止，不删除不明归属文件 |
| 用户要求已有 active KB 或多个 KB | 首个切片明确报告“后续增量/当前不支持”，不伪装成已具备既有库更新或跨库事务能力 |
| 同一获批批次重复执行、进程中断后重启 | 不重复追加页面/来源/日志；能识别已提交与未提交状态 |
| 一个候选需要超出已批准范围的标签、模块、归档或回链 | 只生成新方案或延期；不借自检扩大语义写入 |
| 回读失败、验证失败或撤销时遇到新用户编辑 | 停止并保留审计，不能覆盖后来编辑或把部分恢复报告为全部恢复 |

源文核查与人工使用结果建立本轮基线，不预设任意语义接受率；机械身份、合法引用与批准/执行一致性仍需全部满足。模型、具体输入/输出预算、总调用数和费用在地图运行批次确定，预算不足时显示缺口并停止或按明确新范围继续。

四条测试笔记保留为以后低摩擦设计的候选材料，本轮不据此设计自动写入规则。与所选目标 KB 有关的查重按该明确目标进行；原先 `E0-R` 的跨文档问题不作为本轮验收前置。
